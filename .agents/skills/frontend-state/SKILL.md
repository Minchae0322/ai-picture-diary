# 상태 관리와 서버 데이터 (frontend-state)

## 목적

상태 관리 문제의 대부분은 **서버 데이터를 클라이언트 상태처럼 다루는 데서** 생긴다. 이 스킬은 상태를 네 종류로 나누고 각각 어디에 두는지 정해서, 전역 스토어가 API 응답 복사본으로 가득 차는 것을 막는다.

기본 도구(2026-09 확인): 서버 상태 **TanStack Query v5**(v6은 RC 진행 중으로 파악, 확실하지 않음 - 적용 전 확인), 공유 클라이언트 상태 **Zustand**(React) / **Pinia**(Vue), URL 상태는 라우터, 로컬 상태는 `useState`/`ref`.

## 언제 적용

새 상태를 만들 때, 상태를 다른 컴포넌트와 공유해야 할 때, API 데이터를 화면에 보여줄 때, "새로고침하면 사라진다"·"화면마다 데이터가 다르다"·"뒤로 가기 하면 초기화된다" 같은 문제, 전역 스토어 설계·리뷰.

> **React Native / Expo라면** 이 스킬을 먼저 읽고, `expo-app-conventions`에서 달라지는 절만 덮어쓴다. 순서를 뒤집지 않는다.

## 0. 상태를 만들기 전에 - 네 가지 중 무엇인가

| 종류 | 정의 | 예 | 도구 |
|---|---|---|---|
| **서버 상태** | 원본이 서버에 있고 클라이언트는 캐시 | 게시글 목록, 회원 정보, 주문 | TanStack Query |
| **URL 상태** | 주소로 공유·복원되어야 함 | 페이지, 필터, 정렬, 선택된 탭, 상세 ID | 라우터 (`searchParams`) |
| **공유 클라이언트 상태** | 서버에 없고 여러 화면이 함께 씀 | 로그인 세션, 테마, 장바구니(로컬), 토스트 | Zustand / Pinia |
| **로컬 상태** | 컴포넌트 하나 안에서만 | 입력 중인 값, 열림/닫힘, hover | `useState` / `ref` |

- 순서대로 판단한다. **서버에 원본이 있으면 서버 상태**다. 스토어에 복사하지 않는다.
- **주소로 공유되거나 뒤로 가기로 복원돼야 하면 URL 상태**다. 필터·페이지를 스토어에 넣으면 새로고침에 사라지고 링크로 공유가 안 된다.
- 로컬로 시작해서 필요할 때 올린다. 처음부터 전역으로 만들지 않는다.
- 전역 스토어는 **작을수록 좋다.** 슬라이스 3~4개(session, ui, cart 정도)를 넘으면 서버 상태가 섞여 들어온 것이다.

## 1. 서버 상태 - TanStack Query

- 서버 데이터는 **컴포넌트에서 직접 `useQuery`를 부르지 않고** feature의 훅으로 감싼다: `useArticles(filter)`, `useArticle(id)`. 쿼리 키와 fetch 함수가 한곳에 모인다.
- 훅 안의 fetch 함수는 `frontend-api-client`의 API 함수를 호출한다. 훅이 URL을 알면 안 된다.
- `staleTime`을 명시한다. 기본값 0은 포커스마다 재요청한다. 목록 30초~1분, 상세 1~5분, 코드성 데이터(카테고리 목록) 10분 이상이 출발점. 실측 없이 확정하지 않는다.
- 파생값은 `select`로. 컴포넌트에서 `useMemo`로 다시 가공하지 않는다.
- 조건부 조회는 `enabled`. `id`가 없을 때 훅을 호출하지 않는 대신 `enabled: !!id`.
- 의존 조회(A의 결과로 B 조회)는 `enabled`로 연결한다. `useEffect`에서 수동 호출 금지.
- 여러 화면이 같은 데이터를 쓰면 **같은 훅, 같은 키**를 쓴다. 자동으로 캐시가 공유된다.

## 2. 쿼리 키

- 키는 **feature마다 팩토리 하나**로 관리한다: `articleKeys.all`, `articleKeys.list(filter)`, `articleKeys.detail(id)`. 문자열 배열을 컴포넌트에 흩뿌리지 않는다.
- 구조는 넓은 것에서 좁은 것으로: `['article']` -> `['article', 'list', filter]` -> `['article', 'detail', id]`. 그래야 `['article']`로 전부 무효화할 수 있다.
- 키에 들어가는 filter 객체는 **직렬화 가능한 순수 값**만. 함수, 클래스 인스턴스, Date 객체 금지(문자열로).
- 키는 fetch 함수의 **모든 인자**를 포함한다. 인자가 바뀌는데 키가 같으면 잘못된 캐시를 보여준다.

## 3. 변경(mutation)과 무효화

- 변경은 `useMutation`을 feature 훅으로 감싼다: `useCreateArticle()`, `usePublishArticle()`.
- 성공 후 **무효화 범위를 명시적으로 정한다.** 기본은 해당 feature의 `all`. 넓게 무효화하는 게 좁게 놓치는 것보다 낫다.
- 응답에 변경된 엔티티가 오면 `setQueryData`로 상세를 바로 갱신하고 목록은 무효화한다. 목록을 손으로 고치지 않는다(정렬·필터 반영이 틀린다).
- 낙관적 업데이트는 **되돌리기 쉬운 단순 토글**(좋아요, 읽음 표시)에만. 롤백 코드가 없으면 하지 않는다.
- 다른 feature의 데이터에 영향을 주는 변경(주문 생성 -> 재고 목록)은 그 feature의 키도 무효화한다. 무효화 목록을 mutation 훅 안에 적어 둔다.
- 변경 중 중복 클릭은 `isPending`으로 버튼을 막는다. 서버 멱등성 키(`api-design`)와 함께.

## 4. 로딩·에러·빈 상태

- 처음 로딩(`isPending`)과 재조회(`isFetching`)를 구분한다. 재조회에 전체 스켈레톤을 띄우면 화면이 깜빡인다.
- 로딩 UI는 **레이아웃이 같은 스켈레톤.** 스피너는 전체 화면 전환에만(`ui-fundamentals` 13장).
- 에러는 `frontend-api-client`의 `ApiError`로 받아 `ErrorCode`별로 처리한다. 문자열 매칭 금지.
- 401은 훅이 아니라 API 계층에서 처리한다(토큰 갱신 또는 로그인 이동). 컴포넌트가 401을 볼 일이 없어야 한다.
- 화면 단위 에러 바운더리를 둔다. 컴포넌트 하나의 에러가 페이지 전체를 지우지 않게.
- 빈 배열은 에러가 아니다. `data.items.length === 0`을 빈 상태 UI로.

## 5. 공유 클라이언트 상태 (Zustand / Pinia)

- 스토어 하나 = 관심사 하나. `useSessionStore`, `useUiStore`. `useAppStore` 하나에 전부 넣지 않는다.
- 스토어에는 **상태 + 그 상태를 바꾸는 액션**만. API 호출은 넣지 않는다(서버 상태는 TanStack Query).
- 선택자로 필요한 조각만 구독한다. 스토어 전체를 구독하면 아무 값이나 바뀔 때마다 리렌더링된다. (Vue Pinia는 반응성이 자동이라 해당 없음)
- 영속화(`persist`)는 세션·테마·설정처럼 **작고 민감하지 않은 값**만. 액세스 토큰은 메모리에, 리프레시 토큰은 httpOnly 쿠키에(`spring-auth`).
- 파생값은 스토어에 저장하지 않고 계산한다(Zustand: 선택자, Pinia: `getters`).

## 6. URL 상태

- 필터, 정렬, 페이지/커서, 탭, 상세 ID는 `searchParams`/라우트 파라미터에. 뒤로 가기와 링크 공유가 공짜로 된다.
- URL 파라미터를 파싱하는 훅을 feature에 둔다: `useArticleListFilter()`가 `searchParams`를 읽고 타입이 있는 filter 객체를 반환한다.
- 기본값은 URL에 쓰지 않는다(`?page=1` 생략). 파싱 시 기본값 적용.
- URL 상태를 다시 스토어에 복사하지 않는다. 진실은 URL 하나.

## 7. 리뷰 체크

- 스토어에 API 응답 복사본이 있는가(있으면 서버 상태로 옮긴다)
- 필터/페이지가 URL이 아니라 스토어·로컬에 있는가
- 컴포넌트에서 `useQuery`를 직접 부르는가, 쿼리 키를 문자열로 흩뿌렸는가
- mutation 성공 후 무효화 범위가 명시돼 있는가
- `staleTime`이 명시돼 있는가
- 401을 컴포넌트에서 처리하고 있는가
- `isPending`과 `isFetching`을 구분했는가

## 하지 말 것

- 서버 데이터를 `useEffect` + `useState`로 직접 가져오기
- 전역 스토어에 API 응답 저장
- 필터·페이지를 스토어에 두고 URL 무시
- 쿼리 키 문자열 하드코딩, 인자를 키에서 빠뜨리기
- 롤백 없는 낙관적 업데이트
- 스토어 하나에 전부, 스토어 전체 구독
- 토큰을 localStorage에 영속화
- 재조회마다 전체 스켈레톤

## 관련 스킬

`frontend-api-client`(fetch 함수, `ApiError`, 401 처리), `frontend-architecture`(훅 위치와 이름), `api-design`(ErrorCode, 커서 페이징, 멱등성 키), `spring-auth`(토큰 보관), `ui-fundamentals`(로딩/빈/에러 화면).
