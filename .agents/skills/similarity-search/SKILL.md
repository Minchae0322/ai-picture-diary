# 유사도 계산 (similarity-search)

## 목적

"비슷한 걸 찾아 줘"는 요구사항이 아니다. **무엇을 비슷하다고 부를지**를 정하지 않으면
어떤 알고리즘을 써도 결과가 틀렸다고 느껴진다. 이 스킬은 (1) 비슷함을 정의하고,
(2) 가장 싼 방법부터 올라가고, (3) 임계값을 감이 아니라 데이터로 정하고,
(4) 한국어에서 무너지는 지점을 피하는 법을 정한다.

## 언제 적용

관련 항목 추천, 중복·도배 검출, 검색어 자동완성, 오타 허용 검색, 태그 자동 부여,
"같은 질문 아닌가요?" 묶기, 표절·재게시 판정, 명칭 매칭(회사명·주소·상품명).

## 0. 시작 전 확인

| # | 질문 | 답이 바꾸는 것 |
|---|---|---|
| 1 | 비슷함의 **뜻**이 무엇인가: 글자가 닮았나, 주제가 같나, 결과가 같나 | 방법 전체 |
| 2 | 짧은 문자열인가(이름·제목) 긴 글인가 | 문자 기반 vs 의미 기반 |
| 3 | 틀렸을 때 비용이 얼마인가 | 임계값. 재현율 우선인지 정밀도 우선인지 |
| 4 | 실시간인가 배치인가 | 미리 계산 가능 여부 |
| 5 | 후보가 몇 건인가 | 전수 비교 vs 인덱스 필요 |
| 6 | 한국어인가 | 형태소 분석기 유무가 방법을 가른다 |

**1번을 한 문장으로 못 쓰면 시작하지 않는다.** "비슷한 글"은 보통 셋 중 하나다:
같은 주제 / 같은 감정·상태 / 같은 사람이 쓴 것. 셋은 완전히 다른 계산이다.

## 1. 방법 사다리 - 밑에서부터

| 단계 | 방법 | 잡는 것 | 비용 |
|---|---|---|---|
| 0 | **정확 일치 / 분류 일치** | 이미 붙여 둔 카테고리·태그·판정 결과 | 0 |
| 1 | **집합 유사도**(Jaccard, 겹치는 태그 수) | 속성이 얼마나 겹치나 | 0 |
| 2 | **문자 유사도**(trigram, 편집 거리) | 오타, 띄어쓰기, 표기 흔들림 | 인덱스 1개 |
| 3 | **어휘 유사도**(TF-IDF, BM25, full-text) | 같은 단어를 많이 쓰나 | 인덱스 + 토크나이저 |
| 4 | **의미 유사도**(임베딩 + 코사인) | 단어가 달라도 뜻이 같나 | 모델 호출 + 벡터 인덱스 |

- **0단계를 건너뛰지 않는다.** 이미 분류해 둔 값이 있으면 그게 가장 정확하고 가장 싸다.
  특히 그 분류가 사람이나 AI의 판정 결과라면, 원문에서 다시 뽑아낸 특징보다 **덜 흔들린다.**
- 단계가 올라갈수록 "왜 이게 비슷하다고 나왔는지" **설명이 어려워진다.** 사용자에게 이유를
  보여 줘야 하면 낮은 단계가 유리하다.
- 섞어도 된다. 0~1단계로 후보를 좁히고 4단계로 순위를 매기는 것이 실무에서 가장 흔한 모양이다.

## 2. 무엇으로 계산할지 - 입력 정규화

같은 방법도 입력을 어떻게 다듬느냐로 결과가 갈린다. **정규화 규칙을 한 곳에 모으고 문서화한다.**

- 대소문자, 공백 축약, 앞뒤 공백, 전각/반각, 유니코드 정규화(NFC/NFD - 한글은 **NFC로 통일**).
- 문장부호·이모지 제거 여부. 지우면 "!!!"만 다른 도배를 못 잡는다.
- 불용어 제거는 **짧은 텍스트에서 위험하다.** 세 단어짜리 제목에서 하나를 지우면 뜻이 사라진다.
- 숫자·단위·날짜는 별도 취급을 고민한다("2개"와 "두 개").
- 색인할 때와 질의할 때 **같은 정규화**를 쓴다. 다르면 조용히 안 맞는다.

## 3. 한국어에서 달라지는 것

- **띄어쓰기를 믿을 수 없다.** "할수있다/할 수 있다"가 섞인다. 공백 기준 토큰화는 그래서 약하다.
- **교착어다.** "좋았다/좋아서/좋은"이 다른 토큰이 된다. 형태소 분석기(은전한닢, Nori) 없이는
  어휘 유사도(3단계)의 이점이 크게 깎인다.
- 형태소 분석기가 없다면 **2단계(trigram)가 현실적인 대안**이다. 어간을 몰라도 글자가 겹치면 잡힌다.
- 조사만 잘라 내는 얕은 규칙은 **짧은 단어에서 뜻을 파괴한다**("비가" -> "비"). 자를 때는
  남는 길이의 하한을 둔다.
- 임베딩은 한국어를 학습한 모델인지 확인한다. 다국어 모델은 짧은 한국어에서 성능이 떨어지는 경우가 있다.
- 검색어는 **두 글자**가 많다. trigram은 두 글자에서 약해지므로 짧은 질의의 폴백을 따로 둔다.

## 4. 임계값은 감으로 정하지 않는다

- "0.8 이상이면 비슷함" 같은 숫자를 **먼저** 정하고 시작하지 않는다. 방법마다 분포가 다르다.
- 절차: 실제 데이터에서 쌍을 50~100개 뽑아 **사람이 비슷함/아님을 라벨링** -> 점수 분포를 보고
  자르는 선을 고른다. 이게 골든셋이다.
- 재현율(놓치지 않기)과 정밀도(엉뚱한 것 안 내기) 중 **무엇이 더 비싼지**로 선을 옮긴다.
  중복 차단은 정밀도(오차단이 치명적), 추천은 재현율 쪽이 보통이다.
- 임계값은 **설정값**이다. 코드에 상수로 박으면 조정할 때마다 배포한다(`config-and-secrets` 4-1장).
- 절대 점수보다 **상대 순위**가 안정적이다. "0.8 이상"보다 "상위 10개"가 덜 깨진다.

## 5. 성능

- 전수 비교는 후보 수의 제곱이다. **먼저 좁히고 나중에 정교하게** 한다(blocking/candidate generation).
  같은 카테고리, 같은 날짜 범위, 첫 글자 같은 값처럼 **싸고 거친 조건**으로 후보를 줄인다.
- PostgreSQL: `pg_trgm` + GIN 인덱스(`gin_trgm_ops`)로 `%` 연산자와 `similarity()`를 인덱스로 탄다.
  `LIKE '%키워드%'`는 인덱스를 못 타지만 trigram GIN 이 있으면 탄다.
- pgvector: 정확도가 필요하면 인덱스 없이 전수(작은 테이블), 규모가 커지면 HNSW.
  **인덱스는 근사다** - 재현율이 100%가 아니라는 사실을 문서에 적는다.
- 미리 계산할 수 있는 유사도(항목 x 항목)는 배치로 굳힌다. 사용자마다 다른 점수는 굳힐 수 없다.
- 정렬 키로 쓸 때의 페이징 문제는 `feed-ranking` 2장.

## 6. 임베딩을 쓸 때

- **모델과 차원을 설정으로 둔다.** 모델을 바꾸면 기존 벡터가 전부 무의미해진다 -
  재색인 계획 없이 모델을 바꾸지 않는다. 벡터 행에 **모델 이름과 버전을 같이 저장**한다.
- 코사인 유사도를 쓰려면 정규화된 벡터인지 확인한다. 거리와 유사도의 **부호 방향**을 헷갈리지 않는다
  (pgvector `<=>` 는 거리 - 작을수록 비슷하다).
- 호출 비용이 든다. 색인 시 1회, 질의 시 1회. **호출 상한을 정하고 시작한다**(`llm-integration` 4장).
- 짧은 텍스트 한 줄의 임베딩은 생각보다 노이즈가 크다. 0~1단계 신호와 **섞어 쓰는 것**이 보통 낫다.
- 임베딩은 캐시한다. 같은 텍스트를 두 번 임베딩하지 않는다.

## 7. 평가

- 골든셋(4장)을 만들면 방법을 바꿀 때마다 **같은 잣대로 비교**할 수 있다. 없으면 "더 나아 보인다"뿐이다.
- 지표: 정밀도/재현율, 상위 K개 정확도(P@K). 순위가 중요하면 MRR.
- 나쁜 예를 모은다. "이건 비슷하면 안 되는데 비슷하다고 나온 쌍"이 개선의 재료다.
- 방법을 바꾸는 PR에는 **골든셋 결과를 붙인다**. 코드만 보고는 좋아졌는지 알 수 없다.

## 8. 리뷰 체크

- [ ] "비슷하다"의 뜻이 한 문장으로 적혀 있는가
- [ ] 0~1단계(이미 있는 분류)를 검토했는가
- [ ] 색인과 질의가 같은 정규화를 쓰는가
- [ ] 한국어인데 공백 토큰화에만 기대고 있지 않은가
- [ ] 임계값이 골든셋에서 나왔는가, 설정값인가
- [ ] 후보를 먼저 좁히는가, 전수 비교인가
- [ ] 임베딩이면 모델·차원·버전이 저장되고 재색인 계획이 있는가
- [ ] 벡터 인덱스가 근사라는 사실이 문서에 있는가

## 하지 말 것

- "비슷함"을 정의하지 않고 알고리즘부터 고르기
- 0~1단계를 건너뛰고 바로 임베딩 (측정 없이 비용부터)
- 임계값을 감으로 정하고 상수로 박기
- 색인과 질의에 다른 정규화 적용
- 한국어에 공백 토큰화 + 불용어 제거만으로 끝내기
- 조사를 길이 하한 없이 잘라 내기
- 모델 교체 시 재색인 없이 기존 벡터와 섞어 쓰기
- 골든셋 없이 "좋아 보인다"로 방법 바꾸기

## 관련 스킬

`feed-ranking`(그 유사도로 목록을 정렬할 때 - 커서 페이징과 다양성),
`rag-pipeline`(검색 결과로 LLM이 답을 만들 때. 정렬만 필요하면 해당 없다),
`llm-integration`(임베딩 호출 상한), `prompt-and-eval`(골든셋 운영 방식),
`jpa-query-optimization`(인덱스를 타는지 확인), `db-schema-and-migration`(확장·인덱스 추가).
