# 트랜잭션과 동시성 (transaction-and-concurrency)

## 목적

트랜잭션 경계는 "어디까지가 하나로 성공하거나 하나로 실패해야 하는가"라는 **비즈니스 규칙**이지 기술 관례가 아니다. 그래서 이 스킬은 경계를 대신 정해주지 않고 **묻는 방법**을 정하고, 대신 판단에 필요한 개념(격리 수준, 락 선택, 경쟁 조건 패턴, 데드락, 재시도)을 한곳에 모은다.

## 언제 적용

`@Transactional` 추가/이동/제거, 여러 애그리거트나 여러 테이블을 한 흐름에서 바꿀 때, 같은 행을 두 요청이 동시에 바꿀 수 있을 때(재고·잔액·좌석·포인트·상태 전이), 배치/스케줄러가 대량 행을 갱신할 때, 락 대기·데드락·중복 생성 장애 후.

## 0. 절대 규칙 - 경계는 묻고 정한다

- 트랜잭션 경계를 **추측해서 확정하지 않는다.** 새 유스케이스에 `@Transactional`을 붙이거나, 기존 경계를 넓히거나 쪼개기 전에 아래 질문표로 확인하고 답을 받은 뒤 설계한다.
- 답을 못 받는 상황(자동 실행 등)이면 가장 좁은 경계를 잡고 **"이렇게 가정했다"를 코드 주석 한 줄과 응답에 명시**한다.
- 확정된 경계와 그 이유는 `docs/`의 해당 비즈니스 로직 문서에 한 줄 남긴다(`deliverable-write`).

### 물어볼 것 (경계 확정 질문표)

| # | 질문 | 답이 바꾸는 것 |
|---|---|---|
| 1 | 이 흐름에서 **하나라도 실패하면 전부 없던 일**이 되어야 하는 범위는 어디까지인가 | 트랜잭션 범위 |
| 2 | 부분 성공이 허용되는 단계가 있나(알림 실패해도 주문은 유지 등) | 커밋 후 처리 분리 |
| 3 | 같은 사용자가 **버튼을 두 번 누르면** 어떻게 되어야 하나 | 멱등성 키, unique 제약 |
| 4 | 두 요청이 같은 행을 동시에 바꾸면 **나중 것이 이겨도 되나, 실패해야 하나** | 낙관 락 vs 원자적 UPDATE |
| 5 | 재고/잔액처럼 **음수가 되면 안 되는 값**이 있나 | 제약 + 조건부 UPDATE |
| 6 | 이 흐름에 **외부 호출**(결제, 알림, 다른 시스템)이 있나 | 트랜잭션 밖으로 분리 |
| 7 | 실패 시 **재시도해도 안전**한가 | 재시도 정책 |
| 8 | 대상 행이 몇 건인가(수십 vs 수십만) | 단일 트랜잭션 vs 청크 |

## 1. 경계 기본값 (질문 결과가 없을 때의 출발점)

- 경계는 **애플리케이션 서비스 메서드 하나 = 유스케이스 하나**. 컨트롤러와 리포지토리에는 붙이지 않는다.
- 조회 전용은 `@Transactional(readOnly = true)`. 클래스에 readOnly, 변경 메서드에만 `@Transactional` 재선언이 기본형.
- 하나의 트랜잭션은 **애그리거트 하나 저장**을 원칙으로 한다(`ddd-spring`). 둘 이상을 한 트랜잭션에서 바꿔야 한다면 애그리거트 경계가 틀렸는지 먼저 의심한다.
- 트랜잭션 안에서는 DB 작업만. 외부 호출, 파일 IO, 메일, 이벤트 발행(동기)은 밖으로.
- `@Transactional`은 프록시 기반이라 **같은 클래스 내부 호출에는 걸리지 않는다.** 자기 주입이나 셀프 프록시로 우회하지 말고 클래스를 분리한다.
- 기본 롤백은 `RuntimeException`만. 체크 예외로 롤백하려면 `rollbackFor` 명시. 트랜잭션 안에서 예외를 잡아 삼키면 롤백이 사라진다.
- `REQUIRES_NEW`는 "실패해도 바깥은 살아야 하는 기록"(감사 로그, 실패 이력)에만. 커넥션을 2개 잡는다는 것을 알고 쓴다.

## 2. 격리 수준

- 기본값은 DB 기본(PostgreSQL/DB2 모두 `READ_COMMITTED`)을 그대로 쓴다. 격리 수준을 올려서 동시성 문제를 푸는 것은 마지막 수단이다.
- `REPEATABLE_READ` 이상은 같은 트랜잭션에서 같은 행을 두 번 읽고 그 사이 값이 변하면 안 될 때만. 락 대기와 직렬화 실패가 늘어난다.
- `SERIALIZABLE`은 실패(직렬화 충돌)를 전제로 재시도 코드를 함께 쓸 때만.
- 실무에서 동시성은 **격리 수준이 아니라 3장의 수단으로 푼다.**

## 3. 동시성 제어 수단 선택

| 수단 | 언제 | 대가 |
|---|---|---|
| **DB 원자적 UPDATE** (`UPDATE ... SET qty = qty - ? WHERE id = ? AND qty >= ?`, 영향 행 0이면 실패) | 값 하나를 증감하고 조건만 지키면 될 때. 재고, 잔액, 카운터 | 엔티티 상태와 DB가 어긋남(`clearAutomatically`), 도메인 로직 표현이 약함 |
| **낙관적 락** (`@Version`) | 충돌이 드물고, 충돌 시 사용자에게 "다시 시도"를 보여도 될 때. 일반적인 수정 화면 | 충돌 시 `OptimisticLockingFailureException` 처리·재시도 필요 |
| **비관적 락** (`PESSIMISTIC_WRITE`, `SELECT ... FOR UPDATE`) | 충돌이 잦고 실패시키면 안 될 때. 좌석/한정 수량 선점, 순번 채번 | 락 대기·데드락, 트랜잭션이 길면 처리량 급락. 타임아웃 필수 |
| **unique 제약** | "중복 생성 금지"가 본질일 때. 중복 신청, 중복 결제 | 예외를 잡아 의미 있는 응답으로 바꿔야 함 |
| **분산 락** (Redis 등) | DB 밖의 자원을 지켜야 하거나, 여러 인스턴스가 같은 배치를 도는 것을 막을 때 | 락 해제 실패·TTL 만료 시 이중 실행. **DB 행 하나 지키려고 쓰지 않는다** |

- 선택 순서: **원자적 UPDATE / unique 제약 -> 낙관적 락 -> 비관적 락 -> 분산 락.** 위에서 해결되면 아래로 내려가지 않는다.
- 비관적 락은 반드시 대기 타임아웃을 준다(`jakarta.persistence.lock.timeout`). 무한 대기 금지.

## 4. 경쟁 조건 패턴

| 상황 | 기본 해법 |
|---|---|
| 재고 차감, 포인트 차감, 잔액 출금 | 조건부 원자적 UPDATE + `ck_` 제약(음수 금지). 영향 행 0 -> 도메인 예외 |
| 좌석/한정 수량 선점 | 비관적 락 또는 "선점 행 INSERT + unique 제약" |
| 중복 신청/중복 결제 | unique 제약 + 멱등성 키(`api-design`). 잡아서 200으로 되돌릴지 409로 알릴지 질문 4 |
| 상태 전이(결제완료 -> 배송중) | `UPDATE ... WHERE status = <이전 상태>`, 영향 행 0이면 이미 전이됨 |
| 번호 채번(주문번호 등) | DB 시퀀스. 애플리케이션에서 `max + 1` 금지 |
| 배치 중복 실행 | 실행 이력 테이블 unique(작업명, 실행일) 또는 분산 락 |

## 5. 데드락 회피

- 여러 행을 갱신할 때 **항상 같은 순서로 잠근다**(예: `id` 오름차순). 순서가 어긋나면 데드락이 난다.
- 트랜잭션 안에서 잠그는 행 수와 시간을 줄인다. 락 잡은 채로 외부 호출·긴 계산 금지.
- 부모-자식을 함께 바꿀 때는 부모부터 일관되게.
- 데드락은 정상적으로 발생할 수 있는 실패다. 잡아서 짧게 재시도(8장)하거나 사용자에게 재시도를 안내한다. 증상 판별은 `rca-procedure`.

## 6. 외부 호출과 커밋 후 처리

- **트랜잭션 안에서 외부 API를 호출하지 않는다.** 외부 지연이 그대로 커넥션 점유가 되고, 외부는 성공했는데 DB가 롤백되면 되돌릴 수 없다(`external-api-client`).
- 커밋된 뒤에만 해야 하는 일(알림, 이벤트 발행, 캐시 무효화)은 `@TransactionalEventListener(phase = AFTER_COMMIT)` 또는 커밋 후 호출로 분리한다.
- `AFTER_COMMIT` 리스너 안의 DB 작업은 트랜잭션 밖이다. 필요하면 `REQUIRES_NEW`를 명시한다.
- 외부 호출이 반드시 성공해야 하는 흐름이면 "DB에 할 일 기록(같은 트랜잭션) -> 커밋 후/배치가 실제 호출" 형태로 나눈다.

## 7. 긴 트랜잭션 쪼개기

- 대량 갱신은 한 트랜잭션에 몰지 않는다. 청크(수백~수천 건) 단위로 커밋하고 **재실행해도 안전하게**(처리 표시 컬럼, 커서) 만든다.
- 사용자 입력 대기, 파일 업로드, 리포트 생성 같은 긴 작업을 트랜잭션 안에 두지 않는다.
- 조회 -> 판단 -> 저장에서 사이가 길면 낙관적 락으로 "그 사이 바뀌었는지"를 검증한다.

## 8. 재시도와 멱등성

- **재시도는 멱등한 작업에만.** 멱등하지 않으면 먼저 멱등하게 만든 뒤(멱등성 키, unique 제약, 조건부 UPDATE) 재시도를 붙인다.
- 재시도 대상은 일시적 실패만: 낙관적 락 충돌, 데드락, 직렬화 실패, 커넥션 타임아웃. 검증 실패·비즈니스 예외는 재시도하지 않는다.
- 재시도는 **트랜잭션 바깥에서** 감싼다. 트랜잭션 안에서 재시도하면 이미 롤백 표시된 트랜잭션을 다시 쓰게 된다.
- 횟수 상한(3회 내외)과 지수 백오프 + 지터. 상한 없는 재시도 금지.

## 9. 리뷰 체크

- 경계가 유스케이스 하나인가, 애그리거트 하나를 저장하는가
- 트랜잭션 안에 외부 호출·긴 작업이 없는가
- 동시에 바뀔 수 있는 값에 3장의 수단 중 하나가 걸려 있는가(없으면 "왜 필요 없는지"가 설명되는가)
- 비관적 락에 타임아웃이 있는가, 잠그는 순서가 일정한가
- 재시도가 멱등한 작업에만 붙었는가, 상한이 있는가
- `readOnly`가 조회에 붙었는가, 내부 호출로 프록시를 우회하지 않았는가

## 하지 말 것

- 경계를 물어보지 않고 `@Transactional` 범위를 임의로 넓히기
- 동시성 문제를 격리 수준 상향으로 덮기
- `synchronized`나 애플리케이션 메모리 락으로 다중 인스턴스 동시성 막기(작동하지 않는다)
- 조회 후 애플리케이션에서 계산해 덮어쓰기(`set(qty - 1)`) - 갱신 손실
- `@Transactional`을 컨트롤러/리포지토리/유틸에 붙이기
- 트랜잭션 안에서 예외를 잡고 정상 반환하기
- 락 없이 "지금까지 문제 없었다"로 넘어가기
