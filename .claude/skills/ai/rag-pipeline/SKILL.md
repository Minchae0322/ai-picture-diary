# RAG 파이프라인 (rag-pipeline)

## 목적

"우리 문서로 답하게 해줘"는 대부분 검색 문제다. LLM이 아니라 **검색이 틀려서** 답이 틀린다. 이 스킬은 파이프라인을 단계로 쪼개고 각 단계에서 무엇을 정해야 하는지, 어디서 품질이 무너지는지를 정한다.

기본 선택: **PostgreSQL + pgvector**(별도 벡터 DB를 도입하기 전 기본값 - 운영 대상이 하나 늘지 않고 권한 필터를 SQL로 건다). 문서 수십만 건과 높은 QPS가 확인되면 그때 전용 벡터 DB를 검토한다.

## 언제 적용

문서 기반 Q&A, 사내 지식 검색, 첨부 파일 요약·질의, 과거 기록을 근거로 한 추천, "답이 엉뚱한 문서를 인용한다"는 문제, 임베딩 모델 교체.

## 0. 시작 전 확인

| # | 질문 | 답이 바꾸는 것 |
|---|---|---|
| 1 | 문서가 몇 건이고 얼마나 자주 바뀌나 | 인덱싱 방식(배치 vs 실시간), 인덱스 종류 |
| 2 | 사용자마다 **볼 수 있는 문서가 다른가** | 권한 필터 설계. 나중에 붙이면 전부 다시 짬 |
| 3 | 답에 출처를 보여줘야 하나 | 청크 메타데이터 설계 |
| 4 | 문서 종류가 무엇인가(PDF, 위키, 표, 코드) | 파싱·청킹 전략 |
| 5 | 틀린 답의 비용이 얼마인가 | 근거 없을 때 "모른다"를 할지, 임계값 |
| 6 | 질문이 한국어 위주인가 | 임베딩 모델 선택, 하이브리드 검색 필요성 |

- **2번을 먼저 답하지 않고 시작하지 않는다.** 권한 필터는 스키마와 쿼리 전체에 영향을 준다.
- 문서가 수십 건이고 전부 짧다면 RAG 없이 **전체를 프롬프트에 넣는 것**이 더 정확하고 싸다. 먼저 검토한다.

## 1. 파이프라인 단계

```
수집 -> 파싱 -> 청킹 -> 임베딩 -> 저장 -> (질의) -> 검색 -> 재순위 -> 컨텍스트 조립 -> 생성 -> 출처 표시
```

각 단계는 독립 컴포넌트로 만든다. 한 메서드에 전부 넣으면 어디서 틀렸는지 알 수 없다. **단계별로 중간 결과를 로그와 테스트에서 볼 수 있어야 한다.**

## 2. 파싱과 청킹

- 청킹 전에 **파싱 품질을 먼저 본다.** PDF에서 표가 깨지거나 머리말/꼬리말이 섞이면 뒤의 모든 단계가 오염된다. 샘플 10건을 눈으로 확인한다.
- 청크는 **의미 단위**로 자른다. 우선순위: 문서 구조(제목/절) > 문단 > 문장 > 고정 길이. 고정 길이 분할은 최후 수단.
- 청크 크기는 출발점 300~800자(한국어 기준 추정), 겹침 10~20%. **실측으로 조정한다.** 작으면 문맥이 끊기고 크면 관련 없는 내용이 섞인다.
- 표와 코드 블록은 쪼개지 않는다. 통째로 한 청크.
- 각 청크에 **원문 위치 정보**를 저장한다(문서 ID, 제목, 절 제목, 페이지/오프셋, URL). 출처 표시와 디버깅의 전제다.
- 청크 앞에 문서 제목과 절 제목을 붙여 저장하면(컨텍스트 헤더) 검색 정확도가 올라간다. 임베딩 대상 텍스트와 표시용 텍스트를 분리해도 된다.

## 3. 임베딩

- 임베딩 모델을 바꾸면 **기존 벡터를 전부 다시 만들어야 한다.** 차원도 바뀐다. 모델명과 차원을 테이블에 함께 저장하고, 교체는 새 컬럼/새 테이블로 병행 운영한 뒤 전환한다(`db-schema-and-migration` 5장 expand-contract).
- 한국어 문서면 **다국어 지원 모델**인지 확인한다. 영어 전용 모델은 한국어에서 눈에 띄게 나쁘다.
- 질의와 문서를 **같은 모델로** 임베딩한다. 비대칭 모델(질의용/문서용 분리)을 쓰면 문서에 명시한다.
- 임베딩은 비용과 시간이 든다. 배치로 돌리고 재실행에 안전하게(`batch-and-scheduler` 6장). 청크 해시를 저장해 **변경되지 않은 청크는 다시 임베딩하지 않는다.**
- 임베딩 호출도 LLM 호출이다. 상한과 로그 규칙은 `llm-integration` 4장, 9장.

## 4. 저장 (pgvector)

- 테이블은 `tb_` 규칙과 공통 컬럼을 따른다(`db-schema-and-migration`). **AI는 DB에 접속하지 않는다** - SQL 파일과 `docs/db/` 문서만 만든다.
- 필수 컬럼: 문서 ID(FK), 청크 순번, 원문 텍스트, 임베딩 벡터, 임베딩 모델명, 청크 해시, 출처 메타(제목/절/페이지), **권한 필터용 컬럼**(소유자, 조직, 공개 범위).
- 차원이 2,000을 넘으면 `vector` 타입에 HNSW 인덱스를 만들 수 없다. `halfvec`으로 캐스팅해 인덱싱하거나 차원 축소를 쓴다(pgvector 0.8 기준).
- 인덱스는 HNSW 기본(검색 품질·속도 우수, 빌드가 느리고 메모리를 씀). 데이터가 자주 통째로 바뀌면 IVFFlat 검토.
- 거리 연산자와 인덱스 연산자 클래스를 **일치**시킨다. 코사인이면 `vector_cosine_ops` + `<=>`. 불일치하면 인덱스를 안 탄다.
- 권한 필터를 `WHERE`로 거는 순간 ANN 인덱스의 결과가 줄어든다. pgvector 0.8의 반복 스캔(iterative scan)을 켜거나, 필터 컬럼에 별도 인덱스를 두고 후보를 넉넉히 뽑는다.

## 5. 검색

- **권한 필터를 쿼리에 항상 건다.** "검색 후 애플리케이션에서 거르기"는 금지 - 상위 k개가 전부 볼 수 없는 문서면 결과가 빈다.
- 벡터 검색만으로는 고유명사·숫자·코드에 약하다. **하이브리드**(벡터 + 키워드/BM25)를 기본으로 검토한다. PostgreSQL이면 `tsvector`와 조합.
- 상위 k는 재순위 전 20~50, 재순위 후 3~8을 프롬프트에 넣는다(출발점, 실측 조정).
- **유사도 임계값을 둔다.** 임계값 미만이면 "관련 문서 없음"으로 처리하고 LLM을 호출하지 않는다. 이게 환각의 가장 큰 방어선이다.
- 같은 문서에서 여러 청크가 올라오면 병합하거나 문서당 최대 개수를 제한한다. 한 문서가 컨텍스트를 독점하지 않게.
- 질의 확장(동의어, 오타 교정, 질문 재작성)은 검색이 안 될 때 추가한다. 처음부터 넣지 않는다.

## 6. 재순위

- 검색 상위 k를 리랭커(cross-encoder) 또는 LLM으로 다시 정렬한다. 벡터 검색의 정밀도를 가장 크게 올리는 단계지만 **지연과 비용이 붙는다.**
- 먼저 재순위 **없이** 품질을 측정한다. 부족할 때 넣는다.
- LLM 재순위는 후보 텍스트를 전부 보내므로 토큰이 많다. 후보 수와 각 후보 길이에 상한을 둔다.

## 7. 컨텍스트 조립과 생성

- 컨텍스트 전체 길이에 상한을 둔다. 상한을 넘으면 뒤를 자르지 말고 **청크 수를 줄인다.**
- 각 청크를 **구분자와 번호**로 감싸고 출처 ID를 붙인다. 프롬프트에서 "근거 번호를 인용하라"고 지시한다.
- 검색 결과는 **외부 입력**이다. 문서 안의 문장이 지시로 해석되지 않게 방어한다(`llm-integration` 7장). 사용자가 업로드한 문서면 특히.
- 프롬프트에 명시한다: **컨텍스트에 없으면 "자료에 없습니다"라고 답하고 지어내지 않는다.**
- 컨텍스트가 비었으면 LLM을 호출하지 않고 바로 "관련 자료 없음" 화면으로.

## 8. 출처 표시

- 답변에 **어느 문서의 어느 부분**인지 표시한다. 문서 제목만으로는 검증이 안 된다. 절 제목이나 페이지까지.
- 인용 번호와 실제 청크를 매핑해 화면에서 원문을 펼쳐 볼 수 있게 한다.
- LLM이 인용한 번호가 실제 컨텍스트에 있는 번호인지 **서버에서 검증**한다. 없는 번호를 인용하면 그 부분을 제거하거나 실패 처리.
- "AI가 생성한 답변" 라벨과 함께 표시한다(`llm-integration` 8장).

## 9. 평가

- 검색과 생성을 **따로 평가한다.** 답이 틀렸을 때 검색이 문제인지 생성이 문제인지 구분되어야 고칠 수 있다.
- 검색 지표: 정답 문서가 상위 k에 있는가(recall@k), 상위 몇 번째인가(MRR). 질문-정답문서 쌍 20~30건이면 시작할 수 있다.
- 생성 지표: 근거 없는 주장이 없는가, 인용이 실제 근거와 맞는가, 답이 질문에 답하는가.
- 평가 셋 구성·회귀 절차는 `prompt-and-eval`을 따른다. 청킹/임베딩/k값을 바꿀 때마다 돌린다.

## 10. 리뷰 체크

- 권한 필터가 SQL `WHERE`에 있는가(애플리케이션 필터링이 아닌가)
- 청크에 출처 메타가 있는가, 임베딩 모델명과 차원이 저장되는가
- 유사도 임계값과 "자료 없음" 경로가 있는가
- 컨텍스트 길이 상한과 문서당 청크 수 제한이 있는가
- 검색된 문서의 텍스트를 지시로 해석하지 않게 방어했는가
- 인용 번호를 서버가 검증하는가
- 인덱스 연산자 클래스와 거리 연산자가 일치하는가
- 재임베딩 없이 모델을 바꾸려 하지 않았는가

## 하지 말 것

- 권한 필터를 검색 후 애플리케이션에서 적용
- 고정 길이로만 청킹, 표/코드 쪼개기
- 출처 메타 없이 텍스트만 저장
- 유사도 임계값 없이 항상 LLM 호출
- 검색 결과를 신뢰된 지시로 취급
- 임베딩 모델 교체 후 기존 벡터 방치
- 검색/생성을 한 지표로 뭉뚱그려 평가
- 문서 수십 건인데 RAG부터 만들기

## 관련 스킬

`llm-integration`(호출 구조, 인젝션 방어, 상한), `prompt-and-eval`(평가 셋과 회귀), `db-schema-and-migration`(테이블/인덱스, DB 실행 금지), `jpa-query-optimization`(검색 쿼리 실행계획), `batch-and-scheduler`(인덱싱 배치), `file-upload-storage`(업로드 문서가 원본일 때), `api-design`(검색 API와 에러 코드).
