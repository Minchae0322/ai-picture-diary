# 알림 발송 (notification)

## 목적

알림은 **되돌릴 수 없고, 잘못 보내면 법적 문제가 되고, 한 번 실수로 수만 건이 나간다.** 이 스킬은 채널을 고르는 기준, 수신 동의와 광고성 정보 규칙, 그리고 "요청 -> 저장 -> 발송 -> 결과"로 나누는 파이프라인을 정한다.

## 언제 적용

푸시/이메일/SMS/알림톡 발송 추가, 알림 설정 화면, 디바이스 토큰 처리, 마케팅 발송, "알림이 안 온다"·"두 번 왔다"·"동의 안 했는데 왔다" 문제, 발송 실패율 대응.

## 이 스킬 폴더의 파일

| 파일 | 용도 | 복사 위치 |
|---|---|---|
| `templates/notification-schema.sql` | 발송 요청·이력·수신 동의·디바이스 토큰 테이블 | `sql/patch/` |
| `templates/notification-types.md` | 알림 종류 정의서(종류별 채널·템플릿·동의 필요 여부) | `docs/notification/` |

## 0. 절대 규칙 - 광고성 정보

한국에서 영리 목적 광고성 정보에는 정보통신망법이 적용된다. **개발자가 아니라 법이 정한 요건**이므로 협의 대상이 아니다.

- **사전 수신 동의 없이 광고성 정보를 보내지 않는다.** (거래 관계 예외: 거래 종료 후 6개월 내 동일·유사 상품)
- 오후 9시~오전 8시 전송은 **별도의 사전 동의**가 필요하다(전자우편 제외).
- 제목/본문 시작에 **"(광고)" 표기**, 전송자 명칭과 연락처, **수신거부 방법**을 명시한다. 회피를 위한 변형 표기는 위반.
- 수신 동의 후 **매 2년마다** 동의 여부를 확인하고 안내한다.
- 위반 시 3천만원 이하 과태료. (2026-09 확인, 아래 reference에 출처)
- **정보성과 광고성을 코드 레벨에서 구분한다.** 주문/배송/인증 알림은 정보성, 일방적 쿠폰·등급 안내·재입고 알림은 광고성이다. 애매하면 광고성으로 취급한다.

## 1. 채널 선택

| 채널 | 도달 | 비용 | 언제 |
|---|---|---|---|
| 앱 푸시(FCM/APNs) | 앱 설치 + 권한 허용자만 | 무료 | 즉시성 있는 앱 내 사건 |
| 인앱 알림(알림함) | 앱 열었을 때 | 없음 | 푸시와 **항상 함께**. 푸시를 놓쳐도 남는다 |
| 이메일 | 높음 | 낮음 | 긴 내용, 영수증, 기록이 남아야 하는 것 |
| SMS/LMS | 매우 높음 | 건당 과금 | 인증번호, 긴급 |
| 카카오 알림톡 | 높음(카카오 사용자) | 건당 과금, SMS보다 저렴 | 정보성 알림. 템플릿 사전 승인 필요 |

- **푸시는 반드시 인앱 알림과 함께 저장한다.** 푸시는 권한 거부·기기 변경·OS 제한으로 흔히 유실된다. 푸시만 보내면 사용자는 영영 모른다.
- 알림톡은 **템플릿을 사전 승인**받아야 하고 광고성 문구를 넣을 수 없다. 실패 시 SMS 대체발송 정책을 정한다. 인증번호는 SMS가 기본.
- 채널을 늘리기 전에 인앱 알림함부터 만든다. 가장 싸고 문제가 적다.

## 2. 알림 종류 정의

- **알림 종류를 열거형으로 정의**하고 종류마다 채널·템플릿·동의 필요 여부·정보성/광고성을 한 곳에 적는다(`templates/notification-types.md`).
- 종류를 추가하면 그 문서를 같은 PR에서 갱신한다. 이게 없으면 "이 알림 왜 오는지" 아무도 모른다.
- 사용자 설정은 **종류별 on/off**로. 전체 on/off만 있으면 하나가 싫어서 전부 끈다.
- 종류별 기본값(기본 on인지 off인지)을 명시한다. 광고성은 항상 기본 off.

## 3. 템플릿

- 문구를 코드에 하드코딩하지 않는다. 템플릿 파일 또는 DB에 두고 **변수 치환**으로.
- 템플릿마다 필요한 변수를 명시하고, 누락 시 발송 전에 실패시킨다. `{userName}`이 그대로 나가는 사고가 가장 흔하다.
- 알림톡은 카카오 승인 템플릿과 코드의 문구가 **글자 하나까지 같아야** 한다. 임의로 바꾸면 발송 실패한다.
- 다국어는 템플릿에 로케일 축을 둔다. 푸시 제목·본문은 잘릴 것을 전제로 **앞부분에 핵심**을 둔다.

## 4. 발송 파이프라인

```
요청(도메인 이벤트) -> 발송 요청 저장(PENDING) -> [커밋 후] 발송 -> 결과 기록(SENT/FAILED) -> (실패 시) 재시도
```

- **트랜잭션 안에서 발송하지 않는다.** 발송 요청만 같은 트랜잭션에 저장하고, 실제 발송은 커밋 후(`@TransactionalEventListener(AFTER_COMMIT)`) 또는 배치가 한다(`transaction-and-concurrency` 6장).
- 발송 요청을 **DB에 남긴다.** 이력이 없으면 "안 왔다"는 문의에 답할 수 없고 재발송도 못 한다.
- 대량 발송은 배치로. 한 번에 수만 건을 동기 호출하지 않는다(`batch-and-scheduler`).
- 발송 직전에 **수신 동의와 알림 설정을 다시 확인**한다. 요청 저장 시점과 발송 시점 사이에 사용자가 껐을 수 있다.
- 채널별 발송은 `external-api-client` 규칙을 따른다(타임아웃, 재시도, 실패 격리).

## 5. 중복 발송 방지

- **같은 사건에 대해 한 번만** 보낸다. `(알림종류, 대상사용자, 사건키)`에 unique 제약을 건다. 사건키는 주문 ID, 게시글 ID 등.
- 재시도가 중복을 만든다. 발송 성공 여부를 확실히 기록하고, 타임아웃처럼 애매하면 재시도 전에 상태를 조회한다. 배치 중복 실행 방지는 `batch-and-scheduler` 3장.
- 대량 발송 전에 **대상 수를 확인하는 단계**를 넣는다. 조건 실수로 전체 사용자에게 나가는 사고를 막는 마지막 방어선이다.
- 운영 환경이 아닌 곳에서 실제 발송이 나가지 않게 한다. dev는 발송 어댑터를 로그 출력으로 대체하거나 허용 목록(내부 계정)만.

## 6. 디바이스 토큰

- 토큰은 **바뀐다.** 앱 시작 시마다 서버에 등록/갱신한다. 한 사용자가 여러 기기를 가지므로 `(userId, token)`은 다대일.
- 발송 실패 응답에 "등록되지 않은 토큰"이 오면 **즉시 비활성화**한다. 방치하면 실패율이 계속 오르고 비용이 든다.
- 로그아웃 시 토큰을 삭제한다. 안 하면 다음 사용자에게 이전 사용자의 알림이 간다. 오래 안 쓴 토큰은 정리 배치로.
- FCM은 레거시 API가 종료되었으므로 **HTTP v1**을 쓴다. 서버 키가 아니라 서비스 계정 자격증명 기반이다(`config-and-secrets`).

## 7. 실패와 재시도

- 채널별 실패를 분류한다: **영구 실패**(잘못된 토큰, 수신 거부, 존재하지 않는 주소)는 재시도하지 않고 비활성화. **일시 실패**(5xx, 타임아웃, rate limit)만 재시도.
- 재시도는 상한과 지수 백오프. 실패 건은 `tb_notification` 상태로 남기고 재처리 배치가 처리한다.
- 실패율을 채널별로 모니터링한다. 갑자기 오르면 자격증명 만료나 정책 변경이다. 알림톡 실패 시 SMS 대체발송 여부는 종류별로 정한다(비용이 든다).

## 8. 로그와 개인정보

- 발송 로그에 **수신자 연락처 원문과 치환된 개인정보를 남기지 않는다.** 사용자 ID와 마스킹된 값만(`logging-observability`).
- 남길 것: `event=notification.<종류>.<채널>.sent/failed`, 알림 종류, 채널, 사용자 ID, 템플릿 ID, 결과 코드, traceId.
- 발송 이력 테이블의 보관 기간을 정하고 정리 배치를 만든다. 무한 증가한다.

## 9. 리뷰 체크

- 광고성 알림에 사전 동의 확인, (광고) 표기, 수신거부 안내, 야간 별도 동의가 있는가
- 정보성/광고성이 알림 종류에 명시돼 있는가
- 트랜잭션 안에서 발송하지 않는가, 발송 이력이 저장되는가
- 발송 직전 수신 동의·설정을 재확인하는가
- 중복 방지 unique 제약이 있는가
- 푸시와 함께 인앱 알림이 저장되는가
- 영구 실패 토큰을 비활성화하는가, 로그아웃 시 토큰을 지우는가
- 대량 발송에 대상 수 확인 단계가 있는가
- 비운영 환경에서 실제 발송이 나가는가

## 하지 말 것

- 동의 없이 광고성 알림 발송, (광고) 표기 누락
- 야간 광고 발송을 별도 동의 없이
- 트랜잭션 안에서 발송 API 호출
- 발송 이력 없이 발송
- 푸시만 보내고 인앱 알림 미저장
- 문구 하드코딩, 변수 누락 검증 없음
- 영구 실패 토큰 방치, 로그아웃 시 토큰 유지
- 대상 수 확인 없이 대량 발송
- 연락처·개인정보를 로그에 원문으로
- 비운영 환경에서 실제 사용자에게 발송

## 관련 스킬

`external-api-client`(FCM/알림톡/메일 API 호출 규칙), `batch-and-scheduler`(대량 발송·재처리·토큰 정리 배치), `transaction-and-concurrency`(커밋 후 발송), `db-schema-and-migration`(이력·동의 테이블), `config-and-secrets`(FCM 서비스 계정, APNs 키), `logging-observability`(발송 로그), `app-store-release`(푸시 권한 고지와 APNs 키 설정), `api-design`(알림 설정 API).
