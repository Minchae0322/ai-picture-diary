# 배치와 스케줄러 (batch-and-scheduler)

## 목적

배치는 아무도 안 볼 때 돌고, 실패해도 조용하고, 인스턴스가 2대가 되는 순간 두 번 돈다. 도구 선택 기준을 정하고, 스케줄과 on/off를 환경변수로 빼고, 중복 실행·부분 실패·재실행을 기본 설계에 넣고, 배치 목록을 문서로 남긴다.

## 언제 적용

`@Scheduled` 추가/변경, Spring Batch Job/Step 작성, 대량 데이터 마이그레이션·정산·집계·정리(purge) 작업, 배치 실패 후 재처리, 인스턴스를 2대 이상으로 늘릴 때.

## 이 스킬 폴더의 파일

| 파일 | 용도 | 복사 위치 |
|---|---|---|
| `templates/배치-목록.md` | 배치 인벤토리(이름, 주기, 대상, 실패 시 영향, 재실행 방법) | `docs/batch/` |
| `templates/batch-run.md` | 대량 처리 1회성 작업 실행 계획서(마이그레이션 등) | `docs/batch/` |
| `templates/shedlock.sql` | ShedLock 락 테이블 DDL | `sql/patch/` |

## 0. 새 배치 전에 확인할 것

| # | 질문 | 답이 바꾸는 것 |
|---|---|---|
| 1 | 대상 건수는 지금 몇 건이고 1년 뒤 몇 건인가 | `@Scheduled` vs Spring Batch, 청크 크기 |
| 2 | 실패하면 **다시 돌려도 되나**, 아니면 중복이 생기나 | 멱등 설계, 진행 상태 컬럼 |
| 3 | 일부만 실패하면 전체 중단인가, 건너뛰고 계속인가 | skip 정책, 실패 건 격리 |
| 4 | 언제까지 끝나야 하나(다음 실행 전? 업무 시작 전?) | 병렬화 여부, 타임아웃 |
| 5 | 인스턴스가 몇 대인가(지금/앞으로) | 중복 실행 방지 필요 여부 |
| 6 | 실패를 누가 어떻게 아는가 | 알림, 메트릭 |

답이 없으면 가장 안전한 쪽(멱등 + 건너뛰지 않음 + 단일 실행 보장)으로 만들고 가정을 명시한다.

## 1. `@Scheduled` vs Spring Batch

| 조건 | 선택 |
|---|---|
| 수천 건 이하, 단순 루프, 실패 시 다음 주기에 다시 하면 됨 | `@Scheduled` + 서비스 메서드 |
| 재시작 지점(어디까지 했는지) 복원이 필요 | Spring Batch |
| 건별 skip/retry 정책, 실패 건 집계가 필요 | Spring Batch |
| 여러 스텝의 순서·조건 분기가 있다 | Spring Batch |
| 파일 읽기/쓰기, 대량 I/O가 중심 | Spring Batch |
| 실행 이력과 파라미터를 남겨야 한다 | Spring Batch |

- 애매하면 `@Scheduled`로 시작한다. Spring Batch는 메타 테이블·설정 비용이 있어 필요할 때 올린다.
- **트리거와 로직을 분리한다.** `@Scheduled` 메서드는 호출만, 로직은 별도 서비스에. 수동 실행과 테스트가 가능해진다.
- 1회성 대량 작업(마이그레이션)은 스케줄러에 넣지 않는다. 수동 진입점 + 실행 계획서(`templates/batch-run.md`).

## 2. 스케줄 정의

- **cron을 하드코딩하지 않는다.** `@Scheduled(cron = "${app.batch.<이름>.cron}", zone = "Asia/Seoul")`로 주입하고 타임존을 명시한다(`config-and-secrets`). 서버 TZ에 의존 금지.
- 배치마다 **on/off 스위치**: `@ConditionalOnProperty("app.batch.<이름>.enabled")` 또는 cron 값 `-`(실행 안 함). 장애 시 배포 없이 끌 수 있어야 한다.
- `fixedDelay`(끝난 뒤 N)와 `fixedRate`(시작 기준 N)를 구분한다. 작업 시간이 들쭉날쭉하면 `fixedDelay`.
- 스케줄러 스레드 풀 기본값은 1이다. 하나가 밀리면 전부 밀리므로 `spring.task.scheduling.pool.size`를 배치 수에 맞춘다.
- 자정·정시에 몰지 않는다. 배치끼리, 트래픽 피크와도 겹치지 않게 분산한다. 로컬/개발 프로파일은 기본 off.

## 3. 다중 인스턴스 중복 실행 방지

- **인스턴스가 2대 이상이 될 가능성이 있으면 처음부터 건다.** "지금은 1대"는 근거가 아니다.
- 기본 수단은 **ShedLock**(DB 락 테이블). `@SchedulerLock(name, lockAtMostFor, lockAtLeastFor)`. `name`은 배치마다 고유하고 바꾸지 않는다.
- `lockAtMostFor`는 **최대 실행 시간보다 넉넉히**. 짧으면 실행 중 락이 풀려 두 번 돈다. `lockAtLeastFor`는 매우 빨리 끝나는 작업의 시계 오차 중복을 막는다.
- ShedLock은 락을 못 잡으면 **대기하지 않고 건너뛴다.** 이 동작이 맞는지 확인한다.
- 대안: 실행 이력 테이블에 `unique(job_name, run_date)` INSERT로 선점. 단순하고 이력이 함께 남는다.
- `synchronized`나 메모리 플래그는 다중 인스턴스에서 무의미하다(`transaction-and-concurrency`).

## 4. 청크와 트랜잭션 크기

- 전체를 한 트랜잭션에 넣지 않는다. 청크 단위로 커밋한다. 출발점 500~1,000건, 이후 실측으로 조정(근거가 아니라 출발점이다).
- 커서/키 기반으로 읽는다. `OFFSET`이 커지면 뒤로 갈수록 느려진다(`jpa-query-optimization`).
- JPA 대량 쓰기는 청크마다 `flush`/`clear`. 안 하면 영속성 컨텍스트가 계속 커진다.
- **읽는 조건이 처리하면 거짓이 되게** 만든다(`status = PENDING` -> `DONE`). 그러면 중단 후 재실행이 자연히 이어진다.
- 트랜잭션 안에서 외부 API를 호출하지 않는다(`external-api-client`).

## 5. 실패 격리와 재처리

- 건별 실패가 전체를 중단시켜야 하는지 먼저 정한다(질문 3). 대부분의 집계·발송 배치는 **건너뛰고 계속**이 맞다.
- 건너뛴 건은 반드시 **어딘가에 남긴다.** 실패 이력 테이블(대상 ID, 사유, 발생 시각, 재시도 횟수) 또는 상태 컬럼 `FAILED`.
- 재처리 방법을 만들 때 함께 만든다. "나중에 수동으로"는 안 만든 것이다. 진입점과 대상 조건을 배치 목록 문서에 적는다.
- 임계치(연속 실패 N건, 실패율 X% 초과)를 넘으면 중단한다. 전부 실패하는 배치가 끝까지 도는 것은 무의미하다.
- 재시도는 일시적 실패에만, 상한과 백오프를 두고(`transaction-and-concurrency` 8장).

## 6. 진행 상태와 재실행 안전성

- 모든 배치는 **중간에 죽어도 다시 돌리면 이어지거나 안전하게 다시 하도록** 만든다.
- 대상 행에 상태/처리 시각 컬럼을, 별도로 실행 이력 테이블(작업명, 시작/종료, 대상·성공·실패 건수, 상태)을 남긴다.
- 실행 파라미터(대상 일자 등)를 받게 만든다. 어제 실패분을 다시 못 돌리면 운영이 막힌다. 기준 시각은 "과거 N시간"보다 명시적 값이 재실행에 강하다.

## 7. 병렬 처리

- **먼저 단일 스레드로 측정한다.** 병목이 DB인지 애플리케이션인지 모른 채 스레드를 늘리면 DB만 더 아프다.
- 순서: 쿼리/인덱스 개선 -> 배치 크기(JDBC batch insert, `hibernate.jdbc.batch_size`) -> 병렬화. 앞에서 풀리면 뒤로 가지 않는다.
- 전제: 작업 단위가 **서로 독립**이고 같은 행을 건드리지 않아야 한다. 겹치면 데드락이 난다(잠그는 순서 통일).
- 분할은 겹치지 않게(ID 범위, 해시 나머지, 날짜) 하고 각 워커 쿼리에 그 조건을 넣는다. 실패 시 어느 범위였는지 기록한다.
- 스레드 수는 DB 커넥션 풀 크기를 넘지 않게. 커넥션 대기가 병목이면 스레드를 늘려도 느려진다.
- 진행률과 워커별 처리 건수를 로그로 남긴다.

## 8. 로그와 메트릭

- 배치 시작/종료마다 남긴다: `event=batch.<이름>.started` / `.finished`, 실행 ID, 파라미터, 대상 건수, 성공/실패/스킵 건수, 소요 시간. 형식은 `logging-observability`.
- 건별 로그는 실패한 건만. 성공 건을 전부 남기면 로그가 폭발한다. 진행률은 N건마다 한 줄.
- 메트릭: 마지막 성공 시각, 소요 시간, 실패 건수. **"돌지 않은 것"을 감지하는 알람**이 실패 알람보다 중요하다. 알림 채널을 정하고 로그에만 남기지 않는다.

## 9. 배치 목록 문서

- 배치를 추가·변경하면 `docs/batch/배치-목록.md`를 같은 PR에서 갱신한다(`templates/배치-목록.md`).
- 각 배치마다: 이름, 트리거(cron/수동), 프로퍼티 키, 대상과 조건, 예상 건수/소요 시간, 실패 시 업무 영향, 재실행 방법, 담당.
- 1회성 대량 작업은 실행 전에 `templates/batch-run.md`로 계획서를 쓴다. DB를 바꾸면 `db-schema-and-migration`의 SQL/문서 규칙과 **AI는 실행하지 않는다**는 규칙을 함께 지킨다.

## 10. 리뷰 체크

- cron·enabled가 프로퍼티로 빠지고 타임존이 명시됐는가
- 중복 실행이 막혔는가, `lockAtMostFor`가 최대 실행 시간보다 긴가
- 청크마다 커밋하는가, 중간에 죽었다 다시 돌려도 안전한가
- 실패 건이 기록되고 재처리 방법이 있는가
- 시작/종료 로그와 건수가 남는가, 안 돌았을 때 알 수 있는가, 배치 목록 문서가 갱신됐는가

## 하지 말 것

- cron 하드코딩, off 스위치 없음, 타임존 미지정
- "지금 1대라서" 중복 실행 방지 생략, 스케줄러 스레드 풀 1로 배치 여러 개 돌리기
- 전체를 한 트랜잭션으로, 트랜잭션 안에서 외부 API 호출
- 실패 건을 로그에만 남기고 넘어가기, 성공 건까지 건별 로깅
- 측정 없이 스레드부터 늘리기
- 배치 추가하고 목록 문서 안 고치기

## 관련 스킬

`transaction-and-concurrency`(트랜잭션 크기, 락, 재시도, 멱등), `db-schema-and-migration`(상태 컬럼, 백필 SQL, DB 실행 금지), `jpa-query-optimization`(커서 조회, 배치 insert, N+1), `logging-observability`(배치 로그/메트릭), `config-and-secrets`(cron·enabled 프로퍼티), `external-api-client`(배치가 외부를 호출할 때), `notification`(대량 발송·재처리 배치), `file-upload-storage`(고아 파일 정리 배치), `rag-pipeline`(임베딩 인덱싱 배치), `deliverable-write`(`docs/batch/` 문서), `test-writing-guide`(경계값: 0건, 1건, 청크 경계, 마지막 청크).
