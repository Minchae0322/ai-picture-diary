# deliverable-structure - 참고 자료

`SKILL.md`의 규칙에 대한 이유, 전체 예시 트리, 상세 설명을 담는다. SKILL.md와 함께 읽는다.

---

## 목적 (왜 표준이 필요한가)

프로젝트마다 `docs/`가 제각각이면 스킬도 사람도 어디에 뭘 둘지 매번 고민한다. 이 문서는 **모든 프로젝트에 같은 모양으로 적용하는 `docs/` 표준**이다. `deliverable-sync`와 `deliverable-write`는 이 구조를 전제로 동작하고, 새 프로젝트는 이 구조로 시작한다.

기본 규칙 하나: **파일을 놓을 자리는 "무엇에 대한 문서인가"(도메인)와 "언제까지 유효한가"(현행/이력)로 결정한다.** 이 두 질문에 답하면 자리는 정해진다.

---

## 표준 구조 (예시 파일 포함 전체 트리)

```
<repo>/
├── README.md                          # 프로젝트 소개, 실행 방법. 짧게. 상세는 docs/로 링크
├── CHANGELOG.md                       # Keep a Changelog. 코드 변경 기록 (날짜 역순)
├── CLAUDE.md                          # 에이전트 지침 (빌드 명령, 컨벤션, 금지 사항). 산출물 아님
└── docs/
    ├── INDEX.md                       # 현행 문서 <-> 코드 경로 매핑 (deliverable-sync가 읽음)
    ├── BOARD.md                       # 동기화 상태, 미분류, 할 일 (deliverable-sync가 씀)
    ├── README.md                      # docs/ 안내: 이 구조 설명 + 도메인 폴더 목록
    ├── _templates/
    │   ├── 현행문서.md                  # 비즈니스 로직 현행 문서 템플릿
    │   ├── 이력문서.md                  # 날짜 문서 템플릿 (문제/원인/해결/결과)
    │   ├── api-명세.md                  # 프론트/외부 전달용 API 명세 템플릿
    │   └── adr.md                      # 결정 기록 템플릿
    │
    ├── guide/                         # 프로젝트 전반 가이드 (도메인 무관, 현행)
    │   ├── 개발-가이드.md               # 커밋 규칙, CHANGELOG 규칙, 코드 리뷰 체크리스트
    │   ├── 환경-설정-가이드.md
    │   ├── 빌드-가이드.md
    │   ├── 배포-가이드.md
    │   ├── 브랜치-전략.md
    │   └── 디렉터리-아키텍처.md
    │
    ├── domain/                        # 도메인별 산출물. 하위 폴더명 = 코드 도메인 패키지명
    │   ├── article/
    │   │   ├── README.md              # 도메인 한 단락 + 이 폴더의 문서 목록
    │   │   ├── 기사-비즈니스로직.md      # 현행 문서 (날짜 없음, 코드 따라 갱신)
    │   │   ├── 편집잠금-비즈니스로직.md  # 현행 문서 (로직 묶음이 여럿이면 여럿)
    │   │   ├── 2026-01-31-DB2-LIKE-쿼리-성능-개선.md          # 이력 문서
    │   │   └── 2026-05-14-편집잠금-하트비트-자동해제-기획안.md  # 이력 문서
    │   ├── cuesheet/
    │   └── auth/
    │
    ├── api/                           # 외부/프론트에 전달한 API 명세 (이력. 전달 시점 고정)
    │   ├── 2026-07-24-영상정보-게시판-개선-API-명세.md
    │   └── 2026-09-02-연합-긴급-머리말-관리-API-명세.md
    │
    ├── adr/                           # 아키텍처/설계 결정 기록 (이력. 번호 또는 날짜)
    │   └── 2026-03-30-토큰-부서정보-DB-조회-전환.md
    │
    ├── incident/                      # 장애 분석 보고서 (이력). backend/rca-procedure.md 형식
    │   └── 2026-07-20-공용기사-잠금-미해제-장애분석.md
    │
    ├── release-notes/                 # 배포 단위 기록 (이력)
    │   ├── INDEX.md
    │   └── v1.0.106.md
    │
    ├── ops/                           # 운영 문서 (현행). 배치 목록, 로그 정의, 큐 정리, 모니터링
    │   ├── 배치-목록.md
    │   ├── 로그-정의서.md
    │   └── rabbitmq-큐-정리-가이드.md
    │
    ├── erd/                           # 스키마 (현행). dbml, 논리명 정리
    │
    ├── handoff/                       # 인수인계, 타 팀 전달 프롬프트/커버노트 (이력)
    │   └── 2026-07-31-비상시스템-백엔드-핸드오프.md
    │
    └── assets/                        # 이미지, drawio, pdf 등 첨부. 문서와 같은 이름 접두어
        └── 편집의뢰-알림-흐름.drawio
```

## 어디에 둘지 결정하는 질문 (원문)

1. **특정 도메인의 로직에 대한 것인가?** 예 -> `domain/<도메인>/`. 아니오 -> 2번.
2. **지금 어떻게 동작하는지(현행)인가, 그 시점 기록(이력)인가?**
   - 도메인 현행 -> `domain/<도메인>/<로직>-비즈니스로직.md`
   - 도메인 이력 -> `domain/<도메인>/YYYY-MM-DD-<제목>.md`
3. 도메인 무관이면 종류로:
   - 개발자가 따를 규칙/절차 -> `guide/`
   - 외부에 전달한 API -> `api/`
   - 왜 이렇게 결정했는가 -> `adr/`
   - 장애 -> `incident/`
   - 배포 -> `release-notes/`
   - 운영 중 참조하는 목록/정의 -> `ops/`
   - 남에게 넘기는 묶음 -> `handoff/`
4. 여러 도메인에 걸친 로직(인증, 알림, 공통 응답)은 `domain/common/` 또는 해당 기능 이름의 도메인 폴더(`domain/auth/`). `common`은 최후 수단.

## 파일명 규칙 (이유)

- 이력 문서에 `YYYY-MM-DD-` 접두어를 붙이면 정렬하면 시간순이 된다.
- 도메인 폴더명은 코드 패키지명과 철자·대소문자까지 동일. `requestVideo`면 `requestVideo`. kebab으로 바꾸지 않는다.
- 공백, 괄호, `(1)` 같은 복사본 표시 금지. 첨부 파일도 같다.
- 한 문서에 딸린 첨부는 `assets/<문서명>-<용도>.<ext>`.

## 문서 상단 메타 (현행 문서만, 예시)

```markdown
# <제목>

> 도메인: `app/<패키지>` · 엔티티 `<Entity>`(테이블 `<table>`)
> 코드: <INDEX.md와 같은 글롭> · 기준 커밋: <hash> · 갱신: YYYY-MM-DD
```

- 프론트매터 대신 인용 블록. 기존 문서와 모양이 같고 어떤 뷰어에서도 보인다.
- 이력 문서는 메타 없이 제목 아래 한 줄로 날짜와 작성 맥락만: `> 2026-07-20 · 장애 분석 · 관련 커밋 abc1234`.

## 기존 프로젝트에 적용할 때 (보충)

기존 `docs/`가 평평하게 섞여 있을 때 한 번에 갈아엎지 않는다.

- 1단계에서 `INDEX.md`, `BOARD.md`, `_templates/`, `README.md`를 먼저 만드는 이유: 파일 이동 없이도 sync/write가 돌아갈 수 있어야 한다.
- 2단계: 도메인 폴더가 이미 `docs/<도메인>/`으로 있으면 `docs/domain/<도메인>/`으로 옮길지 결정한다. 링크가 많이 걸려 있으면 **옮기지 않고** `domain/` 계층을 생략한 변형으로 간다("변형 허용").
- 3단계: 루트에 흩어진 가이드(`빌드-가이드.md`, `배포-가이드.md`...)를 `guide/`로 `git mv`. 다른 문서의 링크를 같이 고친다(`grep -rl "빌드-가이드" docs/`).
- 7단계: 각 단계를 별도 커밋. 한 커밋에 다 넣으면 리뷰가 불가능하다.

## 변형 허용 (조건 상세)

표준에서 벗어나도 되는 경우와 조건:

- **`domain/` 계층 생략**: 기존에 `docs/<도메인>/`이 자리 잡은 프로젝트. 대신 `docs/README.md`에 "도메인 폴더는 루트 직속"이라고 명시하고, INDEX.md 경로도 그에 맞춘다. sync/write는 INDEX.md의 경로를 따르므로 동작에 문제없다.
- **소규모 프로젝트**(도메인 3개 이하, 토이): `guide/`, `ops/`, `handoff/`를 만들지 않고 `domain/`과 `adr/`만. 필요해질 때 추가.
- **프론트엔드 프로젝트**: `domain/` 대신 `pages/` 또는 `features/`(라우트/기능 단위). 현행 문서는 `<페이지>-동작.md`. 나머지 폴더는 동일.
- **모노레포**: 각 서비스 루트에 이 구조를 통째로. 루트 `docs/`에는 서비스 목록과 공통 ADR만.

## 부트스트랩 체크리스트 (보충)

- `docs/guide/개발-가이드.md`에는 커밋 규칙, CHANGELOG 규칙, 문서 파일명 규칙(이 문서 요약)을 넣는다.

---

## 하지 말 것 (원문)

- 도메인 폴더와 종류 폴더를 섞는 것(`docs/article-api/`, `docs/api-article/`). 도메인은 `domain/` 아래, 종류는 루트 아래.
- 현행 문서에 날짜를 붙이거나, 이력 문서에서 날짜를 빼는 것.
- 도메인 폴더명을 패키지명과 다르게 짓는 것.
- 루트 `docs/`에 파일을 바로 두는 것(README, INDEX, BOARD 제외).
- 로그 파일, 덤프, 대용량 바이너리를 `docs/`에 두는 것. `.gitignore`에 `docs/**/*.log`.
- 한 번에 전부 옮기는 대규모 정리 커밋.
