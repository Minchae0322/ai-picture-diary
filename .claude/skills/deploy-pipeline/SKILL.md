# 배포 파이프라인 (deploy-pipeline)

## 목적

`harness`가 **내 컴퓨터에서** 규칙을 지키게 한다면, 이 스킬은 **머지 이후**를 다룬다: 무엇을 검증하고, 어떻게 이미지를 만들고, 어느 순서로 어디에 올리고, 잘못됐을 때 어떻게 되돌리는가.

기준: **GitHub Actions + Docker**. 배포 대상(K8s, ECS, 단일 서버 등)은 프로젝트마다 다르므로 배포 단계만 갈아끼운다.

## 언제 적용

CI/CD 최초 구성, 워크플로 수정, Dockerfile 작성·최적화, 환경 추가, 시크릿 주입 방식 변경, 배포 실패·롤백, "로컬은 되는데 CI는 안 된다".

## 이 스킬 폴더의 파일

| 파일 | 용도 | 복사 위치 |
|---|---|---|
| `workflows/ci.yml` | PR 검증(컴파일·테스트·ArchUnit·정적분석) | `.github/workflows/` |
| `workflows/deploy.yml` | 빌드·이미지 푸시·환경별 배포 | `.github/workflows/` |
| `workflows/Dockerfile` | 멀티스테이지 JVM 이미지 | 프로젝트 루트 |
| `workflows/deploy-checklist.md` | 배포 전후 확인 목록 | `docs/ops/` |

## 1. 파이프라인 단계

```
PR:      lint/format -> 컴파일 -> 단위 테스트 -> ArchUnit -> 정적 분석 -> (경로별) 통합 테스트
main:    위 전부 -> 이미지 빌드 -> 레지스트리 푸시 -> dev 자동 배포 -> 스모크
릴리스:  [수동 승인] -> prod 배포 -> 스모크 -> 관찰
```

- **빠른 것부터.** 포맷·컴파일이 30초 안에 실패하면 나머지를 안 돌린다. 느린 통합 테스트는 뒤로.
- PR에서 도는 검증은 로컬 pre-commit/pre-push와 **같은 규칙**이어야 한다(`harness`). CI에서만 걸리는 규칙은 개발자를 괴롭힌다.
- 같은 아티팩트(이미지)를 **환경마다 다시 빌드하지 않는다.** 한 번 빌드해 dev -> prod로 승격한다. 다시 빌드하면 "dev에서는 됐는데"가 생긴다.
- 실패한 단계의 로그와 리포트를 아티팩트로 올린다. 테스트 리포트, 커버리지, 평가 결과(`prompt-and-eval`).

## 2. 트리거와 경로 필터

- PR 검증은 `pull_request`, 배포는 `push`(main) 또는 태그. 둘을 한 워크플로에 섞지 않는다.
- 문서만 바뀐 PR에 전체 빌드를 돌리지 않는다. `paths-ignore`로 `docs/**`, `**.md` 제외.
- 반대로 특정 경로에서만 도는 검증은 `paths`로 건다(프롬프트 평가, 인프라 코드).
- `concurrency`로 같은 브랜치의 이전 실행을 취소한다. 큐가 밀리지 않는다.
- prod 배포는 자동 트리거를 두지 않는 것이 기본. 태그 푸시 또는 수동 실행(`workflow_dispatch`) + 승인.

## 3. 환경 분리와 승인

- GitHub **Environments**를 실제 있는 환경만큼 만들고(기본 dev/prod) 시크릿과 변수를 환경별로 둔다. 리포지토리 시크릿 하나로 전 환경을 돌리지 않는다.
- **스테이징이 없으면 dev가 유일한 사전 검증 환경이다.** dev를 운영과 최대한 같게 유지하고(같은 DB 엔진·버전, 같은 스토리지 종류, 같은 배포 방식), prod에서 처음 실행되는 것이 없게 한다. 마이그레이션, 대량 배치, 알림 발송은 dev에서 한 번 돌려본 뒤 prod로 간다.
- prod 환경에 **필수 리뷰어(required reviewers)** 를 건다. 이게 사람 승인 게이트다.
- 환경별로 다른 것: DB 접속 정보, 외부 API 키, 버킷, 도메인, 로그 레벨, 배치 on/off(`config-and-secrets`, `batch-and-scheduler` 2장).
- 환경 이름을 이미지 태그나 설정 파일명에 섞지 않는다. **같은 이미지 + 다른 환경변수**가 원칙이다.

## 4. 시크릿

- 시크릿은 **GitHub Secrets 또는 외부 시크릿 매니저**에서만. 워크플로 파일, Dockerfile, 이미지 레이어에 넣지 않는다.
- 빌드 인자(`--build-arg`)로 시크릿을 넘기지 않는다. **이미지 히스토리에 남는다.** 필요하면 BuildKit secret mount.
- 로그에 시크릿이 찍히지 않게 한다. GitHub이 자동 마스킹하지만 base64·JSON 조각은 놓친다.
- 클라우드 접근은 장기 액세스 키 대신 **OIDC 기반 단기 자격증명**을 쓴다. 키가 없으면 유출도 없다.
- PR 워크플로에 운영 시크릿을 노출하지 않는다. 포크 PR은 특히(`pull_request_target` 사용 시 주의).
- 시크릿 스캔(gitleaks)을 CI에도 둔다. pre-commit이 우회될 수 있다(`harness`).

## 5. 이미지

- 멀티스테이지 빌드. 빌드 도구(Gradle, JDK 전체)를 런타임 이미지에 남기지 않는다.
- 런타임은 JRE 또는 distroless. 베이스 이미지 태그를 **다이제스트로 고정**하면 재현 가능해진다.
- 레이어 캐시: 의존성 다운로드와 소스 복사를 분리한다. 소스만 바뀌면 의존성 레이어를 재사용한다.
- 태그 규칙: `<커밋SHA>`를 **불변 태그**로 항상 붙이고, `latest`나 환경명 태그는 보조로만. 롤백은 SHA 태그로 한다.
- 이미지 취약점 스캔을 파이프라인에 넣는다. 심각도 기준과 실패 정책을 정한다.
- 비 root 사용자로 실행한다. 컨테이너 안에서 root일 이유가 없다.
- 헬스체크 엔드포인트(`/actuator/health/liveness`, `/readiness`)를 노출하고 배포 도구가 그것을 본다.

## 6. DB 마이그레이션과 배포 순서

- **스키마 변경과 코드 배포는 같은 순간에 일어나지 않는다.** expand-contract 순서를 지킨다(`db-schema-and-migration` 5장).
- 순서: 마이그레이션(하위 호환) -> 코드 배포 -> (관찰) -> 정리 마이그레이션.
- **파이프라인이 운영 DB에 직접 DDL을 실행할지는 신중히 정한다.** 회사 관행이 수동 실행이면 파이프라인은 SQL 파일을 산출물로 올리고 실행은 사람이 한다.
- 어느 쪽이든 **AI는 DB에 접속하지 않는다**(`db-schema-and-migration` 0장). 워크플로 파일을 만드는 것과 실행하는 것은 다르다.
- 롤백 가능한 마이그레이션인지 확인한다. 컬럼 삭제는 롤백이 안 된다.

## 7. 배포와 롤백

- 무중단 배포(rolling, blue-green)를 쓰면 **구버전과 신버전이 동시에 뜨는 구간**이 있다. API와 스키마가 그 구간을 견뎌야 한다.
- 배포 후 **스모크 테스트**를 자동으로 돌린다: 헬스체크, 핵심 엔드포인트 1~2개, 로그인. 실패하면 롤백.
- 롤백은 **이전 이미지 SHA로 되돌리는 것**이고, 명령 하나로 돼야 한다. 절차를 `docs/ops/`에 적어 둔다.
- 코드 롤백이 스키마까지 되돌리지 않는다는 것을 인지한다. 그래서 6장의 순서가 중요하다.
- 배포 기록(누가 언제 무엇을)을 남긴다. `rca-procedure`의 타임라인이 여기서 시작한다.
- 배포 직후 관찰 지표를 정한다: 에러율, p95 지연, 재시작 수(`logging-observability`).

## 8. 실패 대응

- 플레이키 테스트를 재시도로 덮지 않는다. 격리하거나 고친다. 재시도는 실패를 숨긴다.
- CI가 자주 깨지면 사람들이 결과를 안 본다. **깨진 main은 최우선으로 고친다.**
- 캐시 때문에 실패가 재현되지 않으면 캐시를 끄고 재실행하는 경로를 둔다.
- 워크플로 자체를 디버깅할 때 임시로 시크릿을 출력하지 않는다.

## 9. 리뷰 체크

- 액션이 버전(가능하면 커밋 SHA)으로 고정돼 있는가
- 같은 이미지를 환경 간에 승격하는가, 환경마다 재빌드하지 않는가
- prod 배포에 사람 승인이 있는가
- 시크릿이 빌드 인자·이미지 레이어·로그에 노출되지 않는가
- 이미지 태그에 커밋 SHA가 있는가(롤백 가능한가)
- 마이그레이션과 코드 배포 순서가 정의돼 있는가
- 배포 후 스모크 테스트와 롤백 절차가 있는가
- CI 검증이 로컬 hook과 같은 규칙인가

## 하지 말 것

- 액션을 `@main`이나 태그 없이 사용
- 환경마다 이미지 재빌드
- `--build-arg`로 시크릿 전달
- 리포지토리 시크릿 하나로 전 환경 운영
- prod 자동 배포(승인 없음)
- `latest` 태그만 붙이고 SHA 태그 없이 배포
- 스키마 변경과 코드 배포를 같은 단계에서
- 플레이키 테스트를 재시도로 통과시키기
- 빌드 도구가 남은 런타임 이미지, root로 실행

## 관련 스킬

`harness`(로컬 검증과 같은 규칙), `config-and-secrets`(환경별 설정과 시크릿 분류), `db-schema-and-migration`(마이그레이션 순서, DB 실행 금지), `logging-observability`(배포 후 관찰 지표), `rca-procedure`(배포 기록과 타임라인), `test-writing-guide`(어떤 테스트를 어느 단계에), `prompt-and-eval`(경로 필터 평가 실행), `app-store-release`(모바일은 스토어 파이프라인이 별도).
