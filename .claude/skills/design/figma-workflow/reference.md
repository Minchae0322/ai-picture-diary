# figma-workflow - 참고

SKILL.md의 절 번호와 같은 순서.

## 0. Figma 스킬을 로드하는 법

Figma MCP는 스킬을 **리소스**로 제공한다. 두 경로가 있다.

1. 에이전트에 Figma 플러그인이 설치돼 있으면 `/figma-use` 같은 슬래시 명령으로 로드된다.
2. 없으면 MCP 리소스를 직접 읽는다.

```
skill://index.json                         # 전체 목록 (이름, 설명, URI)
skill://figma/<스킬이름>/SKILL.md            # 본문
skill://figma/<스킬이름>/references/<경로>   # SKILL.md가 상대 경로로 링크한 참고 파일
```

`get_figma_skill` 도구로 읽는다. 한 번에 하나씩, URI마다 한 번 호출한다.

일부 스킬은 설명에 **"MANDATORY prerequisite"** 가 붙어 있다. 해당 도구를 부르기 전에 반드시 로드해야 하는 것들이다(확인 시점 기준 `figma-use`, `figma-create-new-file`, `figma-design-to-code`, `figma-generate-diagram`, `figma-generative-plugins`, `figma-shaders`). **목록과 조건은 바뀔 수 있으므로 작업 시작 시 `skill://index.json`을 먼저 읽는 것이 안전하다.**

`get_design_context`에는 `skillNames` 파라미터가 있다. 리소스로 로드했으면 이름 앞에 `resource:`를 붙인다(예: `resource:figma-design-to-code`). 사용량 로깅용이라 동작에는 영향이 없지만 규약이므로 지킨다.

### 이 저장소가 Figma 스킬을 복사하지 않는 이유

`figma-design-to-code` 하나만 봐도 게이트 프로토콜(G1~G5), 힌트 우선순위 5단계, 에셋 지오메트리 규칙처럼 구체적인 절차가 들어 있고, Figma가 도구를 바꾸면 같이 바뀐다. 복사본을 두면 **두 개의 규칙이 생기고 하나는 틀린 것**이 된다. 그래서 이 스킬은 라우팅과 프로젝트 접합만 담는다.

## 2. 방향이 어긋났을 때

코드와 Figma가 다를 때 조용히 한쪽으로 맞추면 안 되는 이유는, **어느 쪽이 의도인지 모르기 때문**이다.

- Figma가 최신 = 디자이너가 개선했다 -> 코드를 맞춘다
- 코드가 최신 = 구현 중 제약을 발견해 바꿨다 -> Figma를 맞추고 **왜 바꿨는지 디자이너에게 전달**한다
- 둘 다 의도적 = 요구사항이 갈렸다 -> 사람이 결정할 문제

보고 형식 예:

> 시안과 코드가 세 군데 다릅니다. (1) 버튼 라운드: 시안 8, 코드 10(토큰 `--radius-md`) (2) 목록 간격: 시안 20, 코드 24(스케일에 20 없음) (3) 에러 문구: 시안에 없음, 코드에 있음. 어느 쪽을 기준으로 할까요?

## 3. 가져오기

### 시안 값 -> 토큰 매핑 표

시안을 받으면 구현 전에 이 표부터 만든다. 나중에 같은 시안을 또 볼 때 재사용된다.

| 시안 값 | 우리 토큰 | 판단 |
|---|---|---|
| `#3b6ef6` | `--color-primary` | 동일 |
| `#6b7385` | `--color-text-muted` | 동일 |
| `#9aa2b1` | `--color-text-subtle` | 시안은 본문에 썼으나 대비 2.9:1 미달 -> `--color-text-muted`로 올림. **디자이너에게 알림** |
| 간격 20 | `--space-6`(24) | 스케일에 20 없음. 24로 통일 |
| 간격 5 | `--space-1`(4) | 반올림 |
| 라운드 8 | `--radius-md`(10) | 토큰 사용 |
| 폰트 15 | `--text-base`(16) | 스케일에 15 없음 |

- **어긋난 값을 조용히 넘기지 않는다.** 표의 "판단" 열이 리뷰와 디자이너 피드백의 근거가 된다.
- 어긋남이 3~4개를 넘으면 토큰이 시안과 안 맞는 것이다. 토큰 스케일을 고칠지 시안을 고칠지 논의한다.

### 절대 좌표 -> 레이아웃

Figma가 돌려주는 구조는 종종 절대 좌표다.

```jsx
// Figma 반환 (참고용)
<div className="relative w-[375px] h-[812px]">
  <div className="absolute left-[16px] top-[24px] w-[343px] h-[56px]">...</div>
  <div className="absolute left-[16px] top-[96px] w-[343px] h-[200px]">...</div>
</div>
```

```jsx
// 우리 코드
<div className="flex flex-col gap-6 p-4">
  <Header />
  <ArticleCard {...props} />
</div>
```

- `375px`는 시안 폭이지 우리 화면 폭이 아니다. 고정 폭을 옮기지 않는다.
- `top` 차이(96 - 24 - 56 = 16)가 실제 간격이다. 이것을 스케일 값(16)으로 바꾼다.
- Figma에 Auto Layout이 적용된 노드는 flex로 거의 그대로 대응된다. 절대 좌표가 많이 나오면 시안 자체가 Auto Layout 없이 그려진 것이므로, 디자이너에게 Auto Layout 적용을 요청하면 이후 작업이 훨씬 수월해진다.

### 시안 수령 체크리스트

시안을 받고 구현을 시작하기 전에 확인한다. 없는 것은 **구현하면서 지어내지 말고 물어본다.**

- [ ] 모바일/데스크톱 중 어느 폭의 시안인가, 다른 폭은 어떻게 되나
- [ ] hover / focus / disabled / 선택 상태가 정의돼 있나
- [ ] 로딩, 데이터 없음, 에러 화면이 있나
- [ ] 텍스트가 길거나 비었을 때 어떻게 되나 (제목 3줄, 이름 20자)
- [ ] 목록의 최대/최소 개수, 무한 스크롤인지 페이징인지
- [ ] 다크 모드가 있나
- [ ] 아이콘이 우리 아이콘 세트에 있나, 새로 받아야 하나
- [ ] 폰트가 프로젝트에 있는 폰트인가 (없으면 라이선스 확인)
- [ ] 대비 미달인 조합이 있나 (직접 계산)

체크리스트를 통과 못 한 항목은 **구현 전에 목록으로 만들어 한 번에 물어본다.** 구현 중에 하나씩 물으면 진행이 계속 끊긴다.

## 4. 토큰 동기화 절차

코드가 진실인 경우(기본):

1. `tokens.css`의 2단계(의미 토큰)를 기준 목록으로 뽑는다.
2. Figma 변수 컬렉션을 같은 이름으로 만든다(`color/primary`, `radius/md`, `space/4`).
3. 값이 다른 것을 찾아 코드 값으로 맞춘다. 이때 **Figma에서 그 변수를 쓰는 컴포넌트가 함께 바뀐다** - 디자이너에게 미리 알린다.
4. 이후 토큰 변경은 코드에서 하고 Figma에 반영한다.

Figma가 진실인 경우:

1. Figma 변수를 뽑아(`get_variable_defs`) 이름·값 표를 만든다.
2. `tokens.css`의 2단계를 그 값으로 맞춘다. 1단계 원시값은 코드에만 두어도 된다.
3. 다크 모드는 Figma의 모드(mode)와 CSS의 `[data-theme]`을 대응시킨다.

어느 쪽이든 `CLAUDE.md`에 한 줄:

```
- 디자인 토큰 진실: 코드 (`src/styles/tokens.css`) -> Figma 변수는 여기서 파생
```

## 5. 쓰기 안전

### 작업 전

```
1. 대상 파일이 누가 쓰는 파일인지 확인한다
2. 새 파일 / 새 페이지 / 새 프레임 중 어디에 그릴지 정한다
3. 기존 파일을 고쳐야 하면 무엇을 바꿀지 먼저 말하고 승인받는다
4. (가능하면) 브랜치 기능이 있는 플랜이면 브랜치에서 작업한다
```

### 인스턴스와 메인 컴포넌트

Figma에서 같은 컴포넌트를 여러 화면이 쓴다. 인스턴스를 직접 뜯어고치면 그 화면만 달라지고 "왜 여기만 다르지"가 남는다.

- 모든 인스턴스가 바뀌어야 함 -> **메인 컴포넌트** 수정
- 일부만 달라야 함 -> **변형(variant) 추가** 후 그 변형 사용
- 이 인스턴스만 예외 -> 정말 예외인지 의심한다. 코드의 "이번만 다른 버튼"과 같은 문제다(`design-system` 5장)

### 되돌릴 근거 남기기

작업 전후로 `get_screenshot`을 찍어 두거나, 변경한 노드 목록을 요약해 남긴다. Figma의 버전 기록으로 되돌릴 수 있지만, **무엇을 되돌려야 하는지** 아는 것은 우리 몫이다.

## 6. Code Connect 도입 기준

- 같은 컴포넌트를 **세 번째 옮기고 있으면** 매핑한다. 한두 번이면 그냥 옮기는 게 빠르다.
- 매핑 대상: `shared/ui/`의 Button, Input, Card, Modal 같은 공용 컴포넌트.
- 매핑 안 함: feature 전용 컴포넌트(`ArticleCard`), 페이지 레이아웃, 일회성 화면.
- props ↔ 변형 이름을 맞춘다.

```
Figma variant:  Size = Small | Medium | Large
코드 props:      size: 'sm' | 'md' | 'lg'
```

이름이 다르면 매핑 파일에 변환을 적어야 하고, 그 변환이 또 하나의 관리 지점이 된다. 처음부터 맞추는 게 싸다.

## 7. 다이어그램 선택

| 상황 | 도구 |
|---|---|
| 문서에 남길 흐름도·시퀀스·ERD | Mermaid (`deliverable-write`) |
| 설계 회의에서 같이 보며 논의 | FigJam |
| 발표·제안서용 그림 | FigJam 또는 Figma |
| 코드 리뷰에서 diff가 보여야 함 | Mermaid |

FigJam에서 논의한 결과는 **결론만 문서로 옮긴다.** 보드를 그대로 두고 링크만 남기면, 그 보드가 최신인지 아무도 모르게 된다.
