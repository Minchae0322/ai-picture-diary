# 산출물 동기화 (deliverable-sync)

## 목적
코드가 바뀌면 그 도메인의 **비즈니스 로직 현행 문서**도 같이 바뀌어야 한다. 이 스킬은 **마지막 동기화 이후의 커밋만** 보고, **인덱스로 찾은 문서만** 읽고 갱신해서 저장소 전체를 다시 읽지 않고 산출물을 최신 상태로 유지한다.

원칙 세 가지:

1. 전체를 읽지 않는다. 읽는 순서는 보드 -> 인덱스 -> (변경과 매칭된) 현행 문서 -> (필요하면) 코드 diff.
2. 커밋 해시가 진실이다. 보드의 `last_synced_commit` 이후만 처리하고, 문서 커밋이 끝나면 보드를 올린다.
3. 사람이 판단할 것은 사람에게 넘긴다. 인덱스에 없는 변경은 추측으로 문서를 만들지 않고 보드의 "미분류"에 적는다.

## 언제 적용
- "산출물 업데이트해줘", "문서 최신화", "이번 작업 문서에 반영" 요청
- PR 머지 후, 릴리즈 노트 작성 전 정기 동기화
- 새 도메인/기능이 추가되어 현행 문서와 인덱스를 새로 만들어야 할 때
- 보드에 미분류 항목이 쌓여 정리할 때

> 문서의 **문체**(개조식, 종결어미, 수치 표기)는 `report-style`. 이 스킬은 무엇을 쓸지를 정한다.

## 두 종류의 문서
| 구분 | 파일명 | 갱신 | 예 |
|---|---|---|---|
| 이력 문서 | `YYYY-MM-DD-제목.md` | 작성 후 불변. 이 스킬은 건드리지 않음 | `article/2026-07-20-공용기사-잠금-미해제-장애분석.md` |
| 현행 문서 | `<로직>-비즈니스로직.md` (날짜 없음) | 코드 따라 계속 갱신. 이 스킬의 대상 | `articleDeletionRequest/기사삭제요청-비즈니스로직.md` |

현행 문서의 큰 변경(상태 모델 개편 등)은 "기존 vs 현재" 절에 요약하고 상세 배경은 이력 문서로 링크한다. 현행 문서가 역사책이 되면 안 된다.

## 폴더 구조
표준 구조는 `deliverable-structure` 스킬이 정의한다. 이 스킬이 직접 다루는 것: `docs/INDEX.md`(현행 문서 <-> 코드 경로, 매 실행마다 읽는 유일한 파일), `docs/BOARD.md`(동기화 상태, 미분류, 할 일), `docs/_templates/현행문서.md`, `docs/domain/<도메인>/`(폴더명 = 코드 도메인 패키지명, 철자·대소문자 동일) 아래 현행 문서와 이력 문서.

- 기존 프로젝트가 `domain/` 계층 없이 `docs/<도메인>/`을 쓰면 그대로 둔다. INDEX.md의 경로가 진실이다.
- 현행 문서 하나 = 비즈니스 로직 묶음 하나(서비스/유스케이스 단위 또는 상태 모델을 공유하는 엔티티 단위). 나누는 기준은 `deliverable-write` 1단계.

## INDEX.md 형식
매 실행마다 전부 읽는 유일한 파일이라 짧아야 한다. 현행 문서 한 줄, 설명 없이 매핑만. 이력 문서는 넣지 않는다. 템플릿: `deliverable-structure` 스킬의 `templates/INDEX.md`.

- 열: `| 문서 | 코드 경로(글롭, 쉼표 구분) | 키워드 |`. 문서 경로는 docs/ 기준, 코드 경로는 `src/main/java/<base>/app` 이하 상대 경로(`git diff --name-only` 결과와 매칭).
- 한 코드 파일이 여러 문서에 걸릴 수 있다. 정상이다.
- 현행 문서가 하나인 도메인은 `도메인/**` 허용. 둘 이상이면 글롭을 좁게 나눈다.
- 키워드는 코드 경로로 못 잡는 변경(SQL 패치, 설정, 커밋 메시지)을 문서에 연결하는 보조 수단.
- `src/test/**`, 빌드 파일, 인프라 설정은 넣지 않는다.
- 현행 문서가 50개를 넘으면 도메인별 `INDEX.md`로 쪼개고 루트는 도메인 목록만.

## BOARD.md 형식
템플릿: `deliverable-structure` 스킬의 `templates/BOARD.md`. 절 구성:

- 동기화 상태: `last_synced_commit`, `last_synced_at`, `synced_by`
- 미분류 변경 (사람 판단 필요): `| 커밋 | 파일 | 추정 도메인 | 메모 |`
- 갱신 이력 (최근 10건만 유지): `| 일시 | 갱신 문서 | 커밋 범위 |`
- 할 일: 체크박스 목록

`last_synced_commit`은 **문서 커밋이 끝난 뒤** 올린다. 갱신 이력은 10건만, 그 이상은 git log가 이력이다. CHANGELOG.md는 코드 변경 기록, release-notes/는 배포 단위 기록, 보드는 현행 문서 동기화 상태만 다룬다.

## 현행 문서 형식
구조와 작성 기준은 `deliverable-write` 스킬이 정의한다(템플릿: `_templates/현행문서.md`). 절 순서: 메타(도메인 / 코드 / 기준 커밋 / 갱신, 이 스킬이 기계적으로 올림) -> 1 실행 흐름 -> 2 한눈에 보기 -> 3 상태 모델 -> 4 주요 액션 -> 5 액션 상세 -> 6 이력 및 알림 -> 7 기존 vs 현재 -> 8 알려진 이슈 / TODO -> 변경 이력.

- 이모지를 쓰지 않는다. 강조는 `> [!IMPORTANT]`, `> [!WARNING]` 같은 Markdown 구조로.
- 코드를 복사하지 않는다. 메서드명/클래스명 수준까지만.
- 액션 상세의 항목 순서(실행 주체 / 실행 전 조건 / 막히는 경우 / 상태 변화 / 이력 / 알림)를 모든 문서에서 같게 유지한다.
- 문서와 코드가 어긋나면 "알려진 이슈"에 적고 코드를 고치지 않는다.

## 동기화 절차
### 0. 준비
- 저장소 루트에서 실행. `docs/INDEX.md`가 없으면 "최초 구축"으로.
- `BOARD.md`만 읽어 `last_synced_commit`을 얻는다.

### 1. 변경 범위 수집 (코드는 아직 읽지 않는다)
- `git log --oneline <last>..HEAD`, `git diff --name-only <last>..HEAD -- src/main`
- 커밋 0개면 `last_synced_at`만 갱신하고 종료. 변경 파일 200개 초과면 사람에게 범위를 묻는다.
- 커밋 메시지는 키워드 매칭용으로 보관. `<type>(<scope>): <subject>` 규칙이면 `scope`가 곧 도메인.

### 2. 인덱스 매칭
- `INDEX.md`를 읽고 변경 파일을 코드 경로 글롭과 대조해 **갱신 후보 문서 집합**을 만든다.
- 매칭 안 된 파일: 인덱스에 없는 도메인 패키지 파일이거나 새 `*Service`/`*Facade` -> "신규 문서 후보". 그 외(설정, 유틸, DTO 필드 추가) -> 커밋 scope와 키워드 대조, 없으면 "미분류".
- 테스트/빌드/인프라/`docs/` 변경은 무시.

### 3. 현행 문서 갱신 (후보 문서만 읽는다)
1. 문서를 읽는다.
2. 그 문서의 코드 경로 중 **이번에 바뀐 파일만** `git diff <last>..HEAD -- <파일>`로 본다. diff로 판단이 안 될 때만 파일을 연다.
3. 영향 절 판단: 가드/권한/처리/알림 -> 5번(4번 표 조건/결과도 함께) / 순서·분기 -> 1번 Mermaid와 2번 / 상태값 추가·삭제 -> 3번 / 이력·알림 기록값 -> 6번 / 큰 개편 -> 7번 요약 + 이력 문서 링크(없으면 보드 할 일에 "이력 문서 작성 필요") / 영향 없는 변경(리팩터링, 로그, 성능) -> 메타의 기준 커밋만.
4. 상단 메타(`기준 커밋`, `갱신`)를 올리고 변경 이력에 한 줄 추가.
5. 확실하지 않으면 `<!-- TODO(sync): ... 확인 필요 -->`를 남기고 보드 "할 일"에도 적는다. 추측으로 규칙을 쓰지 않는다.

### 4. 신규 현행 문서 -> `deliverable-write` 실행
| 상황 | 처리 |
|---|---|
| 2단계 "신규 문서 후보" | 이 스킬이 직접 쓰지 않는다. `deliverable-write` 스킬을 실행해 문서를 만들고 돌아온다 |
| write 종료 후 | `INDEX.md`에 줄이 추가되어 있어야 한다. 없으면 write가 덜 끝난 것 |
| 기존 `docs/`에 현행 문서 성격 파일 존재 | `deliverable-write`의 "승격 절차"로 |

### 5. 보드 갱신과 커밋
- 미분류 변경을 보드에 적고 갱신 이력에 한 줄 추가.
- 문서 변경만 하나의 커밋. 프로젝트 커밋 규칙을 따른다. 예: `docs(article): 현행 문서 갱신 (a1b2c3d..f4e5d6)`
- CHANGELOG.md에는 넣지 않는다. 코드 커밋과 문서 커밋을 섞지 않는다.
- **커밋이 끝난 뒤** `last_synced_commit`을 이번에 처리한 코드 커밋의 HEAD로 올린다. 문서 커밋은 다음 범위에 들어가도 `docs/` 변경이라 무시된다.

### 최초 구축 (docs/INDEX.md가 없을 때)
1. 도메인 패키지 목록(`ls src/main/java/<base>/app/`). 65개처럼 많으면 **최근 6개월 커밋이 있는 도메인**부터.
2. 기존 `docs/{모듈명}/`에 현행 문서 성격 파일(예: `기사삭제요청-비즈니스로직-이력.md`)이 있으면 승격: `-이력`을 떼고 메타를 붙이고 인덱스에 등록. 새로 쓰지 않는다.
3. 나머지 도메인은 서비스/파사드 목록으로 문서 후보를 만들고 사람에게 "만들 것 / 합칠 것 / 뺄 것"을 확인받는다. 전부 자동 생성하지 않는다.
4. 확인된 목록으로 템플릿 뼈대를 만들고 `INDEX.md`를 채운다. 본문은 도메인별로 나눠서 채운다.
5. `BOARD.md`의 `last_synced_commit`을 현재 HEAD로. 이후 증분 동기화.

## 토큰 절약 규칙
- 읽는 파일 수: 보드 1 + 인덱스 1 + 후보 문서 N + diff N. 저장소 전체 탐색은 최초 구축 때만.
- 코드는 diff로 본다. 이력 문서는 읽지 않고 링크만 건다. 인덱스가 커지면 도메인별로 쪼갠다.
- 변경 파일이 여러 문서에 매칭되면 diff는 한 번만 읽고 여러 문서에 적용한다.
- 문서 변경 이력과 보드 갱신 이력은 10건까지만.

## 하지 말 것
- 보드 없이 "전체 문서를 코드와 대조". 이력 문서(`YYYY-MM-DD-*.md`) 수정. 현행 문서를 역사책으로 만들기.
- 매칭 안 되는 변경을 추측으로 문서에 넣기(미분류로). 문서에 코드를 통째로 붙이기. 문서-코드 불일치 시 코드 수정("알려진 이슈"에).
- 문서가 여럿인 도메인에서 인덱스 글롭을 `도메인/**`로 잡기.
- 코드 커밋에 문서 변경 끼워 넣기, CHANGELOG에 문서 갱신 적기. 동기화 실패 상태에서 `last_synced_commit` 올리기.

## 관련 스킬
- `deliverable-structure` 스킬 - docs/ 표준 구조, INDEX/BOARD 템플릿
- `deliverable-write` 스킬 - 신규 현행 문서 작성과 승격 (4단계에서 호출)
- `ddd-spring` 스킬 - 도메인 패키지/유스케이스 단위 = 도메인 폴더/현행 문서 단위
