# deliverable-sync - 참고 자료

`SKILL.md`의 규칙에 대한 이유, 예시, 상세 형식을 담는다. SKILL.md와 함께 읽는다.

---

## 두 종류의 문서 (왜 나누는가)

기존 `docs/{모듈명}/` 안에는 이미 날짜 붙은 문서(`2026-05-14-편집잠금-하트비트-자동해제-기획안.md`)가 쌓여 있다. 이건 **이력 문서**다. 그 시점의 기획안, API 안내, 장애 분석, 프론트 전달 프롬프트 같은 것이고, 한 번 쓰면 고치지 않는다. 이 스킬은 이력 문서를 건드리지 않는다.

이 스킬이 관리하는 것은 **현행 문서**다. 도메인의 비즈니스 로직이 "지금 어떻게 동작하는가"를 한 파일에 유지하는 문서로, 코드가 바뀌면 같이 바뀐다.

현행 문서에서 큰 변경(상태 모델 개편 등)이 있으면 "기존 vs 현재" 절에 요약하고, 상세 배경은 이력 문서로 따로 남겨 링크한다. 현행 문서가 역사책이 되면 안 된다.

---

## 폴더 구조 (이 스킬이 다루는 부분)

```
docs/
├── INDEX.md                        # 현행 문서 <-> 코드 경로. 매 실행마다 읽는 유일한 파일
├── BOARD.md                        # 동기화 상태, 미분류, 할 일
├── _templates/현행문서.md
└── domain/<도메인>/                 # 폴더명 = 코드 도메인 패키지명 (철자·대소문자 동일)
    ├── <로직>-비즈니스로직.md         # 현행 문서 (이 스킬이 갱신)
    └── YYYY-MM-DD-<제목>.md          # 이력 문서 (건드리지 않음)
```

---

## INDEX.md 형식 (예시)

인덱스는 **매 실행마다 전부 읽는 유일한 파일**이라 짧아야 한다. 현행 문서 한 줄, 설명 없이 매핑만. 이력 문서는 넣지 않는다.

```markdown
# 현행 문서 인덱스

<!-- 형식: | 문서 | 코드 경로(글롭, 쉼표 구분) | 키워드 | -->
<!-- 문서 경로는 docs/ 기준, 코드 경로는 src/main/java/<base>/app 이하 상대 경로. git diff --name-only 결과와 매칭된다. -->
<!-- domain/ 계층을 생략한 프로젝트면 문서 경로도 그에 맞춘다. -->
<!-- 이력 문서(YYYY-MM-DD-*.md)는 여기 넣지 않는다. -->

| 문서 | 코드 경로 | 키워드 |
|---|---|---|
| domain/article/기사-비즈니스로직.md | article/service/Article*, article/domain/Article.java, article/domain/ArticleStatus*.java | 기사 등록, 송고, 출고, 상태 |
| domain/article/편집잠금-비즈니스로직.md | article/service/*Lock*, article/domain/*Lock*, article/scheduler/* | 편집잠금, 하트비트, 자동해제 |
| domain/articleDeletionRequest/기사삭제요청-비즈니스로직.md | articleDeletionRequest/** | 삭제요청, 출고확인, 디지털확인, 국장확인 |
| domain/cuesheet/큐시트-비즈니스로직.md | cuesheet/service/*, cuesheet/domain/*, cuesheet/facade/* | 큐시트, 수퍼제작, 상태 동기화 |
| domain/auth/인증-비즈니스로직.md | auth/**, common/security/** | 토큰, 로그인, WISE 자동로그인 |
```

규칙 설명:

- 한 코드 파일이 여러 문서에 걸릴 수 있다(`Article.java`가 기사/편집잠금 둘 다). 정상이다.
- 도메인이 작아 현행 문서가 하나면 `도메인/**`로 잡아도 된다. 문서가 둘 이상인 도메인은 글롭을 좁게 나눈다. 안 그러면 모든 변경이 모든 문서에 걸려 인덱스의 의미가 없다.
- 키워드는 코드 경로로 못 잡는 변경(SQL 패치, 설정, 커밋 메시지)을 문서에 연결하는 보조 수단.
- `src/test/**`, 빌드 파일, 인프라 설정은 인덱스에 넣지 않는다.
- 현행 문서가 50개를 넘으면 도메인별 `INDEX.md`로 쪼개고 루트는 도메인 목록만.

## BOARD.md 형식 (예시)

```markdown
# 산출물 진행 보드

CHANGELOG.md는 코드 변경 기록, release-notes/는 배포 단위 기록, 이 보드는 **현행 문서 동기화 상태**만 다룬다.

## 동기화 상태
- last_synced_commit: a1b2c3d
- last_synced_at: 2026-09-08 19:50 KST
- synced_by: claude (deliverable-sync)

## 미분류 변경 (사람 판단 필요)
<!-- 인덱스에 매칭되지 않은 변경. 확인 후 현행 문서를 만들거나 인덱스에 추가하거나 "문서 불필요"로 지우고 커밋한다. -->
| 커밋 | 파일 | 추정 도메인 | 메모 |
|---|---|---|---|
| f4e5d6 | app/stt/service/SttModeService.java | stt | 새 서비스. stt/STT-비즈니스로직.md 신설 여부 결정 필요 |

## 갱신 이력 (최근 10건만 유지)
| 일시 | 갱신 문서 | 커밋 범위 |
|---|---|---|
| 2026-09-08 19:50 | article/편집잠금-비즈니스로직.md, cuesheet/큐시트-비즈니스로직.md | a1b2c3d..f4e5d6 |

## 할 일
- [ ] 기사삭제요청-비즈니스로직.md 3-6 삭제완료 이력 주석 해제 여부 확인 (코드 bd6f2bb94 기준 미기록 상태)
```

- `last_synced_commit`은 **문서 커밋이 끝난 뒤** 올린다. 중간에 실패하면 이전 값이 남아야 다음 실행이 놓치지 않는다.
- 갱신 이력은 10건만. 그 이상은 git log가 이력이다.

## 현행 문서 형식 (절 구성)

구조와 작성 기준은 `deliverable-write` 스킬이 정의한다(템플릿: `_templates/현행문서.md`). 이 스킬이 갱신할 때 알아야 할 것만 요약하면:

```text
# <도메인> 비즈니스 로직
> 도메인 / 코드 / 기준 커밋 / 갱신     <- 메타. 이 스킬이 기계적으로 올린다
## 1. 실행 흐름      Mermaid. 업무 동작 순서 (코드 호출 관계 아님)
## 2. 한눈에 보기    표
## 3. 상태 모델      stateDiagram 또는 조건 표
## 4. 주요 액션      표
## 5. 액션 상세      실행 주체 / 실행 전 조건 / 막히는 경우 / 상태 변화 / 이력 / 알림
## 6. 이력 및 알림   표
## 7. 기존 vs 현재   큰 변경 때만
## 8. 알려진 이슈 / TODO
## 변경 이력
```

액션 상세의 항목 순서를 모든 문서에서 같게 유지하는 이유: 순서가 같아야 diff를 보고 어느 항목을 고칠지 바로 찾는다.

---

## 동기화 절차 (보충 설명)

### 1. 변경 범위 수집

```bash
git log --oneline <last_synced_commit>..HEAD
git diff --name-only <last_synced_commit>..HEAD -- src/main
```

- 변경 파일이 200개를 넘으면(대규모 리팩터링, 포맷팅) 사람에게 범위를 묻는다. 자동으로 전부 처리하지 않는다.
- 커밋 메시지는 키워드 매칭에 쓰므로 함께 보관한다. 커밋 규칙이 `<type>(<scope>): <subject>`이면 `scope`가 곧 도메인이라 매칭에 바로 쓴다.

### 2. 인덱스 매칭

- 여기까지 읽은 파일: 보드, 인덱스 두 개.

### 3. 현행 문서 갱신 - diff와 절의 대응

- 가드/권한/처리/알림 변경 -> 5번 액션 상세의 해당 항목 수정. 4번 주요 액션 표의 조건/결과도 같이
- 업무 순서나 분기가 바뀜 -> 1번 실행 흐름 Mermaid와 2번 한눈에 보기 수정
- 상태값 추가/삭제 -> 3번 상태 모델
- 이력/알림 기록값 변경 -> 6번 표
- 큰 개편 -> 7번 "기존 vs 현재"에 요약하고, 상세는 이력 문서가 있으면 링크. 없으면 보드 "할 일"에 "이력 문서 작성 필요"로 남긴다.
- 문서에 영향 없는 변경(리팩터링, 로그, 성능) -> 본문은 손대지 않고 상단 메타의 기준 커밋만 올린다.

파일 전체를 읽지 않는다. diff만으로 규칙 변화를 판단하기 어려울 때만 해당 파일을 연다.

### 5. 보드 갱신과 커밋

- CHANGELOG.md에는 넣지 않는다. CHANGELOG는 코드 변경 기록이고, 현행 문서 갱신은 그 결과다.

### 최초 구축

- 4단계에서 본문을 한 번에 다 하면 품질이 떨어진다. 도메인별로 나눠서 채운다.

## 토큰 절약 규칙 (원문)

- 읽는 파일 수 기준: 보드 1 + 인덱스 1 + 후보 문서 N + diff N. 저장소 전체 탐색은 최초 구축 때만.
- 코드는 전체 파일이 아니라 diff로 본다. diff로 판단이 안 될 때만 파일을 연다.
- 이력 문서는 읽지 않는다. 현행 문서에서 링크만 건다.
- 인덱스가 커지면 도메인별로 쪼갠다.
- 변경 파일이 여러 문서에 매칭되면 diff는 한 번만 읽고 여러 문서에 적용한다.
- 문서 변경 이력과 보드 갱신 이력은 10건까지만. 나머지는 git이 기억한다.

## 하지 말 것 (이유 포함)

- 보드 없이 "전체 문서를 코드와 대조"하는 것.
- 이력 문서(`YYYY-MM-DD-*.md`)를 고치는 것. 그건 그 시점의 기록이다.
- 현행 문서를 역사책으로 만드는 것. 큰 변경은 요약 + 이력 문서 링크.
- 매칭 안 되는 변경을 추측으로 문서에 넣는 것. 미분류로 넘긴다.
- 문서에 코드를 통째로 붙이는 것.
- 문서가 코드와 어긋난다고 코드를 고치는 것. "알려진 이슈"에 적는다.
- 인덱스 글롭을 문서가 여럿인 도메인에서 `도메인/**`로 잡는 것.
- 코드 커밋에 문서 변경을 끼워 넣거나, CHANGELOG에 문서 갱신을 적는 것.
- 동기화 도중 실패했는데 `last_synced_commit`을 올리는 것.

## 참고

- `deliverable-structure` 스킬 - docs/ 표준 구조. 파일을 어디에 둘지는 여기서 정한다.
- `deliverable-write` 스킬 - 신규 현행 문서 작성과 승격. 이 스킬의 4단계에서 호출.
- `ddd-spring` 스킬 - 도메인 패키지와 유스케이스 단위가 이 문서의 도메인 폴더/현행 문서 단위와 1:1로 대응한다.
- 프로젝트의 `docs/개발-가이드.md` - CHANGELOG, 커밋 규칙, 이력 문서 파일명 규칙(`YYYY-MM-DD-제목.md`)
