# 산출물 작성 (deliverable-write)

## 목적

코드에서 비즈니스 로직 현행 문서를 처음 작성한다. `deliverable-sync`는 기존 현행 문서를 갱신하고, 이 스킬은 아직 없는 현행 문서를 만든다.
문서의 중심은 코드 설명이 아니라 `실제 동작 -> 업무 흐름 -> 상태 변화 -> 주요 규칙 -> 코드 근거` 순서다. 코드 구조를 그대로 설명하는 문서를 만들지 않는다.

## 언제 적용

- `deliverable-sync` 2단계에서 "신규 문서 후보"가 나왔을 때 (sync 4단계에서 호출)
- 최초 구축 중 도메인별 현행 문서를 채울 때
- "이 도메인 문서 만들어줘" 요청
- 기존 `*-비즈니스로직-이력.md` 등을 현행 문서로 승격할 때

> 문서의 **문체**(개조식, 종결어미, 수치 표기)는 `report-style`. 이 스킬은 무엇을 쓸지를 정한다.

## 작성 원칙

1. 컨트롤러에서 시작해 안쪽으로 읽는다. 엔드포인트로 액션을 먼저 찾고 Service, Entity, Repository를 따라간다.
2. 코드에서 확인되는 사실만 기록한다: 조건문, 예외, 상태 변경, 저장/삭제, 이벤트, 알림, 권한, 테스트, 커밋.
3. 의도와 동작을 구분한다. 동작은 코드로, 이유는 커밋/ADR/이력 문서 근거가 있을 때만. 확인 불가면 추측하지 않는다.
4. 설명보다 시각화를 우선한다. 실행 순서 flowchart / 상태 변화 stateDiagram 또는 표 / 조건 조합 decision table / 역할별 동작 표 / 단일 규칙 bullet.
5. 가장 중요한 내용(실제 실행 흐름)을 코드 경로나 클래스 설명보다 먼저 배치한다.
6. 한 문서에는 하나의 업무 흐름만. 독립 흐름이 여러 개면 문서를 분리한다.
7. 이모지를 산출물 전체(제목, 경고, 상태, 주석, 표, 예시)에서 쓰지 않는다. 강조는 `> [!IMPORTANT]` 또는 `**중요 규칙**` 같은 Markdown 구조로.

## 최종 문서의 기본 구조

특별한 이유가 없다면 다음 순서를 따른다. `실행 흐름`이 첫 번째 본문 절이다.

```text
# <도메인> 비즈니스 로직
메타 정보
## 1. 실행 흐름      실제 업무가 시작부터 종료까지 어떻게 움직이는지. Mermaid 중심
## 2. 한눈에 보기    목적 / 시작점 / 주요 참여자 / 완료 조건 / 주요 결과
## 3. 상태 모델      상태값 / 상태 전이 / 상태 결정 조건
## 4. 주요 액션      어떤 행동을 누가 하고 어떤 결과가 발생하는지
## 5. 액션 상세      권한 / 가드 / 처리 / 상태 변화 / 이력 / 알림
## 6. 이력 및 알림
## 7. 기존 vs 현재   필요한 경우만
## 8. 알려진 이슈 / TODO
## 변경 이력
```

절별 핵심 규칙 (상세와 예시는 `reference.md`):

- 1 실행 흐름: 업무 동작 순서를 그린다. 코드 호출 관계(`Controller -> Service -> Repository`) 금지. DTO 변환, Mapper, save, Optional, Builder, getter는 제외. 흐름이 여럿이면 최상위 흐름 하나 + 복잡한 흐름만 상세화. API별 Mermaid를 만들지 않는다.
- 2 한눈에 보기: 목적 / 시작 / 주요 참여자 / 주요 흐름 / 반려 가능 단계 / 완료 조건 / 완료 결과 표. 세부 구현 없음.
- 3 상태 모델: stateDiagram 다음에 상태 의미 표. 상태 이름은 실제 코드 값. Boolean/날짜 컬럼 조합이면 enum을 만들어내지 않고 조건 표로 쓰며 `문서상 의미`가 코드 값이 아님을 명시.
- 4 주요 액션: 액션 / 실행 주체 / 실행 조건 / 주요 결과 표. API 명세처럼 모든 endpoint를 나열하지 않는다. 필요하면 API 열 추가.
- 5 액션 상세: 실행 주체 / 실행 전 조건 / 막히는 경우(조건-예외 메시지 표) / 처리 흐름 / 상태 변화 / 이력 / 알림. 간단한 액션은 Mermaid 생략. `confirm=true|false` 토글형은 확인/취소를 나누어 쓰고, 동작이 크게 다르면 흐름을 별도 시각화.
- 6 이력 및 알림: 이력(발생 시점 / `actType` / 주요 기록값), 알림(발생 시점 / 수신자 / 조건) 표.
- 7 기존 vs 현재: 최근 변경으로 규칙이 달라진 경우만. 이유는 ADR, 이력 문서, PRD, 커밋 메시지, 테스트 이름 근거가 있을 때만.
- 8 알려진 이슈 / TODO: 코드-주석 불일치, 주석 처리된 로직, 도달 불가 분기, 의도 불명 동작, 잠재 문제, 확신 부족 항목. `> [!WARNING]`, `> [!NOTE]`로.

## 코드 읽는 순서

1. 범위 확정: 대상 패키지의 파일 목록만 본다(`ls -R`). 서비스 1~2개, 같은 Entity, 같은 상태 모델, 하나의 흐름이면 문서 하나. 상태 모델/업무 목적/시작-종료가 다르거나 한 흐름도로 어렵면 분리 검토. 처음엔 하나로 조사하고 독립 흐름이 확인되면 분리.
2. Controller: endpoint, HTTP method, 권한 annotation, 호출 Service/Facade, 분기 입력값. 여기서 액션 목록을 먼저 만든다. 이 목록이 이후 탐색의 기준.
3. Service / Facade: 액션별로 선행/거부 조건, 예외 메시지, 상태 변경, 저장/삭제, 다른 객체 변경, History/Notification/Event, 다음 단계. private은 호출되는 것만. 미사용 코드 제외. 500줄 이상이면 public 목록 먼저.
4. Entity / Enum: 상태 필드, DB column, 상태값, 상태 변경 메서드, 생성/변경 불변식. 컬럼 조합 상태는 그대로 문서화.
5. 이력 / 알림 / 이벤트: 발생 액션, `actType`, 이전/이후 값, 알림 타입, 수신 대상, 행위자 제외, 중복 제거, 수신 설정, 후속 동작. 중요 이벤트는 실행 흐름에도 포함.
6. Repository: 조회/비즈니스 조건에 영향 주는 커스텀 쿼리만. 검색 조건, 정렬, 삭제 여부, 상태 필터, 사용자/조직 범위, 존재 판단.
7. 테스트: 클래스 이름과 `@DisplayName`만 먼저. 새 규칙이 보이면 코드 재확인. 테스트에만 있는 동작은 확정 규칙으로 쓰지 않는다.
8. Git 이력: 마지막에 `git log --oneline -20 -- <패키지>`. 상태/가드/순서 변경, 기존 vs 현재 필요 여부, 변경 이유. 커밋 메시지만으로 규칙을 확정하지 않는다.

## 확신 기준

- 확정: 조건문, 예외, 권한 annotation, 상태 변경, 저장/삭제, 이력, 알림, 이벤트가 코드에서 직접 확인됨 -> 사실로 기록.
- 근거와 함께: 의도가 커밋/테스트에서 확인됨 -> `(커밋 abc1234 기준)` 표시.
- 동작만: 이유를 모르면 동작만 쓴다. "다시 승인할 수 있도록" 같은 미확인 의도 문구 금지.
- 확인 필요: 확신 60% 미만이면 `<!-- TODO(sync): 확인 필요 - ... -->`를 남기고 `BOARD.md` 할 일에 올린다.

## 시각화와 길이

- 시각화는 이해 시간을 줄일 때만. 순서/분기 flowchart, 상태 전이 stateDiagram, 조건 조합/역할/가드 표, 단순 규칙 bullet, 단순 CRUD 짧은 설명. 같은 내용을 Mermaid, 표, 문장으로 반복하지 않는다.
- 길어지면 정보를 삭제하지 않고 구조를 개선한다: `긴 문단 -> bullet -> 표 -> 흐름도 -> 공통 규칙 분리 -> 독립 흐름이면 문서 분리`.
- 최종 문서는 10초 / 30초 / 검색 테스트를 통과해야 한다 (`reference.md`).

## 마무리

1. 상단 메타 작성: `> 코드: <실제 읽은 코드 범위>` / `> 기준 커밋: <HEAD>` / `> 갱신: <오늘>`
2. `INDEX.md` 등록. 실제 읽은 파일 기준 경로, 키워드는 액션과 상태에서 3~5개.
3. `BOARD.md` 갱신 이력에 `신규: <문서>` 기록. `TODO(sync)`가 있으면 할 일에도 등록.
4. 별도 커밋: `docs(<scope>): <도메인> 현행 문서 신규 작성`
5. `deliverable-sync`에서 시작했다면 sync의 후속 단계로 복귀.

## 승격 절차

기존 `*-비즈니스로직-이력.md`, `*-비즈니스로직-정리.md`가 현행 문서 역할을 하면 새로 만들지 않고 승격한다.
`git mv`로 `<로직>-비즈니스로직.md` -> 기존 링크 수정 -> 메타 추가 -> 절 재배치 -> 내용 재해석 금지 -> 마지막 수정 이후 코드 변경 확인 -> 필요 시 `deliverable-sync` -> `INDEX.md` 등록 -> `BOARD.md` 기록 -> 커밋. 실행 흐름이 없으면 현재 코드를 확인해 가장 앞에 추가한다.

## 트리거 규칙

| 상황 | 이어서 실행 |
|---|---|
| `deliverable-sync` 2단계 "신규 문서 후보" | 이 스킬 -> 완료 후 sync 5단계로 복귀 |
| 기존 `docs/`에 현행 문서 성격 파일 존재 | 이 스킬의 승격 절차 |
| 문서 위치, 파일명 판단 | `deliverable-structure` 스킬 |
| Controller/Service/Domain 책임 구분 | `ddd-spring` 스킬 |
| 액션 엔드포인트 규칙(`POST .../confirm`), ErrorCode. "막히는 경우" 표는 ErrorCode와 대응 | `api-design` 스킬 |

## 하지 말 것

- 이모지 사용. 문서 시작을 코드 구조 설명으로 채우기. `Controller -> Service -> Repository`만으로 흐름 설명.
- 서비스 코드를 처음부터 끝까지 읽기. Controller에서 액션을 찾기 전에 내부 구현부터 읽기.
- DTO 필드 전부 나열, 코드 블록 대량 복사, 코드의 줄 단위 한국어 번역, 모든 클래스와 메서드 나열.
- 구현 세부사항을 업무 흐름처럼 보이기. Mapper/Builder/getter를 흐름도에 넣기. 모든 endpoint를 같은 중요도로 다루기.
- Mermaid를 장식으로 쓰기. 같은 내용을 표, Mermaid, 문장으로 반복.
- 코드에 없는 상태나 업무 개념 만들기. 추정한 연결선을 Mermaid에 넣기. "아마", "의도한 것으로 보인다"를 규칙으로 기록.
- 기존 현행 문서를 무시하고 새 문서 만들기. INDEX/BOARD 등록 없이 끝내기. 여러 도메인을 동시에 작성.

## 완료 체크

- [ ] 이모지가 없는가? 가장 먼저 실제 업무 실행 흐름이 보이는가? 흐름도가 코드 호출이 아닌 업무 동작인가?
- [ ] 첫 부분만 보고 시작과 종료, 주요 참여자와 처리 순서를 파악할 수 있는가?
- [ ] 상태 변화가 시각적인가? 주요 액션과 결과가 한눈에 보이는가?
- [ ] 중요한 가드와 실제 예외 메시지, 이력과 알림 발생 시점을 쉽게 찾을 수 있는가?
- [ ] 구현 세부사항이 비즈니스 흐름을 가리지 않는가? 코드에서 확인되지 않은 내용을 사실처럼 적지 않았는가?
- [ ] `TODO(sync)`가 BOARD에 등록되어 있는가? INDEX/BOARD 갱신 후 sync 흐름으로 복귀했는가?

## 관련 스킬

`deliverable-structure`(파일을 어디에 둘지, 파일명 규칙), `deliverable-sync`(이 스킬을 호출하는 쪽, 완료 후 복귀), `ddd-spring`(도메인 경계와 용어), `api-design`/`db-schema-and-migration`/`batch-and-scheduler`(각각 `api/`, `db/`, `batch/` 문서를 남기는 규칙), `rca-procedure`(장애 문서는 별도 형식), `figma-workflow`(FigJam으로 논의한 결과를 문서로 옮길 때 - 문서 다이어그램은 Mermaid 기본).
