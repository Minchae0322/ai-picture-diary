# 외부 API 클라이언트 (external-api-client)

## 목적

외부 호출은 **언젠가 반드시 느려지고 실패한다.** 그 전제 위에서 (1) 클라이언트 선택을 한 가지로 통일하고, (2) 타임아웃·재시도·격리를 기본값으로 강제하고, (3) 외부 장애가 내 트랜잭션과 스레드 풀을 무너뜨리지 않게 하고, (4) 테스트와 로그로 실제 계약을 붙잡아 둔다.

## 언제 적용

결제/PG, 소셜 로그인, 알림(카카오·SMS·푸시), LLM API, 사내 다른 시스템, 공공 API 등 프로세스 밖 HTTP 호출을 추가·변경할 때. 외부 호출 관련 장애(타임아웃, 커넥션 고갈, 응답 포맷 변경) 후에도.

## 0. 클라이언트 선택

- 기본값: **`@HttpExchange` 선언형 인터페이스 + RestClient 어댑터.** 호출 계약이 인터페이스로 드러나고 테스트가 쉽다.
- `RestTemplate` 신규 사용 금지. Spring Framework 7.0에서 deprecation 예고, 7.1 `@Deprecated`, 8.0 제거 예정. 기존 코드는 점진 교체하고 새 코드만 막는다.
- `WebClient`는 폐기된 것이 아니다. 아래 판단표에서 해당하면 쓴다.
- Boot 4에서는 그룹 단위 설정을 쓴다: `@ImportHttpServices(group = "...", basePackages = "...")` + `spring.http.client.service.group.<이름>.base-url` / `.read-timeout`.
- 클라이언트 빈은 **호출 대상 시스템마다 하나**. 타임아웃·커넥션 풀이 다르므로 공용 빈 하나를 돌려쓰지 않는다.

### 동기/비동기 판단 (물어보고 정한다)

| 조건 | 선택 |
|---|---|
| 일반 요청-응답, 응답을 기다려야 다음 단계 진행 | RestClient (동기) |
| 애플리케이션 전체가 리액티브 스택(WebFlux) | WebClient |
| 스트리밍(SSE, 청크 응답), 대량 팬아웃(수십 건 동시 호출) | WebClient |
| 응답이 당장 필요 없다(알림 발송 등) | 동기 클라이언트 + 커밋 후 비동기 실행/큐 |
| 가상 스레드(Java 21+) 사용 중 | RestClient. 블로킹이어도 스레드가 저렴하므로 리액티브로 갈 이유가 줄어든다 |

- "동시 호출이 많아서 비동기"는 **가상 스레드 도입 여부를 먼저 확인**하고 판단한다. 확인 없이 리액티브로 전환하지 않는다.
- 스택 혼용(MVC에 WebClient만 끌어오기)은 가능하지만 `block()`으로 되돌리는 순간 이점이 사라진다. 그럴 거면 RestClient.

## 1. 타임아웃 - 필수값

- **모든 클라이언트에 연결 타임아웃과 읽기 타임아웃을 명시한다.** 기본값(무한 또는 인프라 기본)에 맡기지 않는다. 값 없는 클라이언트는 리뷰에서 BLOCKER.
- 출발점: 연결 1~3초, 읽기 = 상대방 SLA 또는 p99 실측의 2배. 근거 없는 값은 주석에 "잠정, 측정 후 조정"이라고 남긴다.
- 내 API의 응답 시간 예산 안에 들어와야 한다. (내 타임아웃 x 재시도 횟수) < (내 API 타임아웃).
- 커넥션 풀 크기와 풀 대기 타임아웃도 정한다. 풀 고갈은 타임아웃보다 먼저 온다.
- 파일 업로드/다운로드, LLM 스트리밍처럼 긴 호출은 **별도 클라이언트 빈**으로 분리한다.

## 2. 재시도

- **멱등한 요청에만.** GET/PUT/DELETE는 보통 안전, POST는 상대가 멱등성 키를 지원할 때만(`api-design`).
- 재시도 대상: 커넥션 실패, 타임아웃, 429, 5xx. 재시도 금지: 4xx(429 제외), 응답 파싱 실패, 인증 실패.
- 지수 백오프 + 지터, 상한 있는 횟수(2~3회). `Retry-After` 헤더가 오면 그 값을 우선한다.
- 재시도는 **트랜잭션 밖**에서(`transaction-and-concurrency` 8장).
- 상대가 결제처럼 "중복 실행이 치명적"인 경우, 재시도 전에 상태 조회 API로 확인하거나 멱등성 키를 반드시 보낸다.

## 3. 장애 격리

- 서킷 브레이커(Resilience4j) 도입 기준: 호출량이 많고, 상대 장애가 반복 관찰되며, **열렸을 때의 대체 동작(fallback)이 정의되는** 경우. 셋 다 아니면 타임아웃 + 재시도 상한으로 충분하다.
- fallback이 없는 서킷 브레이커는 예외를 다른 예외로 바꾸는 장식일 뿐이다. 도입 전에 "열리면 무엇을 반환하나"를 먼저 정한다.
- 벌크헤드: 한 외부 시스템의 지연이 다른 요청까지 잡아먹지 않도록 커넥션 풀/실행 풀을 분리한다.
- **필수 의존과 선택 의존을 구분한다.** 선택 의존(알림, 추천, 로깅용 외부 호출) 실패는 주 흐름을 실패시키지 않는다.

## 4. 트랜잭션과의 관계

- 트랜잭션 안에서 외부 API를 호출하지 않는다. DB 커넥션을 외부 지연만큼 붙잡는다.
- "DB 저장 + 외부 호출"이 함께 성공해야 하면 트랜잭션으로 묶으려 하지 말고, 상태 컬럼(`PENDING` -> `DONE`) + 커밋 후 호출 + 재처리로 나눈다.
- 외부 호출 예외가 트랜잭션을 롤백시키는지 항상 의식한다. 롤백되면 안 되는 기록은 먼저 커밋한다.
- 상세는 `transaction-and-concurrency` 6장.

## 5. 요청/응답 다루기

- **외부 DTO를 도메인이나 컨트롤러까지 흘리지 않는다.** `infrastructure` 계층에서 우리 모델로 변환한다(`ddd-spring`).
- 응답 DTO는 record + 필요한 필드만. 모르는 필드는 무시하도록 관대하게(`FAIL_ON_UNKNOWN_PROPERTIES` 비활성) 두고, 필수 필드 누락은 명시적으로 실패시킨다.
- 상대의 에러 응답을 우리 `ErrorCode`로 매핑하는 지점을 한 곳에 만든다(`ResponseErrorHandler` 또는 어댑터 메서드). 상대 에러 코드를 그대로 사용자에게 노출하지 않는다.
- 파싱 실패는 "상대가 계약을 바꿨다"는 신호다. 조용히 null로 넘기지 말고 명확한 예외 + 원문 일부 로깅.
- 응답 본문 전체를 로그에 남기지 않는다. 개인정보/카드/토큰이 섞인다(`logging-observability`, `config-and-secrets`).

## 6. 인증 정보

- API 키·시크릿은 코드/설정 파일에 두지 않고 `${ENV}`로만(`config-and-secrets`). 기본값 금지.
- 토큰 갱신이 필요한 경우 갱신 로직을 클라이언트 한 곳에 두고, 동시 갱신이 중복되지 않게 한다.
- 로그·예외 메시지·URL 쿼리스트링에 키가 실리지 않는지 확인한다.

## 7. 캐시

- 잘 안 변하고 호출량이 많은 응답(코드 목록, 환율, 공개 프로필)은 캐시한다. TTL과 무효화 조건을 함께 정한다.
- 캐시 미스가 몰릴 때 외부로 폭주하지 않게(요청 병합 또는 짧은 락) 한다.
- 사용자별 개인 데이터는 기본적으로 캐시하지 않는다. 하려면 키에 사용자 식별자를 반드시 포함한다.

## 8. 테스트

- 외부 호출 코드는 **실제 네트워크 없이** 테스트한다. WireMock(또는 `MockRestServiceServer`)으로 응답을 고정한다.
- 최소 케이스: 정상, 4xx, 5xx, 타임아웃, 잘못된 본문(파싱 실패), 재시도 후 성공. 경계값 규칙은 `test-writing-guide`.
- 상대 API 문서의 예시 응답을 그대로 픽스처로 저장해 두고, 스펙 변경 시 이 파일부터 고친다.
- 운영 자격증명으로 실제 외부 API를 호출하는 테스트를 CI에 넣지 않는다.

## 9. 비용이 드는 API (LLM 등)

**LLM 연동은 `llm-integration` 스킬이 따로 있다.** 이 절은 비용이 드는 외부 API 일반 규칙이고, 프롬프트 관리·구조화 출력·인젝션 방어는 그쪽에 있다.

- 호출당 비용이 있는 API는 **호출 수와 토큰(또는 건수) 상한을 코드에 넣는다.** 무한 루프 한 번이 청구서가 된다.
- 재시도가 비용을 배로 만든다. 상한을 더 낮게 잡는다.
- 요청/응답 크기, 모델명, 소요 시간, 토큰 수를 구조화 로그로 남긴다(`logging-observability`).
- 타임아웃은 스트리밍 여부에 따라 크게 다르다. 스트리밍은 별도 클라이언트로 분리한다.

## 10. 로깅과 관측

- 외부 호출마다 남긴다: `event=external.<시스템>.<동작>`, 대상 시스템, 엔드포인트(경로만), HTTP 상태, 소요 시간, 재시도 횟수, traceId. 형식은 `logging-observability`.
- 요청 본문 전체 대신 식별자만. 응답 본문은 실패 시 앞부분만.
- 상대 시스템별 지연/실패율 대시보드를 만든다. 내 API 지연의 원인이 외부인지 판별하는 최소 조건이다.

## 하지 말 것

- 타임아웃 없는 클라이언트
- 새 코드에 `RestTemplate`
- 트랜잭션 안에서 외부 호출
- 멱등하지 않은 POST를 무조건 재시도
- 상대 DTO를 도메인/응답까지 그대로 노출
- fallback 없는 서킷 브레이커
- 응답 본문 전체 로깅, URL에 API 키
- 실제 외부 API를 때리는 단위 테스트
- 모든 외부 호출을 하나의 공용 클라이언트 빈으로 처리

## 관련 스킬

`transaction-and-concurrency`(트랜잭션 분리, 재시도), `api-design`(멱등성 키, ErrorCode), `config-and-secrets`(API 키), `logging-observability`(외부 호출 로그), `test-writing-guide`(WireMock, 경계값), `ddd-spring`(infrastructure 어댑터), `batch-and-scheduler`(배치에서의 외부 호출), `llm-integration`(LLM 호출), `notification`(FCM·알림톡 발송), `rca-procedure`(외부 원인 판별).
