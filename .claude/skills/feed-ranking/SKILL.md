# 피드 정렬과 추천 (feed-ranking)

## 목적

"비슷한 글을 먼저 보여 주자"는 대부분 **유사도 문제가 아니라 페이징 문제**로 끝난다.
점수 정렬은 사람마다 다르고 시간이 지나면 값이 변해서, 무한 스크롤의 커서를 깨뜨린다.
이 스킬은 (1) 정렬 축을 먼저 쪼개고, (2) 개인화를 커서와 어떻게 공존시키고,
(3) 유사도를 어느 단계까지 올릴지, (4) 무엇이 제품을 망치는지를 정한다.

## 언제 적용

정렬 옵션 추가, "추천" 탭 설계, 관련 게시물 영역, 개인화 피드, 인기 정렬 기준 결정,
유사도 계산 방법 선택, "추천이 이상하다"는 문제.

## 0. 시작 전 확인

| # | 질문 | 답이 바꾸는 것 |
|---|---|---|
| 1 | 정렬 축이 몇 개인가 (정렬 / 필터가 섞여 있지 않은가) | API 파라미터 구조 |
| 2 | 무한 스크롤인가, 페이지 번호인가 | 커서 설계. 개인화 가능 범위 |
| 3 | 개인화의 **재료**가 무엇인가 | 콜드 스타트 처리 |
| 4 | 그 재료가 없는 사용자는 몇 %인가 | 폴백이 주력이 될 수도 있다 |
| 5 | 점수가 결정적인가 (같은 입력 -> 같은 값) | 커서에 점수를 실을 수 있는지 |
| 6 | 비슷한 것만 보면 해로운 도메인인가 | 다양성 주입 필요 여부 |

**3번과 4번을 먼저 답한다.** 재료가 없는 사용자가 절반이면 "추천"은 사실상 폴백 정렬이다.

## 1. 정렬 축을 먼저 쪼갠다

디자인 시안은 정렬과 필터를 **한 줄에 섞어** 놓는 경우가 많다(인기 / 최신 / 맑음 / 비).
축이 다르므로 API에서 나눈다.

- **정렬은 하나**(`sort`). 라디오다. 해제할 수 없다.
- **필터는 여럿**(`filter`). 체크박스다. 0개면 전체.
- 섞어서 하나의 파라미터로 받으면 "인기 + 최신"처럼 뜻이 없는 조합이 생긴다.

정렬 이름은 사용자 언어로, 값은 코드 언어로(`인기` -> `POPULAR`). 화면 문구가 바뀌어도 값은 그대로다.

## 2. 개인화와 커서 페이징의 충돌 - 이 스킬의 핵심

keyset 커서는 **안정적인 정렬 키**를 전제한다(`(id)`, `(likeCount, id)`).
개인화 점수는 사용자마다 다르고 시간이 지나면 변해서 그 전제를 깬다. 셋 중 하나를 고른다.

| 방법 | 어떻게 | 언제 |
|---|---|---|
| **점수를 커서에 싣는다** | 커서 = `(정렬이름, 점수, id)`. 정렬이 바뀌면 커서는 무효 | 점수가 **결정적**일 때. 기본값 |
| **첫 페이지만 개인화** | 상위 N개만 점수 정렬, 이후는 안정 정렬로 이어붙임 | 점수 계산이 비쌀 때 |
| 세션 스냅샷 | 조회 시작 시 순서를 테이블에 굳혀 두고 그걸 페이징 | 점수가 비결정적이거나 랭킹이 외부에서 올 때 |

- **점수를 실을 때는 요청 안에서 기준을 고정한다.** "내 오늘 기분"을 페이지마다 다시 읽으면
  2페이지에서 순서가 바뀌어 같은 글이 두 번 나오거나 사라진다.
- 점수는 **동점이 많다.** 반드시 유일 키를 뒤에 붙인다(`점수 DESC, id DESC`).
- 정렬이 바뀌면 이전 커서는 **400으로 거절**한다. 조용히 무시하면 목록이 뒤섞인다.

> [!IMPORTANT]
> 점수 계산 규칙이 SQL과 애플리케이션 코드 **두 곳에** 생기면(정렬은 DB가, 커서 인코딩은 Java가)
> 언젠가 갈라진다. 한 파일에 나란히 두고, 둘이 같은 답을 내는지 **통합 테스트로 묶는다.**

## 3. 유사도는 사다리다 - 밑에서부터

계산 방법 자체(정규화, 한국어, 임계값, 평가)는 `similarity-search`에 있다. 여기서는 **정렬에 쓸 때의 비용과 순서**만 본다.

| 단계 | 방법 | 비용 | 언제 올라가나 |
|---|---|---|---|
| 1 | **규칙 점수** - 이미 가진 분류·수치의 일치 | 0. DB 변경 없음 | 항상 여기서 시작 |
| 2 | **문자/단어 유사도** - `pg_trgm`, full-text | 인덱스 1개 | 1이 너무 거칠 때 |
| 3 | **임베딩** - pgvector 코사인 거리 | 확장 + 컬럼 + 호출마다 비용 | 1·2의 부족함이 **측정된 뒤** |

- 1단계를 건너뛰지 않는다. 대부분의 "비슷함"은 **이미 분류해 둔 값**(카테고리, 태그, 판정 결과)으로 충분하다.
  특히 그 분류가 이미 AI 판정을 거친 요약이라면, 원문 임베딩보다 **덜 흔들린다.**
- 한국어에서 2단계는 형태소 분석기가 없으면 `pg_trgm`이 현실적이다. full-text는 토크나이저에 좌우된다.
- 3단계는 **글마다 임베딩 호출**이 붙는다. 비용 상한을 먼저 정한다(`llm-integration` 4장).

### RAG가 아니다

유사도 정렬에 RAG를 끌어오지 않는다. RAG는 검색 결과를 **LLM 프롬프트에 넣어 답을 생성**하는
파이프라인이고, 정렬에는 생성이 없다. 필요한 조각은 **임베딩과 벡터 검색 둘뿐**이며
청킹·재순위·컨텍스트 조립·출처 표시는 해당 없다. 3단계로 갈 때 `rag-pipeline`에서 보는 것은
pgvector 스키마와 인덱스 절이다.

## 4. 다양성 - 비슷한 것만 보여 주면 생기는 일

- 유사도만으로 정렬하면 **같은 것만 계속 나온다.** 사용자는 새로운 것을 못 보고, 새 글은 노출되지 않는다.
- **감정·건강·정치처럼 상태를 다루는 도메인에서는 해롭다.** 우울한 사용자에게 우울한 글만 주는 피드는
  기능이 아니라 사고다. 상위 목록에 **다른 상태를 일정 비율 섞는다.**
- 신선도를 점수에 넣는다. 오래된 인기 글이 영원히 1등이면 피드가 죽는다.
- 섞는 비율은 감이 아니라 정한 값으로 두고, 바꿀 수 있게 한다(설정 또는 상수 한 곳).

## 5. 콜드 스타트

- 개인화 재료가 없는 사용자(가입 직후, 오늘 안 쓴 사람)가 **항상 있다.**
- 폴백은 조용히 동작해야 한다. "추천할 게 없어요"는 빈 화면과 같다.
- 폴백이 무엇인지 **API 명세에 적는다.** 앱이 "추천"을 눌렀는데 최신순이 오면 프론트가 혼란스럽다.
- 재료가 생기는 순간 자연히 개인화되면 된다. 별도 온보딩을 만들지 않는다.

## 6. 인기 정렬의 기준

"인기순"은 대부분 정의되지 않은 채 구현된다. 정해서 문서에 적는다.

- **누적 좋아요순**: 가장 단순. 오래된 글이 고정된다. 초기에는 이걸로 충분하다.
- **시간 감쇠**: `점수 / (경과시간 + 2)^중력` 같은 형태. 값을 상수 한 곳에 두고 조정한다.
- 어느 쪽이든 **커서 키가 안정적인지** 확인한다. 시간 감쇠 점수는 시간이 지나면 변하므로
  2장의 "점수를 커서에 싣는다"가 흔들린다 - 감쇠는 시(hour) 단위로 양자화하거나 스냅샷을 쓴다.

## 7. 평가

- 추천은 "좋아 보인다"로 판단하지 않는다. **무엇이 좋아지면 성공인지**를 먼저 정한다
  (첫 화면 클릭률, 스크롤 깊이, 반응률).
- A/B가 없어도 **정렬별 지표는 나눠서** 남긴다. 로그에 `sort` 값을 넣는다.
- 규칙 점수는 단위 테스트로 경계를 고정한다. 순서가 바뀌는 것은 버그가 아니라 사양 변경이다.

## 8. 리뷰 체크

- [ ] 정렬과 필터가 다른 파라미터인가
- [ ] 정렬을 바꿨을 때 이전 커서가 거절되는가
- [ ] 점수 기준이 요청 안에서 고정되는가 (페이지마다 다시 읽지 않는가)
- [ ] 정렬 키 뒤에 유일 키가 붙어 있는가
- [ ] 점수 규칙이 두 곳에 있다면 같은 답을 내는지 테스트가 묶고 있는가
- [ ] 콜드 스타트 폴백이 있고 명세에 적혀 있는가
- [ ] 다양성·신선도가 들어가 있는가. 도메인상 해로운 편향이 없는가
- [ ] 임베딩을 쓴다면 호출 상한이 있는가

## 하지 말 것

- 정렬과 필터를 한 파라미터에 섞기
- 개인화 점수로 정렬하면서 커서 설계를 그대로 두기
- 페이지마다 개인화 기준을 다시 읽기
- 1·2단계를 건너뛰고 바로 임베딩 (측정 없이 비용부터 지불)
- 유사도 정렬에 RAG 파이프라인을 통째로 끌어오기
- 다양성 없이 유사도만으로 정렬 (특히 감정·건강 도메인)
- "인기"의 정의를 코드에만 두고 문서에 안 적기

## 관련 스킬

`similarity-search`(유사도 계산 방법·임계값·평가), `api-design`(커서 페이징과 파라미터 규칙),
`rag-pipeline`(3단계로 갈 때 pgvector 스키마),
`llm-integration`(임베딩 호출 상한), `jpa-query-optimization`(점수 정렬의 인덱스),
`db-schema-and-migration`(정렬용 컬럼·인덱스 추가), `logging-observability`(정렬별 지표).
