# Figma 연동 (figma-workflow)

## 목적

Figma MCP는 **자체 스킬을 14개 제공**하고 그중 여럿은 도구 호출 전 필수 로드다. 그 내용(파라미터, 게이트 절차, 에셋 규칙, Plugin API)을 여기에 복사하면 Figma가 바꿀 때마다 틀린 문서가 된다.

그래서 이 스킬은 **그 위의 층**만 담는다: (1) 어떤 작업에 어떤 figma 스킬을 로드하는지, (2) Figma가 준 결과를 우리 프로젝트 규칙으로 어떻게 바꾸는지, (3) 시안에 없는 것(반응형·상태·접근성)을 어디서 채우는지, (4) 남의 파일을 건드릴 때의 안전 규칙.

## 언제 적용

figma.com 링크를 받았을 때, 시안을 코드로 옮길 때, 코드/화면을 Figma에 그릴 때, Figma 파일을 수정할 때, FigJam에 다이어그램을 그릴 때, 디자인 토큰과 Figma 변수를 맞출 때, Code Connect 매핑.

## 0. 절대 규칙 - 도구 전에 스킬

- **Figma MCP 도구를 부르기 전에 해당 figma-* 스킬을 먼저 로드한다.** 일부는 "MANDATORY prerequisite"로 명시돼 있고, 건너뛰면 디버깅이 어려운 실패가 난다.
- 스킬 목록과 URI는 `skill://index.json`에서 확인한다. 내용은 Figma가 관리하므로 **이 문서에 옮겨 적지 않는다.**
- 이 스킬과 figma-* 스킬이 충돌하면 **도구 사용법은 figma-*, 프로젝트 규칙은 이 스킬**이 우선이다.

## 1. 라우팅

| 하려는 일 | 먼저 로드할 Figma 스킬 |
|---|---|
| 시안을 코드로 구현 (읽기) | `figma-design-to-code` |
| 코드/화면을 Figma에 그리기 | `figma-generate-design` + `figma-use` |
| Figma 파일을 직접 수정(노드, 변수, 컴포넌트) | `figma-use` |
| 디자인 시스템/컴포넌트 라이브러리 구축 | `figma-generate-library` + `figma-use` |
| 새 Figma/FigJam/Slides 파일 생성 | `figma-create-new-file` |
| FigJam 작업 | `figma-use-figjam` (+ `figma-use`) |
| 다이어그램(플로우, 아키텍처, ERD, 시퀀스) | `figma-generate-diagram` |
| Figma 컴포넌트 ↔ 코드 컴포넌트 매핑 | `figma-code-connect` |
| 애니메이션을 코드로 | `figma-implement-motion` |
| iOS/SwiftUI 양방향 | `figma-swiftui` |

- 여러 개가 걸리면 전부 로드한다. 쓰기 작업은 대부분 `figma-use`가 함께 필요하다.
- 목록은 바뀔 수 있다. 표에 없는 작업이면 `skill://index.json`을 먼저 읽는다.

## 2. 방향 판단 - 무엇이 진실인가

| 상황 | 방향 | 진실의 원천 |
|---|---|---|
| 디자이너가 시안을 줬다 | Figma -> 코드 | Figma (단, 3장의 보정 필요) |
| 코드가 먼저 있고 디자인 파일이 없다 | 코드 -> Figma | 코드 |
| 둘 다 있고 어긋난다 | **먼저 물어본다** | 정하지 않고 덮어쓰지 않는다 |
| 아이디어 단계, 화면이 아직 없다 | Figma에서 시작 | Figma |

- **양방향을 동시에 열어두지 않는다.** 코드와 Figma를 서로 덮어쓰면 어느 쪽도 믿을 수 없게 된다. 기능 단위로 한 방향을 정하고 문서에 적는다.
- 어긋난 것을 발견하면 조용히 맞추지 말고 **무엇이 어긋났는지 먼저 보고**한다.

## 3. 가져오기 (Figma -> 코드)

Figma가 돌려주는 코드는 **참고 자료다.** 우리 프로젝트 규칙으로 바꿔야 완성이다.

- 반환 코드(React + Tailwind)를 그대로 붙여넣지 않는다. 프로젝트의 프레임워크·컴포넌트·스타일 체계로 옮긴다(`frontend-architecture`).
- **이미 있는 컴포넌트를 먼저 찾는다.** `shared/ui/`에 Button이 있는데 시안에서 새 Button을 만들지 않는다.
- 색·간격·라운드는 **우리 토큰으로 매핑**한다(`design-system`). `#3b6ef6`을 그대로 쓰지 않고 `--color-primary`로. 시안 값이 토큰에 없으면 토큰에 추가할지, 가장 가까운 토큰을 쓸지 판단하고 그 판단을 남긴다.
- 절대 좌표(`position: absolute`, 고정 px)는 그대로 옮기지 않는다. flex/grid로 재구성한다.

### 시안에 없는 것 - 반드시 채운다

시안은 보통 **한 화면 폭의 정상 상태 하나**다. 아래는 시안에 없으니 물어보거나 규칙으로 채운다.

- **반응형**: 시안이 데스크톱 하나뿐이면 좁은 폭 동작이 정의되지 않은 것이다(`ui-fundamentals` 11장). 주 타깃을 확인하고(`design-system` 3장) 브레이크포인트 동작을 정한다.
- **상태 5종**: hover / focus-visible / active / disabled가 시안에 거의 없다. `ui-fundamentals` 9장으로 채운다. **focus 표시는 시안에 없어도 반드시 넣는다.**
- **로딩 / 빈 상태 / 에러**: 정상 화면만 있으면 나머지 셋이 빠진 것이다(`ui-fundamentals` 13장).
- **대비**: 시안이 접근성을 보장하지 않는다. 본문 4.5:1 / UI 3:1을 **직접 계산**한다. 미달이면 구현 전에 알린다.
- **다크 모드**: 라이트 시안만 있으면 다크는 토큰 재정의로 만든다(`design-system` 4장).
- **긴 텍스트 / 빈 값 / 최대 개수**: 시안의 예쁜 더미 데이터는 경계값이 아니다.

## 4. 토큰 동기화

- 토큰의 진실은 **한쪽만**이다. 보통 코드의 `tokens.css`(`design-system`). Figma 변수는 거기서 파생된다.
- 디자이너가 Figma 변수를 주도하는 팀이면 반대로 정하고, 어느 쪽이든 **문서에 한 줄 적는다**. 정하지 않으면 양쪽이 조금씩 다른 값으로 갈라진다.
- 이름을 맞춘다. Figma 변수 `color/primary`와 CSS `--color-primary`가 같은 것을 가리켜야 매핑이 자동이 된다.
- 토큰을 동기화할 때 **의미 단계(2단계)만** 맞춘다. 원시 색상표까지 양쪽에 두면 관리가 두 배가 된다.

## 5. 그리기와 수정 (코드 -> Figma)

쓰기는 되돌리기 어렵다. 읽기보다 조심한다.

- **남의 파일을 고치기 전에 확인한다.** 디자이너가 작업 중인 파일에 쓰면 그 사람의 작업을 덮을 수 있다. 새 파일이나 새 페이지/프레임에 그리는 것이 기본이다.
- 기존 노드를 **삭제하거나 대체하지 않는다.** 추가하고, 교체가 필요하면 무엇을 교체할지 먼저 말한다.
- 컴포넌트 **인스턴스를 직접 수정하지 않는다.** 메인 컴포넌트를 고치거나 변형(variant)을 추가한다.
- 하드코딩 값 대신 **기존 변수/스타일/컴포넌트를 찾아 쓴다.** 디자인 시스템이 있는 파일에 값을 박아 넣으면 시스템이 무너진다(`figma-generate-design`이 이 탐색 절차를 담고 있다).
- 큰 화면은 한 번에 만들지 않고 **섹션 단위로 나눠 확인받으며** 진행한다.
- 작업 전 상태를 알 수 있게 한다(스크린샷 또는 변경 요약). 되돌릴 근거가 된다.

## 6. Code Connect

- 같은 컴포넌트를 반복해서 옮기고 있으면 **Code Connect로 매핑**한다. 이후 `get_design_context`가 우리 컴포넌트를 바로 알려준다.
- 매핑 대상은 `shared/ui/`의 공용 컴포넌트다. feature 전용 컴포넌트는 매핑하지 않는다(`frontend-architecture` 1장).
- 컴포넌트 props와 Figma 변형(variant)의 이름을 맞춰 두면 매핑이 단순해진다.

## 7. FigJam 다이어그램

- 아키텍처·플로우·ERD·시퀀스는 FigJam으로 그릴 수 있다. 다만 **문서에 남길 다이어그램은 Mermaid가 기본**이다(`deliverable-write`) - 코드 리뷰에서 diff가 보이고 저장소 안에 남는다.
- FigJam은 **같이 보면서 논의할 때**(설계 회의, 브레인스토밍) 쓴다. 결론은 문서로 옮긴다.
- FigJam 링크만 남기고 문서를 안 쓰면 6개월 뒤 아무도 못 찾는다.

## 8. 리뷰 체크

- Figma 반환 코드를 그대로 붙여넣지 않았는가, 기존 컴포넌트를 재사용했는가
- 색·간격이 토큰으로 매핑됐는가, 하드코딩 hex가 남았는가
- 절대 좌표가 flex/grid로 재구성됐는가
- 반응형·상태 5종·로딩/빈/에러가 채워졌는가
- 대비를 계산했는가
- (쓰기) 남의 작업 파일에 직접 쓰지 않았는가, 삭제·인스턴스 수정이 없는가
- 토큰 동기화 방향이 문서에 정해져 있는가

## 하지 말 것

- figma-* 스킬 로드 없이 Figma 도구 호출
- Figma 스킬 내용을 이 저장소에 복사해 두기 (곧 어긋난다)
- 반환 코드 그대로 사용, 하드코딩 hex와 절대 좌표 유지
- 시안에 없다는 이유로 focus 표시·에러 화면·반응형 생략
- 시안이 대비 미달인데 그대로 구현
- 디자이너 작업 파일에 확인 없이 쓰기, 노드 삭제, 인스턴스 직접 수정
- 코드와 Figma를 양방향으로 동시에 덮어쓰기
- FigJam 링크만 남기고 문서 생략

## 관련 스킬

`design-system`(토큰 - 매핑의 기준), `ui-fundamentals`(시안에 없는 것을 채우는 규칙), `frontend-architecture`(가져온 코드를 어디에 어떤 모양으로), `frontend-state`(시안에 없는 로딩/에러 상태 처리), `app-store-release`(모바일 화면 규격), `deliverable-write`(다이어그램은 Mermaid 기본).
