# 파일 업로드와 저장소 (file-upload-storage)

## 목적

업로드는 조용히 시스템을 망가뜨린다. **서버 메모리로 큰 파일이 올라오고, 검증 없이 저장되고, DB와 스토리지가 어긋나고, 지운 줄 알았던 파일이 남는다.** 이 스킬은 업로드 경로를 하나로 정하고, 검증·정리·권한을 기본값으로 둔다.

## 언제 적용

프로필 사진·첨부파일·문서 업로드 추가, 스토리지 선택, 이미지 리사이즈/썸네일, 다운로드 엔드포인트, "파일이 안 지워진다"·"용량이 계속 는다"·"업로드가 타임아웃 난다" 문제.

## 이 스킬 폴더의 파일

| 파일 | 용도 | 복사 위치 |
|---|---|---|
| `templates/file-schema.sql` | 파일 메타 테이블 DDL (상태, 해시, 고아 정리용 컬럼) | `sql/patch/` |
| `templates/StorageProperties.java` | 버킷·상한·허용 타입 설정 record | `infrastructure/storage/` |

## 0. 업로드 경로 선택

| 방식 | 언제 | 주의 |
|---|---|---|
| **presigned URL 직접 업로드** (기본) | 이미지·문서 등 대부분 | 서버는 URL 발급과 완료 통보만 처리. 서버 대역폭·메모리를 안 쓴다 |
| 서버 경유(`MultipartFile`) | 업로드 즉시 서버가 내용을 봐야 할 때(파싱, 변환, 엄격한 검증) | 파일 크기 상한을 반드시 설정. 메모리가 아니라 임시 파일로 |
| 청크/재개 업로드 | 수백 MB 이상, 모바일 네트워크 | 복잡도가 크다. 필요한 게 확인되면 |

- **기본은 presigned URL이다.** 서버 경유를 고르려면 "왜 서버가 내용을 봐야 하는가"에 답할 수 있어야 한다.
- 서버 경유라면 `spring.servlet.multipart.max-file-size`와 `max-request-size`를 반드시 설정한다. 기본값에 맡기면 서버가 죽는다.
- 저장소는 S3 호환(AWS S3, Cloudflare R2, MinIO) 중 하나. **로컬 파일시스템은 단일 인스턴스에서만** 성립한다 - 인스턴스가 늘면 파일이 반만 보인다.

## 1. 업로드 흐름 (presigned)

```
1. 클라이언트 -> 서버: 업로드 요청(파일명, 크기, MIME)
2. 서버: 검증(2장) -> 파일 메타 INSERT(status=PENDING) -> presigned PUT URL 발급 -> 반환
3. 클라이언트 -> 스토리지: 직접 PUT
4. 클라이언트 -> 서버: 완료 통보(fileId)
5. 서버: 스토리지에 실제 존재·크기·타입 확인 -> status=READY -> 후속 처리(썸네일 등)
```

- **5번의 실제 존재 확인을 생략하지 않는다.** 클라이언트 말만 믿으면 없는 파일이 READY가 된다.
- 4번 완료 통보에 `Idempotency-Key`를 붙인다. 재시도로 후속 처리가 두 번 돌지 않게(`api-design` 10장).
- presigned URL 유효기간은 짧게(5~15분). 업로드 크기 상한과 Content-Type을 URL 발급 시 조건으로 건다.
- 업로드된 파일을 **비즈니스 엔티티에 연결하는 것은 별도 단계**다. 게시글 저장 시 `fileId`를 참조한다. 연결되지 않은 파일은 고아(5장).

## 2. 검증

- **확장자를 믿지 않는다.** 파일 시그니처(매직 넘버)로 실제 타입을 확인한다. `.jpg`로 올라온 실행 파일이 흔한 공격이다.
- 허용 타입은 **화이트리스트**로. "이건 막자"가 아니라 "이것만 허용".
- 크기 상한을 타입별로 둔다(프로필 이미지 5MB, 문서 20MB 같은 식). presigned URL 조건과 서버 검증 양쪽에.
- 파일명은 **그대로 쓰지 않는다.** 저장은 UUID 기반, 원본 파일명은 메타로만 보관. 경로 조작(`../`), 널 바이트, 제어문자, 과도한 길이가 전부 파일명으로 들어온다.
- SVG는 스크립트를 품을 수 있다. 이미지로 받되 별도 호스트/다운로드 전용으로 제공하거나 sanitize한다.
- 압축 파일을 서버에서 풀지 않는다. 풀어야 한다면 압축 해제 후 크기와 엔트리 수 상한을 건다(zip bomb).
- 바이러스 검사가 필요한 성격이면(사용자끼리 파일을 주고받는 서비스) 업로드 후 비동기 검사 -> 통과 전까지 다운로드 차단.

## 3. 저장 경로와 파일명

- 경로 규칙을 한곳에 정의한다: `<용도>/<yyyy>/<MM>/<dd>/<uuid>.<ext>`. 날짜 계층이 있으면 정리·수명주기 정책이 쉽다.
- 사용자 식별자를 경로에 넣지 않는다(URL로 유추 가능). 필요하면 해시.
- 원본과 파생물은 **다른 키**에 둔다: `<용도>/origin/<날짜>/<uuid>.<ext>`, `<용도>/<변형>/<날짜>/<uuid>.webp`. 변형 키는 원본 키에서 규칙으로 유도되게 한다(prefix만 교체).
- 버킷은 환경별로 분리한다(dev/prod). 같은 버킷에 prefix만 다르게 쓰면 실수로 운영 파일을 지운다.

## 4. 원본과 파생물 (이미지)

- **원본은 업로드된 그대로 보존하고 절대 덮어쓰지 않는다.** 썸네일은 원본을 축소해 만든 **별개의 파일**이며, 원본 자리에 덮어쓰거나 원본을 리사이즈된 것으로 교체하지 않는다.
- 파생물은 **원본에서 다시 만들 수 있는 캐시**로 취급한다. 지워져도 재생성하면 되고 크기 정책이 바뀌면 배치로 다시 만든다. 원본이 없으면 이 전부가 불가능하다.
- 변형 종류를 **용도별로 미리 정의**한다(예: `thumb` 목록용 짧은 변 256, `medium` 상세용 1024, `origin` 원본). 화면마다 즉석에서 크기를 정하지 않는다.
- 축소만 한다. **원본보다 큰 변형을 만들지 않는다**(확대는 화질만 나빠지고 용량은 는다). 원본이 이미 작으면 그 변형은 건너뛰고 원본을 쓴다.
- 비율은 유지한다. 잘라내기(crop)가 필요하면 변형 정의에 방식(중앙/스마트)을 명시한다. 변형 포맷은 WebP처럼 압축률 높은 것으로 통일해도 된다(원본 포맷은 원본에만).
- 변형은 **업로드 직후 비동기**로 생성한다. 동기로 하면 업로드 응답이 느려진다. 생성 전에는 원본이나 플레이스홀더를 보여준다.
- EXIF를 제거한다. **위치 정보가 그대로 노출된다.** 회전(Orientation)은 적용한 뒤 제거. 원본을 외부에 그대로 내려주는 경로가 있으면 그쪽도 걸러야 한다.
- 원본 보관은 기본 on. 보관하면 용량이 몇 배가 되지만 **안 하면 새 변형을 영원히 못 만든다.**
- 이미지 디코딩은 메모리를 많이 쓴다. 픽셀 수 상한(예: 1억 픽셀)을 두어 decompression bomb을 막는다.
- 변형이 3종을 넘거나 크기가 자주 바뀌면 미리 만들지 말고 **요청 시 생성 + CDN 캐시**(이미지 서비스)로 간다. 미리 만든 파일이 쓰이지 않고 쌓이는 것이 더 비싸다.

## 5. 고아 파일과 삭제

- **PENDING 상태로 남은 파일**(발급했는데 업로드 안 됨, 업로드했는데 연결 안 됨)을 정리하는 배치를 만든다. 없으면 용량이 단조 증가한다(`batch-and-scheduler`).
- 삭제는 **소프트 삭제 먼저, 실제 삭제는 유예 후.** 사용자가 지운 파일을 바로 지우면 복구 요청에 답할 수 없다. `deleted_at` 후 N일 뒤 배치가 실제 삭제(`db-schema-and-migration` 2장).
- DB 삭제와 스토리지 삭제를 한 트랜잭션으로 묶을 수 없다. **DB를 먼저 표시하고 스토리지는 배치가 정리한다.** 반대로 하면 스토리지는 지워졌는데 DB에 남는다(`transaction-and-concurrency` 6장).
- 스토리지 수명주기 규칙(lifecycle)으로 임시 prefix를 자동 만료시키면 배치가 줄어든다.
- 엔티티가 삭제되면 첨부 파일도 삭제 대상으로 표시한다. 연결이 끊긴 채 남지 않게.

## 6. 접근 권한과 다운로드

- **버킷을 공개로 두지 않는다.** 공개해도 되는 것(공지 이미지)과 아닌 것(개인 문서)을 같은 버킷에 두면 실수가 난다.
- 비공개 파일은 **presigned GET URL**을 짧은 유효기간으로 발급한다. 발급 시점에 권한을 검사한다.
- 서버 스트리밍 다운로드는 권한 검사가 쉽지만 서버 대역폭을 쓴다. 큰 파일은 presigned로.
- `Content-Disposition`으로 파일명을 지정한다. 한글 파일명은 RFC 5987 인코딩(`filename*=UTF-8''...`).
- 업로드된 HTML/SVG를 같은 도메인에서 서빙하지 않는다. 별도 도메인이나 다운로드 전용 헤더로.
- 다운로드 로그(누가 언제 무엇을)를 남길지 정한다. 개인 문서를 다루면 보통 필요하다.

## 7. 설정과 운영

- 버킷명, 리전, 액세스 키는 전부 환경변수로(`config-and-secrets`). 키는 기본값 없이.
- 가능하면 액세스 키 대신 IAM 역할/워크로드 아이덴티티를 쓴다. 키가 없으면 유출도 없다.
- 스토리지 비용은 조용히 는다. 용량·요청 수 메트릭을 대시보드에 올린다.
- 업로드 실패율과 평균 업로드 시간을 본다. 모바일에서만 실패하면 크기나 타임아웃 문제다.

## 8. 리뷰 체크

- presigned인가 서버 경유인가, 서버 경유면 크기 상한이 설정돼 있는가
- 파일 시그니처 검증과 타입 화이트리스트가 있는가
- 저장 파일명이 UUID인가, 원본 파일명을 경로에 쓰지 않는가
- 완료 통보 시 스토리지 실제 존재를 확인하는가
- PENDING 정리 배치와 삭제 유예 정책이 있는가
- 비공개 파일이 공개 URL로 나가지 않는가
- 원본을 보존하고 변형을 별도 키에 만드는가, 변형만 지워도 재생성되는가
- 원본보다 큰 변형을 만들지 않는가
- EXIF 제거와 픽셀 수 상한이 있는가

## 하지 말 것

- `MultipartFile`을 메모리에 통째로, 크기 상한 없이
- 확장자만 보고 타입 판단
- 원본 파일명을 그대로 저장 경로에 사용
- 버킷 전체 공개
- DB 삭제와 스토리지 삭제를 한 트랜잭션으로 묶으려 하기
- 고아 파일 정리 배치 없이 운영
- **원본을 리사이즈 결과로 덮어쓰기**, 원본 없이 썸네일만 보관
- 원본보다 큰 변형 생성, 화면마다 즉석에서 크기 정하기
- EXIF 그대로 보관(위치 정보 노출)
- 업로드 직후 동기 이미지 변환
- 액세스 키를 코드나 설정 파일에

## 관련 스킬

`api-design`(업로드 API 형태, 멱등성 키), `frontend-api-client`(클라이언트 업로드, 진행률), `db-schema-and-migration`(파일 메타 테이블, 소프트 삭제), `batch-and-scheduler`(고아 정리, 실제 삭제 배치), `config-and-secrets`(버킷·키 설정), `transaction-and-concurrency`(커밋 후 스토리지 작업), `rag-pipeline`(업로드 문서를 색인할 때), `app-store-release`(앱의 사진 권한 고지).
