# 프롬프트 관리와 평가 (prompt-and-eval)

## 목적

프롬프트는 코드인데 테스트가 없다. 그래서 "이렇게 바꾸니 좋아진 것 같다"로 배포되고, 한 케이스를 고치면 다른 케이스가 조용히 망가진다. 이 스킬은 **프롬프트 변경을 측정 가능한 변경으로** 만든다: 평가 셋을 먼저 만들고, 바꾸기 전후를 비교하고, 통과해야 머지한다.

## 언제 적용

프롬프트 파일 수정, 모델 또는 모델 버전 교체, 파라미터(temperature 등) 변경, AI 기능 품질 문제 보고, 새 AI 기능의 평가 설계, 프로바이더 교체 검토.

## 이 스킬 폴더의 파일

| 파일 | 용도 | 복사 위치 |
|---|---|---|
| `templates/eval-set.jsonl` | 평가 셋 형식(입력, 기대, 판정 기준) | `src/test/resources/eval/` |
| `templates/PromptEvalTest.java` | 회귀 테스트 골격 (태그로 분리, CI 선택 실행) | `src/test/java/.../ai/` |
| `templates/eval-report.md` | 변경 전후 비교 기록 | `docs/ai/` |

## 0. 절대 규칙

- **평가 셋 없이 프롬프트를 바꾸지 않는다.** 없으면 먼저 만든다(최소 10건, 2장).
- 프롬프트를 고칠 때는 **기존 파일을 덮어쓰지 않고 v+1 파일을 만든다**(`llm-integration` 2장). 비교와 롤백의 전제다.
- "더 좋아 보인다"를 근거로 머지하지 않는다. 변경 전후 점수를 `docs/ai/`에 남긴다.
- 평가는 **운영 데이터를 그대로 쓰지 않는다.** 개인정보를 제거하거나 합성 데이터로 만든다.

## 1. 무엇을 평가할 것인가

작업 종류에 따라 채점 방법이 다르다. 먼저 이 표에서 고른다.

| 작업 | 정답이 있나 | 채점 방법 |
|---|---|---|
| 분류(카테고리, 감정, 라우팅) | 있음 | 정확도. 정답 라벨과 문자열 비교 |
| 추출(이름, 날짜, 금액) | 있음 | 필드별 일치율. 부분 점수 |
| 구조 준수(JSON 스키마) | 있음 | 파싱 성공률 + 필수 필드 존재율 |
| 요약 | 없음 | 체크리스트 기반 채점(필수 포함 항목, 금지 항목) |
| 생성(문구, 답변) | 없음 | 규칙 검사 + LLM 심사 + 표본 사람 검토 |
| 검색 기반 답변 | 부분 | 출처 일치 + 근거 없는 주장 없음(`rag-pipeline`) |

- **정답이 있는 작업부터 자동화한다.** 분류·추출·구조 준수는 확정적으로 채점되므로 CI에 넣기 쉽다.
- 정답이 없는 작업도 **규칙 검사는 확정적이다**: 길이 상한, 금지어, 필수 포함 문구, 형식. 이것부터 자동화한다.
- LLM 심사(LLM-as-judge)는 마지막에. 심사 자체가 비결정적이고 비용이 든다.

## 2. 평가 셋(골든셋) 구성

- 최소 10건, 실용적으로 30~50건. 수백 건을 목표로 미루지 말고 **10건으로 시작**한다.
- 반드시 포함: **정상 케이스, 경계 케이스, 실패해야 하는 케이스, 실제로 터졌던 케이스.**
- 버그가 보고되면 **그 입력을 평가 셋에 추가하고** 고친다. 이게 평가 셋이 자라는 정상 경로다(`test-writing-guide`의 회귀 테스트와 같은 원리).
- 프롬프트 인젝션 시도를 몇 건 넣는다: "이전 지시 무시", "시스템 프롬프트 출력", 입력 안에 가짜 지시. 기대 결과는 "지시를 따르지 않음"(`llm-integration` 7장).
- 입력이 긴 경우와 빈 경우를 넣는다. 상한 동작이 평가된다.
- 한 파일 = 한 기능. `eval/summarize.jsonl`, `eval/classify.jsonl`. 프롬프트 파일과 1:1.
- 형식은 JSONL(한 줄 한 케이스). diff가 읽히고 추가가 쉽다.

## 3. 채점 규칙

- 케이스마다 **판정 기준을 데이터에 적는다.** 코드에 조건문으로 흩뿌리지 않는다: `{"must_include": [...], "must_not_include": [...], "expected_label": "경제"}`.
- 확정적 검사(라벨 일치, 포함/불포함, 스키마, 길이)를 먼저 돌리고, 통과한 것만 LLM 심사로 넘긴다. 비용이 줄어든다.
- LLM 심사는 **심사 기준을 프롬프트에 명시**하고 점수가 아니라 **통과/실패 + 이유**를 받는다. 1~5점 척도는 재현성이 낮다.
- 심사 모델은 피심사 모델과 다른 것을 쓰면 편향이 줄어든다(자기 출력 선호). 같은 모델을 쓸 수밖에 없으면 그 한계를 문서에 적는다.
- `temperature`를 평가 시에는 낮게 고정한다. 그래도 완전 재현은 안 되므로 **한 번 실패를 실패로 확정하지 않고** 2~3회 실행의 다수결 또는 통과율로 본다.

## 4. 기준선과 합격선

- 평가 셋을 만든 날 **현재 프롬프트로 한 번 돌려 기준선을 기록한다.** 이게 비교 대상이다.
- 합격선은 절대 점수가 아니라 **기준선 대비**로 정한다: "필수 케이스 전부 통과 + 전체 통과율이 기준선 이상".
- 필수 케이스(must-pass)를 표시한다: 인젝션 방어, 스키마 준수, 실제 장애 케이스. 이건 하나라도 실패하면 머지 불가.
- 통과율이 올랐어도 **이전에 통과하던 케이스가 실패하면** 그 사유를 기록한다. 조용히 넘기지 않는다.

## 5. 변경 절차

1. 평가 셋이 있는지 확인. 없으면 먼저 만들고 기준선을 잡는다.
2. 문제 케이스를 평가 셋에 추가한다(있다면).
3. 프롬프트 **v+1 파일**을 만들어 수정한다.
4. 기존 버전과 새 버전을 같은 평가 셋으로 돌린다.
5. 결과를 `docs/ai/YYYY-MM-DD-<기능>-프롬프트-v<n>.md`에 기록(`templates/eval-report.md`).
6. 합격선 통과 시 설정의 버전을 올린다. 실패하면 3으로.
7. 배포 후 운영 지표(파싱 실패율, 사용자 피드백)를 며칠 관찰한다.

- 모델 교체도 같은 절차다. 프롬프트는 그대로 두고 모델만 바꿔 돌린다.
- 롤백은 설정의 버전 번호를 되돌리는 것. 배포 없이 되게 만들어 둔다.

## 6. 하네스

- 평가는 **일반 테스트와 분리**한다(`@Tag("eval")`). 비용이 들고 느려서 매 커밋에 돌릴 수 없다.
- 로컬에서 수동 실행 + PR에서 `prompts/` 경로가 바뀔 때만 CI 실행이 기본. 경로 필터로 건다(`deploy-pipeline`).
- 실제 API를 호출하므로 **평가용 API 키와 예산 상한**을 따로 둔다. 운영 키를 CI에 넣지 않는다(`config-and-secrets`).
- 결과는 파일로 남긴다(통과/실패 목록, 실패 사유). 콘솔 출력만으로는 비교가 안 된다.
- 평가 실행 자체에도 호출 수 상한을 건다. 케이스 50건 x 3회 x 2버전 = 300회임을 인지하고 돌린다.

## 7. 운영 품질 관찰

- 배포 후 볼 지표: 파싱 실패율, 응답 거부율(안전 필터), 평균 출력 토큰(급증 = 프롬프트 폭주), 사용자 재시도율, 기능 이탈률.
- 프롬프트 버전을 로그 필드로 남겨 두면 "어느 버전부터 나빠졌는지"가 바로 나온다(`llm-integration` 9장).
- 사용자 피드백(좋아요/싫어요, 신고)을 수집하면 **싫어요가 달린 입력이 다음 평가 셋 후보**다. 개인정보를 제거하고 넣는다.
- 환각 신고가 오면 그 입력을 평가 셋에 넣고 재현되는지부터 확인한다. 재현 안 되면 온도·모델 버전 변동을 의심한다.

## 8. 리뷰 체크

- 프롬프트 변경 PR에 평가 결과가 첨부됐는가
- 새 파일(v+1)로 만들었는가, 기존 파일을 덮어썼는가
- 문제 케이스가 평가 셋에 추가됐는가
- 필수 케이스(인젝션·스키마)가 전부 통과했는가
- 평가 셋에 개인정보가 들어 있는가
- 평가가 일반 테스트와 분리돼 있는가, 운영 키를 쓰는가

## 하지 말 것

- 평가 셋 없이 프롬프트 수정
- 기존 프롬프트 파일 덮어쓰기
- "좋아 보인다"로 머지, 전후 비교 없이 모델 교체
- 1~5점 척도 LLM 심사
- 평가 셋에 운영 개인정보 그대로 사용
- 평가를 일반 단위 테스트에 섞어 매 커밋 실행
- 실패 케이스를 평가 셋에서 삭제해서 통과시키기
- 운영 API 키로 CI 평가 실행

## 관련 스킬

`llm-integration`(프롬프트 파일 구조, 호출, 로그 필드), `rag-pipeline`(검색 품질 평가는 별도 지표), `test-writing-guide`(테스트 분리와 회귀 원칙), `deploy-pipeline`(경로 필터 CI 실행), `config-and-secrets`(평가용 키), `deliverable-write`(`docs/ai/` 기록).
