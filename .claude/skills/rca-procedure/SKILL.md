# 장애 원인 분석(RCA) 절차

## 목적

장애가 났을 때 **복구 -> 증거 보존 -> 원인 특정 -> 재발 방지** 순서로 움직이고, 남이 읽어도 재현 가능한 보고서로 남긴다.
핵심 원칙: (1) 복구가 분석보다 먼저다, (2) 가설은 증거로 확정한다, (3) 사람이 아니라 시스템을 고친다(blameless).

## 언제 적용

서비스 다운/응답 지연/오류율 급증/데이터 오류 신고, 알림(로그 ERROR 급증, 헬스체크 실패, 노드 NotReady 등), 사후 "왜 그랬는지" 보고서, RCA 에이전트/자동 분석 결과 검증.

> 장애 보고서의 **문체**(개조식, 시각 표기, 사실과 추정의 구분)는 `report-style`.

## 절차

### 0단계. 분류 (1분)
- 영향 범위: 전체 / 일부 기능 / 일부 사용자. 사용자 체감이 있는가.
- 심각도: `SEV1` 핵심 기능 중단, `SEV2` 일부 기능 장애/심한 지연, `SEV3` 제한적 영향, `SEV4` 내부 영향만.
- 담당자와 소통 채널을 정하고 시작 시각 기록. 이후 모든 행동은 시각과 함께 기록.

### 1단계. 복구 우선 (완화)
- "무엇이 바뀌었나"를 가장 먼저 묻는다. 최근 배포, 설정 변경, 인프라 작업, 트래픽 변화, 외부 시스템 변경.
- 변경이 의심되면 **롤백** 먼저. 원인 분석은 롤백 후.
- 롤백 대상이 없으면 완화책: 재시작, 스케일 아웃, 기능 플래그 끄기, 문제 노드 격리, 트래픽 차단.
- 완화 조치 전에 **증거 보존**(2단계). 최소한 스레드 덤프(`jcmd <pid> Thread.print`)와 힙 히스토그램(`jcmd <pid> GC.class_histogram`)은 뜨기 전에 받는다. 단, 보존이 복구를 몇 분 이상 지연시키면 복구를 택한다.

### 2단계. 증거 수집
장애 시간대 **전후 15분**을 함께 본다.
- 로그: ERROR/WARN 급증 시점, 최초 오류 메시지, 스택 트레이스 전체, traceId.
- 트레이스: 느려진 span 위치(DB, 외부 API, 내부 처리). 부모 span 느림 + 자식 빠름 = 커넥션 풀 대기, 락 대기, GC 의심.
- 메트릭: CPU, 메모리, GC pause, 스레드 수, HTTP 요청 수/오류율/지연시간(p50/p95/p99), DB 커넥션 풀 active/pending, 큐 적체(Kafka lag).
- 인프라: 노드/파드 상태(`kubectl get events --sort-by=.lastTimestamp`, `kubectl describe`), OOMKilled, 디스크, 네트워크.
- DB: 슬로우 쿼리 로그, 락 대기(`pg_locks`, `pg_stat_activity`), 커넥션 수, 복제 지연.
- 외부: 의존 서비스 상태 페이지, 인증서 만료, DNS. 변경 이력: 배포 로그, 설정 커밋, 인프라 변경 티켓.
- 타임라인은 **UTC 또는 KST 중 하나로 통일**.

### 3단계. 타임라인 작성
- 수집한 것을 시각순으로 적는다(예시는 `reference.md`). "가장 먼저 이상해진 지표"가 출발점이다.

### 4단계. 가설 수립과 검증
- 원인 가설을 2~3개 세운다. 하나만 세우면 확증 편향.
- 각 가설에 "맞다면 반드시 보여야 하는 증거"를 적고 확인한다.
- 5 Whys로 근본 원인까지. "쿼리가 느렸다"에서 멈추지 않는다(예시는 `reference.md`).
- 가능하면 **재현**한다. 재현이 안 되면 "유력 원인(추정)"으로 표기하고 확정이라고 쓰지 않는다.

### 5단계. 자주 보는 원인 패턴 (스프링/JVM/K8s)

| 증상 | 확인할 것 |
|---|---|
| 응답 지연 후 타임아웃 폭증 | HikariCP pending, 슬로우 쿼리, 외부 API 타임아웃 미설정 |
| 메모리 계속 증가 후 OOM | 힙 덤프 분석(MAT), 캐시 무제한 증가, 컬렉션 정적 보관, 대량 조회 결과 적재 |
| CPU 100% + 응답 없음 | 스레드 덤프에서 RUNNABLE 스레드 스택, 무한 루프, 정규식 백트래킹, GC 스레드 |
| 간헐적 지연(수 초) | GC 로그 Full GC, 커넥션 재연결, DNS 재조회 |
| 특정 요청만 실패 | 요청 파라미터 특이값, 인코딩, 데이터 특정 행 |
| 배포 직후 장애 | 설정 누락, 스키마 불일치, 빈 초기화 순서, 프로파일 오류 |
| 파드 재시작 반복 | OOMKilled(limit 대비 -Xmx), liveness probe 타임아웃, 초기화 시간 초과 |
| 노드 NotReady | kubelet 로그, 디스크/메모리 압박(DiskPressure/MemoryPressure), 네트워크 플러그인 |
| Kafka lag 증가 | 컨슈머 처리 시간, 리밸런스 반복, 파티션 수 대비 컨슈머 수 |
| 데드락/락 대기 | `pg_locks`, 트랜잭션 안 외부 호출, 갱신 순서 불일치 |

### 6단계. 재발 방지와 보고서
- 재발 방지는 세 층: **탐지**(알림/대시보드), **완화**(타임아웃, 서킷 브레이커, 리소스 제한, 자동 롤백), **예방**(코드 수정, 테스트 추가, 리뷰 체크리스트, 파이프라인 게이트).
- 각 조치에 담당자와 기한. 없으면 실행되지 않는다.
- 보고서는 `reference.md` 템플릿(요약 / 영향 / 타임라인 / 원인 / 잘 된 점·아쉬운 점 / 재발 방지 조치 / 미확인 사항).

## RCA 에이전트/자동 분석 결과를 검증할 때

- 제시한 원인이 **타임라인상 가장 먼저 이상해진 지표**와 일치하는가. 결과 증상을 원인으로 짚는 경우가 많다.
- 인용한 로그/트레이스가 실제로 존재하는지 원본에서 대조.
- "확정"과 "추정"이 구분되어 있는가. 구분이 없으면 전부 추정으로 취급.
- 재현 없이 확정된 결론은 보고서에 "추정"으로 적는다.

## 하지 말 것

- 원인 분석하느라 복구를 미루는 것.
- 재시작 먼저 하고 나서 "로그가 없다"고 하는 것. 최소 증거는 먼저 뜬다.
- 첫 번째 가설을 확인 없이 원인으로 적는 것.
- "개발자 실수"를 근본 원인으로 쓰는 것. 실수를 통과시킨 절차가 근본 원인이다.
- 재발 방지 조치에 담당자와 기한을 안 붙이는 것.
- 시간대가 섞인 타임라인.

관련: `logging-observability`(이 절차가 읽는 로그를 미리 남기는 규칙), `transaction-and-concurrency`(락 대기·데드락·갱신 손실 증상의 원인과 대책), `external-api-client`(외부 시스템이 원인일 때), `db-schema-and-migration`(스키마 원인. 조사용 SQL도 실행하지 않고 사람에게 넘긴다).
