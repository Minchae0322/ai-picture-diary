# DB를 PostgreSQL에서 MySQL로 바꾼다

> 2026-10-14 · 상태: 승인 · 결정자: minchae

## 배경

프로젝트 스킬 4장(확정 사항)은 백엔드를 `Spring Boot 3.5 / Java 21 / PostgreSQL`로 적어 두었고,
`sql/patch/*.sql` 4개와 엔티티 매핑이 모두 PostgreSQL 전용 기능 위에 있었다.

- 시퀀스(`CREATE SEQUENCE` + `nextval`)와 `@SequenceGenerator(allocationSize = 50)`
- 부분 인덱스(`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`) - 소프트 삭제와 하루 1건 규칙의 근거
- `timestamptz`, `COMMENT ON`, `UPDATE ... FROM`, `ALTER INDEX ... RENAME`

운영 환경을 MySQL로 맞추기로 해서 이 전제가 바뀌었다. 확정 사항을 바꾸는 결정이라 ADR을 먼저 쓴다.

바꾸기 좋은 시점이다: `sql/patch/*.sql` 4개는 **아직 어느 환경에서도 실행되지 않았다**
(각 `docs/db/*.md`의 실행 기록이 전부 "미실행"). 데이터 이관이 없다.

## 선택지

1. **PostgreSQL 유지** - 부분 인덱스와 시퀀스를 그대로 쓴다. 바꿀 코드가 없다.
   단점: 운영 환경과 다르다. 다른 DB에서 처음 뜨는 날 스키마 전체를 다시 검증해야 한다.
2. **MySQL 8.0으로 전환** - 패치 4개를 MySQL 방언으로 다시 쓰고, ID 생성 전략과 드라이버를 바꾼다.
   단점: 부분 인덱스가 없어 "살아 있는 행만 unique"를 우회 수단으로 만들어야 한다.
   시퀀스가 없어 `allocationSize = 50`의 쓰기 배치 이점을 잃는다.
3. **방언 중립 스키마**(둘 다 되는 공통 분모만 쓰기) - 부분 인덱스를 포기하고 애플리케이션 검사로 대체.
   단점: 하루 1건·중복 좋아요·중복 공유를 DB가 보장하지 못한다. 경쟁 상태가 그대로 남는다.
   불변 규칙("DB 제약으로 강제한다")을 포기하는 쪽이라 받아들일 수 없다.

## 결정

**2번.** MySQL 8.0으로 간다. 데이터가 없는 지금이 가장 싸다.

DB가 보장하던 것은 하나도 애플리케이션으로 내리지 않는다. 부분 인덱스만 수단을 바꾼다.

| 잃은 것 | 대체 수단 |
|---|---|
| 부분 unique 인덱스 | `alive` 생성 컬럼(`IF(deleted_at IS NULL, 1, NULL)` STORED)을 unique 키 뒤에 끼운다. MySQL은 NULL을 중복으로 보지 않아 삭제된 행끼리는 겹칠 수 있고, 살아 있는 행은 1로 모여 유일해진다 |
| 부분 비유일 인덱스 | 조건 없는 일반 인덱스. 소프트 삭제 행이 섞여도 `@SQLRestriction("deleted_at IS NULL")`이 걸러낸다. 삭제 비율이 높아지면 그때 다시 본다 |
| 시퀀스 + `allocationSize = 50` | `AUTO_INCREMENT` + `GenerationType.IDENTITY` |
| `timestamptz` | `datetime(6)` + `hibernate.jdbc.time_zone: UTC` (저장은 계속 UTC) |

`alive`는 애플리케이션이 매핑하지 않는다. `ddl-auto: validate`는 매핑된 컬럼만 보기 때문에
DB에만 있는 컬럼은 기동을 막지 않는다.

## 결과

- 바뀐 것: `sql/patch/*.sql` 4개(제자리에서 다시 씀), 엔티티 7개의 ID 생성 전략,
  `@SQLDelete`의 `now()` -> `now(6)`, 드라이버(`mysql-connector-j`), Testcontainers 이미지(`mysql:8.4`),
  `application-local.yml`·`.env.example`의 접속 URL.
- 바뀌지 않은 것: JPQL 7개(방언 중립), 응답 계약, 도메인 규칙, 커서 페이징 키.
- 감수하는 것:
  - **쓰기 배치 이점 상실.** `IDENTITY`는 insert마다 생성 키를 받아야 해서 Hibernate가 insert를 묶지 않는다.
    하루 1건짜리 쓰기 양에서는 문제가 아니다. 대량 입력이 생기면 그때 다시 본다.
  - **인덱스에 삭제된 행이 남는다.** 지금은 소프트 삭제가 드물어 무시할 수 있다.
  - **검증이 아직 코드 수준이다.** `./gradlew test` 74건은 통과했지만 `validate`와 DDL 실행은
    MySQL 8.0이 떠 있어야 확인된다(`./gradlew integrationTest`, Docker 필요). 아래 "되돌릴 조건" 참고.
- 되돌릴 조건: MySQL에서 `ddl-auto: validate`가 매핑 불일치로 기동을 막고 그 원인이 방언 차이로
  풀리지 않을 때. 데이터가 쌓이기 전까지는 되돌리는 비용이 이 결정과 같다.
- 확정 사항 표(프로젝트 스킬 4장)와 `README.md`·`docs/guide/개발-가이드.md`를 같이 고쳤다.
