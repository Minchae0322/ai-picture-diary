# ADR: 오늘의 기분을 필수로, 본문 상한을 200자로

- 날짜: 2026-10-20
- 상태: 채택
- 범위: 02 홈(기록 전), `POST /api/v1/diaries`, `app.diary.max-content-length`

## 배경

02 홈은 지금까지 **본문만 필수**였다. 빠른 감정 칩은 보조 힌트였고 고르지 않아도 기록이 됐다.
본문 상한은 1~500자였다.

두 가지가 걸렸다.

1. **고르지 않으면 AI 가 참고할 것이 문장 하나뿐이다.** 같은 문장도 쓴 사람의 기분에 따라 다른 날이다
   ("오늘 회식했다"가 즐거운 날일 수도 지친 날일 수도 있다). 칩을 선택사항으로 두면 대부분 건너뛴다 -
   안 눌러도 되는 버튼은 안 눌린다.
2. **500자는 이 제품의 글이 아니다.** 홈 화면의 약속은 "하루 한 줄"이다. 상한이 500이면 화면은
   한 줄 입력창인데 상한은 에세이라 둘이 어긋나고, 긴 글일수록 감정이 여러 개 섞여 9종 판정이 흐려진다.

## 결정

1. **오늘의 기분(`userHint`)을 쓰기의 필수 입력으로 올린다.** 고르지 않으면 기록되지 않는다.
2. **본문 상한을 200자로 내린다.** `app.diary.max-content-length: 200`.

## 그래도 바뀌지 않는 것

- **고른 기분이 AI 판정을 대체하지는 않는다.** 결과 화면의 감정은 여전히 서버가 정한 `Diary.emotion`
  이고 `userHint` 와 다를 수 있다. 필수가 된 것은 "입력"이지 "정답"이 아니다.
- 감정 세기(`EmotionGauge`)는 **보내지 않았다.** 받을 필드가 API 에 없었고,
  그래서 2026-10-25 에 UI 째로 걷어냈다 - 고르고 나면 버려지는 입력이었다.
- DB 컬럼 `tb_diary.content` 는 varchar(500) 그대로다. 업무 상한과 컬럼 길이는 다른 값이고,
  업무 상한만 설정에서 내린다 - 스키마를 건드리지 않으므로 마이그레이션이 없다.
- `tb_diary.user_hint` 도 nullable 그대로다. 필수가 되기 전에 쓰인 행이 남아 있고,
  그 과거를 지우려고 DDL 을 바꿀 이유는 없다. 강제는 도메인(`Diary.write`)과 요청 검증이 한다.

## 거절은 어느 코드로 나가나

사유가 둘이면 코드도 둘이다(`api-design` 3장).

| 상황 | 코드 | HTTP |
|---|---|---|
| 요청에 `userHint` 필드가 없다 | `COMMON_INVALID_REQUEST` + `errors[0].field = "userHint"` | 400 |
| 도메인에 null 이 들어왔다 | `DIARY_EMOTION_REQUIRED` | 400 |
| 본문이 비었거나 201자 이상 | `COMMON_INVALID_REQUEST` | 400 |

`DIARY_EMOTION_REQUIRED` 를 따로 둔 이유는 앱이 "기분을 먼저 골라 주세요"로 안내할 근거를 잃지 않기 위해서다.
본문 길이 위반과 같은 코드로 뭉개면 앱은 무엇을 가리켜야 할지 모른다.

## 화면이 달라지는 지점

- 02 가 **두 단계**를 드러낸다. 1 오늘의 기분 -> 2 오늘 한 줄. 각 단계 머리에 번호 동그라미가 있고
  끝낸 단계는 체크로 바뀐다.
- "기록" 버튼이 알약 입력창 안에서 나와 **화면 아래 큰 버튼("오늘 그리기")**이 된다.
  비활성일 때는 바로 아래에 **무엇이 비었는지** 한 줄로 쓴다 - 흐린 버튼만 두면 고장으로 읽힌다.
- 쓰는 자리는 알약 입력창이 아니라 **괘선이 그어진 공책 한 장**(`NotePaper`)이다.
  200자는 한 줄이 아니라 몇 줄이고, 몇 줄을 받는 자리는 줄이 그어진 종이로 보여야 한다.

## 버린 대안

- **칩을 그대로 선택사항으로 두고 AI 쪽을 개선한다**: 문장만으로 판정을 더 잘하게 만드는 쪽.
  실모델이 붙기 전까지 확인할 방법이 없고, 모델이 좋아져도 "쓴 사람이 느낀 기분"을 대신 알 수는 없다.
- **고른 기분을 그대로 결과로 쓴다**(AI 판정 생략): 그러면 이 앱은 그림만 그리는 앱이 된다.
  판정이 제품의 절반이다.
- **상한을 300~500 사이로 절충**: 숫자의 문제가 아니라 화면의 약속과 맞는지의 문제라 어중간한 값은
  둘 다 아니게 된다. 200자는 한국어로 대여섯 줄이고, 화면의 공책 일곱 줄과 맞는다.


## 이후 (2026-10-25) - 기본값이 생겨 이 결정이 약해졌다

02 를 그림일기 한 장으로 다시 짜면서 **기분에 기본값(`HAPPY`)이 생겼고 해제되지 않는다.**

이 ADR 의 근거는 "안 눌러도 되는 버튼은 안 눌린다"였다. 기본값을 두면 **손대지 않은 사람은
전부 `HAPPY` 로 기록된다** - 고르게 하려던 목적이 사라진다. 서버는 여전히 `userHint` 를 요구하므로
막는 장치가 없어지는 것이 아니라 **늘 충족되는 것**이다(`DIARY_EMOTION_REQUIRED` 는 이제 앱에서
발생하지 않는다).

본문 상한 200자는 그대로다.

**이 항목은 결정이 아니라 기록이다.** 기본값을 유지하려면 이 ADR 을 대체하는 ADR 을 쓰고,
되돌리려면 `DiaryComposer` 의 `DEFAULT_EMOTION` 을 지우고 `hint` 를 nullable 로 되돌린다.
