# 로그인 없이 쓰는 게스트 모드와 로그인 벽

> 2026-10-20 · 상태: 승인 · 결정자: minchae

## 배경

프로젝트 스킬 4장(확정 사항)은 인증을 "없음. `X-User-Id` 헤더 임시"로 적어 두었다.
핵심 루프를 먼저 만들기 위한 선택이었고, 그 결과 앱의 모든 사람이 `EXPO_PUBLIC_DEV_USER_ID=1`
한 사람으로 서버에 들어온다.

`docs/screen/11-login.md` 7장은 **"비회원 체험과의 관계. 01에서 바로 들어온 사람이 나중에 계정을
붙이면 기록을 어떻게 잇는지"** 를 미정으로 남겨 두었다. 이 ADR이 그 자리를 정한다.

정하려는 것은 넷이다.

1. 로그인하지 않은 사람의 일기를 어디에 두는가
2. 비로그인 상태의 AI 호출을 무엇으로 막는가 (호출마다 돈이 나간다)
3. 어디부터 로그인을 요구하는가
4. 그 벽을 어떻게 보여 주는가

## 선택지

1. **전부 로그인 뒤로.** 지금 많은 앱이 하는 방식. 데이터가 깔끔하고 비용이 통제된다.
   단점: 이 제품의 가치("한 줄 쓰면 그림이 나온다")를 쓰기도 전에 계정부터 만들라고 요구한다.
   첫 경험이 로그인 화면인 일기 앱은 설치 직후에 지워진다.
2. **기기 게스트 계정.** 앱이 기기마다 UUID를 만들어 서버에 한 번 등록하고, 서버가 그 기기에
   사용자 번호를 발급한다. 그 뒤는 지금과 똑같다 - 일기도 캘린더도 그래프도 서버에 쌓인다.
   나중에 로그인하면 그 사용자 번호에 소셜 계정을 연결하므로 기록이 저절로 이어진다.
   단점: 서버에 주인 없는 데이터가 쌓인다. 기기를 잃으면 되찾을 길이 없다(로그인 전까지).
3. **기기에만 저장.** 일기를 앱 저장소에 두고 서버는 AI 생성만 해 준다.
   단점: 캘린더·그래프·연속 기록·뱃지를 앱에서 다시 계산해야 한다. 연속 기록은
   **서버 한 곳에서 계산한다**가 불변 규칙이라(프로젝트 스킬 3장) 같은 계산이 두 벌이 된다.
   앱을 지우면 기록이 사라지고, 로그인 시 병합 규칙(같은 날짜 충돌)을 새로 만들어야 한다.

## 결정

### 1. 2번(기기 게스트 계정)으로 간다

서버 구조를 하나도 바꾸지 않는 쪽이다. 캘린더·그래프·뱃지·연속 기록이 지금 코드 그대로 돌고,
로그인 시 병합 규칙이 **필요 없다** - 애초에 같은 사용자 번호이기 때문이다.

- 앱이 기기에서 UUID v4 를 만들어 `expo-secure-store` 에 둔다. `AsyncStorage` 는 평문이라 쓰지 않는다.
- `POST /api/v1/guest/devices` 로 한 번 등록하고 사용자 번호를 받는다. 그 뒤 모든 요청은 지금처럼
  `X-User-Id` 로 그 번호를 보낸다. **서버의 다른 API 는 게스트인지 아닌지 신경 쓰지 않는다.**
- 인증이 붙는 날 `tb_user` 가 생기고 `tb_guest_device.user_id` 가 그것을 가리키게 바뀐다.
  오늘은 `tb_guest_device.id` 가 곧 사용자 번호다.

**기기 UUID 는 개인정보로 다룬다.** 로그에 남기지 않고(`logging-observability`), 서버는 원문 대신
SHA-256 해시로 저장한다. 유출돼도 그 값으로 남의 기록을 열 수 없게 하려는 것이 아니라
(그건 인증이 할 일이다) 한 번 샌 값이 영구 식별자가 되지 않게 하려는 것이다.

### 2. 비로그인은 하루 AI 생성 2회

| 상태 | 하루 AI 호출 | 근거 |
|---|---|---|
| 게스트 | **2회** (최초 1 + 다시 그리기 1) | `app.diary.guest-daily-generate-limit` |
| 로그인 | 4회 (최초 1 + 다시 그리기 3) | 기존 `app.diary.daily-regenerate-limit` |

- **일기 건수는 그대로 하루 1건이다.** "하루 2건"은 그림을 그리는 횟수이지 일기 수가 아니다.
  하루 1건은 DB unique 인덱스(`user_id, entry_date, alive`)가 강제하는 불변 규칙이고,
  캘린더의 하루 한 칸과 05·06 집계 전체가 그 위에 서 있다.
- 상한에 걸렸을 때의 사유가 로그인 사용자와 다르므로 **`ErrorCode` 도 따로 둔다.**
  같은 코드로 뭉개면 앱이 "로그인하면 더 그릴 수 있어요"를 띄울 근거를 잃는다.
- **광고를 보면 횟수를 더 주는 것은 다음 라운드다.** 결정은 여기 적어 두되 지금 구현하지 않는다:
  리워드 광고 SDK 는 Expo Go 에서 돌지 않아 개발 빌드가 필요하고(`app-store-release`),
  광고 식별자는 iOS 추적 동의(ATT)와 개인정보처리방침 갱신을 함께 끌고 온다.
  그때까지 상한 문구는 광고를 약속하지 않는다 - 되는 척하지 않는다.

### 2-1. 게스트인지 아닌지는 **프로필이 들고 있다** (2026-10-20 보강)

처음에는 `tb_guest_device` 에 행이 있는지로 판단했다. **그 설계에는 결함이 있었다** - 위에서 정한 대로
로그인해도 사용자 번호가 바뀌지 않으므로 기기 행이 그대로 남고, 그러면 그 사람은 영원히 게스트로 읽힌다.

권한을 계정 쪽(`tb_profile.role` = `GUEST` | `MEMBER`)에 두면 승격이 **필드 하나를 바꾸는 일**이 된다
(`Profile.promote()`). 프로필이 자리인 이유는 그것이 이미 사용자 테이블을 겸하고 있어서다.
`tb_guest_device` 는 "기기 -> 사용자" 매핑만 맡는다.

- 프로필이 아직 없으면 **게스트로 본다.** 아무 화면도 열어 보지 않았다는 뜻이라 사실에 가깝다
- 이 판정은 읽기 경로(일기 조회)에서도 불리므로 **프로필을 만들지 않는다**

### 2-2. 상한은 저장소가 지워지면 리셋된다 (알고 받아들이는 한계)

기기 식별자가 사라지면 새 번호가 생기고 그날의 상한도 처음으로 돌아간다. 플랫폼마다 다르다.

| 플랫폼 | 저장소 | 언제 사라지나 |
|---|---|---|
| iOS | 키체인 | **앱을 지워도 남는다.** 기기 초기화에서만 사라진다 |
| 안드로이드 | `SharedPreferences` + KeyStore | **앱 데이터 삭제·앱 제거**로 사라진다. "캐시 삭제"로는 지워지지 않는다 |

- 지금은 `MockDiaryPainter` 라 호출 비용이 0 이어서 받아들인다
- **실모델이 붙는 날에는 기기 식별자만으로 막을 수 없다.** 그때는 서버 전체의 일일 호출 상한이
  따로 필요하다(`llm-integration` 상한 규칙). 기기별 상한은 그 위의 보조 수단이다

### 3. 로그인 벽은 네 곳

| 화면 | 로그인 | 이유 |
|---|---|---|
| 02 홈 · 03 생성 · 04 결과 · 05 캘린더 · 06 그래프 | 필요 없음 | 내 기록이다. 이것이 제품의 핵심 루프다 |
| 07 뱃지 | **필요** | 수집품은 계정에 묶인다 |
| 08 커뮤니티 | **필요** | 남에게 보이는 자리. 신고·차단의 대상이 되려면 계정이 있어야 한다 |
| 09 상점·구독 | **필요** | 결제가 붙는 자리. 계정이 없으면 복원이 불가능하다 |
| 10 마이페이지 | **필요** | 프로필·설정·계정 |

### 4. 벽은 시트로 띄운다

탭은 그대로 열리고 그 위에 로그인 시트가 올라온다. 뒤에 무엇이 있는지 보이므로 로그인할 이유가
생긴다. 닫으면 홈으로 돌아간다. 탭 자체를 잠그면 제품이 닫혀 보이고, 로그인 화면으로 밀어내면
맥락이 끊긴다.

**인증이 아직 없으므로 시트에는 "그냥 둘러보기"가 함께 있다.** 이것이 없으면 커뮤니티·상점·뱃지·
마이페이지가 통째로 죽는다 - 통과할 수단이 없는 벽이기 때문이다. 11 로그인 화면이 "인증이 아직
붙지 않았어요"를 솔직히 말하는 것과 같은 처지이고, **인증이 붙는 날 지울 임시 통로**다.

## 결과

- 새로 생기는 것: `tb_guest_device` 테이블, `tb_profile.role` 컬럼, `POST /api/v1/guest/devices`,
  `ErrorCode.DIARY_GUEST_GENERATE_LIMIT`, 앱의 게스트 식별자 보관(`expo-secure-store`),
  로그인 시트와 탭 가드
- 바뀌는 것: `EXPO_PUBLIC_DEV_USER_ID` 가 **개발용 탈출구로 물러난다.** 값이 있으면 그 번호를 쓰고,
  없으면 기기 등록으로 받은 번호를 쓴다. 로컬에서 남의 데이터를 흉내 내던 길을 막지는 않는다
- 바뀌지 않는 것: 일기 하루 1건, 연속 기록 서버 계산, 봉투 응답, 커서 페이징, 나머지 API 전부
- **되돌리기**: 게스트 발급 API 와 앱의 가드를 끄면 끝이다. 데이터는 남아도 해가 없다
  (사용자 번호는 어차피 필요하다). 테이블만 남는다
