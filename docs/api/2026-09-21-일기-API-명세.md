# 일기 API 명세 (핵심 루프 02→03→04)

> 2026-09-21 · 프론트 전달용 · 코드 기준 `api/src/main/java/com/jellydiary/diary`
> 화면 05~10(캘린더·그래프·뱃지·커뮤니티·프로필)은 `2026-09-22-화면05-10-API-명세.md`

## 공통

- Base URL: `http://<host>:8080`
- 인증: **아직 없음.** 임시로 `X-User-Id: <사용자 ID>` 헤더 필수. 없으면 401 `COMMON_UNAUTHORIZED`.
  (`spring-auth` 적용 시 `Authorization: Bearer`로 교체되며 이 헤더는 삭제된다)
- **사용자 번호는 기기 등록으로 받는다**(ADR [게스트 모드](../adr/2026-10-20-로그인-없이-쓰는-게스트-모드.md)).
  아래 `POST /api/v1/guest/devices` 가 유일하게 헤더 없이 부르는 엔드포인트다.
- 성공 봉투: `{ "data": ..., "meta": { "traceId": "..." } }`
- 실패 봉투: `{ "error": { "code", "message", "errors?" }, "meta": { "traceId" } }`
- 날짜: `entryDate`는 `YYYY-MM-DD`. "오늘"의 기준은 서버의 Asia/Seoul 자정.
- ID는 문자열로 내려간다.
- 목록은 커서 페이징. `meta.nextCursor`가 null이면 끝.

### 에러 코드

| code | HTTP | 언제 |
|---|---|---|
| `COMMON_INVALID_REQUEST` | 400 | 본문 누락·201자 이상, `userHint` 누락 등 검증 실패. `errors[]` 동봉 |
| `COMMON_UNAUTHORIZED` | 401 | `X-User-Id` 없음 |
| `COMMON_LOGIN_REQUIRED` | 403 | 게스트로는 할 수 없는 일. 누구인지는 알지만 계정이 없다 |
| `COMMON_INVALID_CURSOR` | 400 | 커서 형식 오류 |
| `DIARY_EMOTION_REQUIRED` | 400 | 오늘의 기분(`userHint`) 없이 기록. `errors[]` 를 거치지 않고 도메인이 던진 경우다 |
| `DIARY_NOT_FOUND` | 404 | 없거나 남의 일기 |
| `DIARY_ALREADY_EXISTS` | 409 | 오늘 기록이 이미 있음 |
| `DIARY_NOT_DONE` | 422 | 아직 그리는 중이라 다시 그릴 수 없음 |
| `DIARY_REGENERATE_LIMIT` | 422 | 재생성 상한(3회) 초과 |
| `DIARY_GUEST_GENERATE_LIMIT` | 422 | **게스트**의 하루 생성 상한(2회) 초과. 사유가 위와 달라 코드도 다르다 - 앱은 이 코드에서 로그인 시트를 띄운다 |
| `COMMON_INTERNAL_ERROR` | 500 | 그 외 |

### 공통 타입

```ts
type Emotion =
  | 'HAPPY' | 'ENERGETIC' | 'SOSO'
  | 'SHY' | 'EMBARRASSED' | 'TIRED'
  | 'SAD' | 'DEPRESSED' | 'ANGRY';
type DiaryStatus = 'GENERATING' | 'DONE' | 'FAILED';
```

`moodScore`는 -3 ~ +3 정수. `status`가 `GENERATING`이면 `emotion`·`moodScore`·`aiComment`·`imageUrl`은 전부 null이다.

## 0. 기기 등록 (로그인 전)

`POST /api/v1/guest/devices` - **`X-User-Id` 없이** 부른다. 번호를 받으러 가는 자리다.

```ts
// 요청
{ "deviceUuid": "8f14e45f-ea8d-4c1b-9f2a-1d0c0b7a5e31" }  // 기기가 만든 UUID. 8~100자

// 200 응답
{ "data": { "userId": "12", "registered": true }, "meta": { "traceId": "..." } }
```

- **멱등이다.** 같은 기기가 다시 부르면 같은 `userId` 와 `registered: false` 를 돌려준다.
  그래서 201 이 아니라 200 이다 - 두 번째 호출은 아무것도 만들지 않는다.
- 앱은 받은 번호를 기기에 저장하고(`expo-secure-store`) 그 뒤 모든 요청의 `X-User-Id` 로 보낸다.
- 서버는 UUID 원문을 저장하지 않는다. SHA-256 만 둔다(ADR 1번).
- 400 `COMMON_INVALID_REQUEST`: `deviceUuid` 가 비었거나 길이를 벗어남.
`DONE`인데 `imageUrl`만 null이면 **그림 생성만 실패한 것**이며 화면은 텍스트 결과를 보여준다.

## POST /api/v1/diaries - 오늘 기록 (02 → 03)

| 요청 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `content` | string(1~200) | O | 오늘의 한 줄 |
| `userHint` | Emotion | **O** | 02 에서 고른 오늘의 기분 |

- **`userHint` 는 필수다**(ADR [기분 선택 필수와 본문 200자](../adr/2026-10-20-기분-선택-필수와-본문-200자.md)).
  빠지면 400 - 요청에 필드 자체가 없으면 `COMMON_INVALID_REQUEST` + `errors[0].field = "userHint"`,
  형식은 맞는데 값이 없으면 도메인이 `DIARY_EMOTION_REQUIRED` 로 거절한다.
- 필수가 됐어도 **AI 판정을 대체하지는 않는다.** 결과의 `emotion` 은 서버가 정하며 `userHint` 와 다를 수 있다.
- 길이 상한은 `app.diary.max-content-length`(200)다. DB 컬럼은 여전히 500 이라 201~500자는
  컬럼 검증(`@Size`)이 아니라 도메인이 `COMMON_INVALID_REQUEST` 로 막는다.

성공 **201** + `Location: /api/v1/diaries/{id}`

```json
{ "data": { "id": "12", "status": "GENERATING" }, "meta": { "traceId": "..." } }
```

```bash
curl -X POST http://localhost:8080/api/v1/diaries \
  -H 'Content-Type: application/json' -H 'X-User-Id: 1' \
  -d '{"content":"오늘 팀 회의가 잘 끝나서 마음이 가볍다","userHint":"HAPPY"}'
```

에러: 409 `DIARY_ALREADY_EXISTS`, 400 `COMMON_INVALID_REQUEST`, 400 `DIARY_EMOTION_REQUIRED`

## GET /api/v1/diaries/{id} - 상세 / 생성 폴링 (03, 04)

성공 **200**

```json
{
  "data": {
    "id": "12",
    "entryDate": "2026-08-24",
    "content": "오늘 팀 회의가 잘 끝나서 마음이 가볍다",
    "status": "DONE",
    "emotion": "HAPPY",
    "moodScore": 2,
    "aiComment": "AI 코멘트 · 성취감이 느껴지는 하루였네요.",
    "imageUrl": "https://.../600/600",
    "canRegenerate": true
  },
  "meta": { "traceId": "..." }
}
```

폴링: `status`가 `GENERATING`인 동안 1초 간격. `DONE`/`FAILED`가 되면 멈춘다.
에러: 404 `DIARY_NOT_FOUND` (남의 일기도 404)

| 쿼리 | 기본 | 설명 |
|---|---|---|

## POST /api/v1/diaries/{id}/regenerate - 다시 그리기 (04)

바디 없음. 성공 **200** `{ "id": "12", "status": "GENERATING" }`

에러는 사유마다 다른 코드다 - 앱이 문구를 골라야 한다.

| 상황 | 코드 | 문구 |
|---|---|---|
| 아직 그리는 중 | 422 `DIARY_NOT_DONE` | "아직 그림을 그리는 중이에요." |
| 오늘 3회를 다 씀 | 422 `DIARY_REGENERATE_LIMIT` | "오늘은 더 다시 그릴 수 없어요." |
| **게스트가 하루 2회를 다 씀** | 422 `DIARY_GUEST_GENERATE_LIMIT` | "오늘 그릴 수 있는 횟수를 다 썼어요. 로그인하면 더 그릴 수 있어요." |
| 없거나 남의 일기 | 404 `DIARY_NOT_FOUND` | - |

게스트의 2회에는 **최초 생성이 이미 들어 있다.** 그래서 다시 그리기는 1회뿐이다.
`canRegenerate` 도 그 기준으로 내려간다 - 앱이 횟수를 세지 않는다.

## DELETE /api/v1/diaries/{id} - 오늘 기록 지우기 (04 "다시 쓰기")

바디 없음. 성공 **204** (본문 없음).

04 에서 글부터 다시 쓰려고 누르는 자리다. **소프트 삭제**라 행은 남고 `deleted_at` 만 채워진다.
하루 1건 unique 인덱스가 `alive` 생성 컬럼을 끼고 있어 지워진 행은 키에서 빠지므로,
같은 날 새로 쓸 수 있다.

| 상황 | 코드 | 문구 |
|---|---|---|
| 없거나 남의 일기 | 404 `DIARY_NOT_FOUND` | - |

**지우기 자체에는 상한이 없다.** 비용은 AI 호출에서 나오고 지우기는 공짜라, 막아야 하는 것은
지우기가 아니라 그리기다. 그래서 앱의 "다시 쓰기" 버튼은 늘 눌리고, 검사는 다시 쓴 글을
**실제로 그릴 때**(`POST /api/v1/diaries`) 한다.

### 생성 횟수는 지워도 이어진다

`POST /api/v1/diaries` 는 같은 날 **이미 쓴 생성 횟수를 이어받는다**(소프트 삭제된 행까지 센다).
이월하지 않으면 지우기만 반복해 하루 상한을 무한히 우회할 수 있다.

| 상황 | 코드 | 문구 |
|---|---|---|
| 오늘 상한을 이미 다 씀 | 422 `DIARY_REGENERATE_LIMIT` | "오늘은 더 다시 그릴 수 없어요." |
| **게스트**가 다 씀 | 422 `DIARY_GUEST_GENERATE_LIMIT` | "오늘 그릴 수 있는 횟수를 다 썼어요. 로그인하면 더 그릴 수 있어요." |

하루에 그릴 수 있는 총 횟수는 **상한 + 1**이다(처음 1회 + 다시 그리기 상한 회).
