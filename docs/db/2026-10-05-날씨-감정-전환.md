# 2026-10-05 날씨 6종을 감정 9종으로

> 2026-10-05 · DB 변경 · SQL `sql/patch/2026-10-05-날씨-감정-전환.sql`
> 선행: `2026-09-22-커뮤니티-추천정렬.sql`
> 2026-10-19 **MySQL 8.0** 으로 다시 썼다 - 아직 실행 전이라 SQL 파일을 제자리에서 고쳤다 (ADR [DB를 MySQL로](../adr/2026-10-14-DB를-MySQL로.md))

## 무엇을

| 대상 | 변경 |
|---|---|
| `tb_diary.weather` | -> `emotion` 으로 이름 변경 + 값 변환 + 주석 교체 |
| `tb_diary.user_hint` | 이름 유지. 같은 enum 을 담으므로 값만 변환 |
| `tb_community_post.weather` | -> `emotion` 으로 이름 변경 + 값 변환 + 주석 교체 |
| `ix_community_post_weather_id_desc` | -> `ix_community_post_emotion_id_desc` |
| `tb_badge.metric` | `SUNNY_RECORDS`/`RAIN_RECORDS`/`ALL_WEATHERS` -> `HAPPY_RECORDS`/`SAD_RECORDS`/`ALL_EMOTIONS` |
| `tb_badge.name` / `condition_text` | 날씨 어휘로 쓴 3건을 감정 어휘로. **`code` 는 바꾸지 않는다** |

테이블·컬럼의 추가나 삭제는 없다. 전부 이름 변경과 값 변환이다.

## 왜

감정을 날씨로 표현하면 은유를 한 겹 더 거친다 - "오늘 구름조금"이 무슨 기분인지 사람마다 다르게 읽는다.
그리고 6칸이 좁았다. 화남·황당함·부끄러움이 들어갈 자리가 없어 비와 흐림에 뭉쳐 있었다.

감정 9종은 그대로 감정이고 과일 캐릭터 그림이 각각을 나른다.
표현의 근거는 `app/src/shared/emotion.ts` 와 `docs/screen/prototype.html` 에 있다.

### 값 대응

| 옛 날씨 | 새 감정 |
|---|---|
| `SUNNY` | `HAPPY` |
| `PARTLY_CLOUDY` | `SOSO` |
| `CLOUDY` | `TIRED` |
| `RAIN` | `SAD` |
| `SNOW` | `DEPRESSED` |
| `RAINBOW` | `ENERGETIC` |
| (없음) | `SHY` · `EMBARRASSED` · `ANGRY` - 새로 생긴 자리 |

### `code` 를 바꾸지 않은 이유

`SUNNY_COLLECTOR` · `RAINY_DAY` · `RAINBOW_30` 은 날씨 시절 이름이지만 **식별자**다.
`tb_user_badge` 가 이 값으로 사용자의 획득 이력을 들고 있고, 앱도 code 로 뱃지를 찾는다.
보이는 이름(`name`)과 조건문(`condition_text`)만 감정 어휘로 옮겼다 - 사용자가 읽는 것은 그쪽이다.

## 영향

- **되돌릴 수 없는 손실이 있다.** 6 -> 9 는 늘리는 방향이라 옛 값은 전부 새 값으로 간다.
  반대로 되돌리면 `ANGRY` · `EMBARRASSED` · `SHY` 는 옛 어휘에 자리가 없어 가장 가까운 값으로 뭉갠다.
  롤백은 그 뭉개짐을 사람이 먼저 승인해야 한다.
- 애플리케이션은 `ddl-auto: validate` 라 이 SQL 이 먼저 실행돼야 기동된다.
  엔티티 필드명이 `emotion` 으로 바뀌었고 매핑이 암시적(`@Column(name)` 없음)이라 이름을 그대로 본다.
- **MySQL 은 DDL 이 암시적 커밋을 일으킨다.** 1) -> 2) -> 3) 을 한 트랜잭션으로 묶을 수 없다.
  각 `UPDATE` 는 `ELSE` 로 제자리를 두어 여러 번 돌려도 같은 결과다(멱등) - 중간에 실패하면 그 지점부터 이어서 돌린다.
- 지금 데이터는 0건이라 실제 변환량은 없다. 절차는 데이터가 있을 때를 기준으로 썼다.
