# 2026-10-20 tb_guest_device 테이블 추가

> 2026-10-20 · DB 변경 · SQL `sql/patch/2026-10-20-게스트-기기-테이블.sql`
> 근거 ADR [로그인 없이 쓰는 게스트 모드](../adr/2026-10-20-로그인-없이-쓰는-게스트-모드.md)

## 무엇을
기기 1대에 사용자 번호 1개를 발급하는 `tb_guest_device` 1개 추가.

## 왜
로그인 없이도 일기를 쓰고 캘린더에 쌓이게 하려면 **사용자 번호가 필요하다.** 지금은 앱이
`EXPO_PUBLIC_DEV_USER_ID=1` 을 보내 모두가 1번 사용자로 들어온다 - 기기가 둘이면 기록이 섞인다.

이 테이블의 `id` 가 곧 사용자 번호다. 인증이 붙는 날 `tb_user` 가 생기고 이 테이블은
"기기 -> 사용자" 매핑만 남는다(그때 `user_id` 컬럼이 추가된다). 로그인 시 병합 규칙이 필요 없는 이유도
그것이다 - 게스트가 로그인해도 **사용자 번호가 바뀌지 않는다.**

## 영향
- 신규 테이블. 기존 데이터 영향 없음. 예상 행 수 = 앱을 설치한 기기 수.
- 애플리케이션은 `ddl-auto: validate` 라 이 SQL 이 먼저 실행돼야 기동된다.
- 기존 데이터(사용자 1번으로 쌓인 일기)는 그대로 둔다. 개발용 `EXPO_PUBLIC_DEV_USER_ID` 가 살아 있어
  그 번호를 계속 쓸 수 있다.

## 먼저 확인할 것

로컬에서 `ddl-auto=update` 로 띄운 적이 있다면 하이버네이트가 **이미 테이블을 만들어 두었다.**
그 테이블에는 **`ux_guest_device_hash` unique 인덱스가 없다** - 기기 1대 = 사용자 1명이 보장되지 않는다.
`DROP TABLE tb_guest_device;` 로 떨어뜨린 뒤 이 패치를 실행한다(게스트 번호는 다시 발급된다).

## 실행 순서
1. 개발 DB 에 SQL 실행 (담당: 개발자)
2. 애플리케이션 기동 확인 (`validate` 통과 = 매핑 일치)
3. 운영은 최초 배포 시 동일 순서

## 제약과 인덱스
| 이름 | 종류 | 의미 |
|---|---|---|
| `PRIMARY` | PK | id (`AUTO_INCREMENT`). 이 값이 사용자 번호다 |
| `ux_guest_device_hash` | unique(+alive) | 기기 1대 = 사용자 1명. 같은 기기가 두 번 등록되면 기록이 갈린다 |

## 개인정보
기기 UUID 원문을 저장하지 않고 **SHA-256 hex** 만 둔다(ADR 1번). 로그에도 남기지 않는다.
이 값으로 남의 기록을 열 수 있는 것은 아니지만(그건 인증이 할 일이다), 한 번 샌 값이
영구 식별자가 되지 않게 한다.
