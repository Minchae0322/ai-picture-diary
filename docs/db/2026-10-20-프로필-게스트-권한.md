# 2026-10-20 tb_profile 에 role 추가

> 2026-10-20 · DB 변경 · SQL `sql/patch/2026-10-20-프로필-게스트-권한.sql`
> 근거 ADR [로그인 없이 쓰는 게스트 모드](../adr/2026-10-20-로그인-없이-쓰는-게스트-모드.md)

## 무엇을
`tb_profile` 에 `role varchar(20) NOT NULL DEFAULT 'GUEST'` 컬럼 1개 추가.

## 왜
게스트인지 계정 보유자인지를 **프로필이 들고 있어야** 하기 때문이다.

처음에는 `tb_guest_device` 에 행이 있는지로 판단했는데, 그 설계에는 결함이 있다.
ADR 이 "로그인해도 사용자 번호가 바뀌지 않는다"로 정했으므로 **로그인한 뒤에도 기기 행이 그대로 남는다** -
그러면 그 사람은 영원히 게스트로 판정된다. 권한을 계정 쪽에 두면 승격이 필드 하나를 바꾸는 일이 된다.

`tb_profile` 이 자리인 이유는 그것이 이미 사용자 테이블을 겸하고 있어서다(엔티티 주석).
`tb_guest_device` 는 "기기 -> 사용자" 매핑만 맡는다.

## 영향
- 기존 행은 전부 `GUEST` 가 된다. 아직 로그인이 없으므로 사실과 맞다.
- 애플리케이션은 `ddl-auto: validate` 라 이 SQL 이 먼저 실행돼야 기동된다.
- 읽기 경로(일기 조회)에서도 이 값을 보지만 **프로필을 만들지는 않는다** - 없으면 게스트로 본다.

## 먼저 확인할 것

로컬에서 `ddl-auto=update` 로 띄운 적이 있다면 하이버네이트가 **이미 컬럼을 만들어 두었다.**
모양이 다르다 - 하이버네이트는 `enum('GUEST','MEMBER')` 로, 이 패치는 `varchar(20)` 으로 만든다.
그대로 두고 패치를 실행하면 `Duplicate column name 'role'` 이 난다.
`ALTER TABLE tb_profile DROP COLUMN role;` 로 떨어뜨린 뒤 실행한다.

## 실행 순서
1. 개발 DB 에 SQL 실행 (담당: 개발자)
2. 애플리케이션 기동 확인 (`validate` 통과 = 매핑 일치)
3. 운영은 최초 배포 시 동일 순서
